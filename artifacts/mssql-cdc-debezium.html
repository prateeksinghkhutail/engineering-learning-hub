Part 1: The problem

Why read the log

01

What change data capture is

CDC records every insert, update and delete on a table, in order, by reading the database’s own log.

WhatA stream of every committed row change.
WhyWarehouses, caches and other services must stay in step with the database.
HowRead the transaction log instead of asking the application or querying the table.
ApproachHowWeakness
Dual writesApp writes to the database and to a message busThe two writes can’t share a transaction, so they drift apart
Query pollingSELECT … WHERE updated_at > ? on a scheduleSees only the current state
Log-based CDCRead the transaction logMore setup, tied to database internals
  • Every change. Deletes and each in-between update are included. Guaranteed
  • Before and after. You get the row on both sides of the change.
  • Commit order. Changes arrive in the order the database committed them. Guaranteed
  • No app changes. The application does not know CDC exists.

02

Why polling is not enough

A query shows where a row ended up. It cannot show what happened on the way.

Try it: change a row between two polls

Update the status a few times, then run the poll.
  • In-between updates vanish. Three updates between polls look like one.
  • Deletes are invisible. A deleted row matches no WHERE clause, so it looks like “nothing changed”.
  • Late commits slip through. A row stamped 10:00:59 but committed at 10:01:02 is missed by both polls.

Soft deletes

Works only if every script and every person follows the rule.

Poll more often

Narrows the window. Never closes it. Adds load.

Full table diff

Catches deletes. Expensive. Still misses in-between updates.

Why can’t a poller see a delete?
The row no longer exists, so no query returns it. The log has an explicit delete record.

Follow the update

If someone sets the salary to 110000 and then 120000 between two polls, a poller reports one change. The log holds two. Example value

03

The transaction log and LSNs

The database writes every change to a log first, and every log record has a position called an LSN.

WhatAn ordered, append-only record of every change.
WhyCrash recovery and replication need it, so it is always complete.
HowEach record gets a Log Sequence Number that only goes up.
  • Written first. The log record is written before the data page changes. Guaranteed
  • Only goes up. A higher LSN always means later. Guaranteed
  • A bookmark. “I have read up to LSN X” is how any log reader keeps its place.

Follow the update

The update becomes two log records inside one transaction. Example value

                            Salary 100000 -> 120000
LSN 00000031:00000a48:0005  COMMIT

Why CDC for our pipeline

We need many databases copied into Snowflake continuously, for more than one consumer, without touching application code.

  • Hooks only see writes that pass through the ORM. Migration scripts and bulk SQL bypass them.
  • Polling has the gaps from the last lesson, and its cost grows with table size.

Part 2: SQL Server CDC

Capture inside the database

05

How SQL Server captures a change

A background process copies changes from the log into a change table that anyone can query.

WhatSQL Server’s built-in CDC feature.
WhyReaders get changes with plain SQL and never parse the log.
HowA capture process scans the log and writes each change into a change table.
  1. Write. The application changes the row.
  2. Log. SQL Server records it in the transaction log.
  3. Scan. The capture process reads the log, about every 20 s on Azure SQL Database. Default · check 1
  4. Copy. It writes the change into the change table.
  5. Read. A consumer asks for changes between two LSNs.
What happens internally
On a SQL Server VM or Managed Instance, capture and cleanup are SQL Server Agent jobs with a configurable schedule. Azure SQL Database has no Agent: a built-in scheduler runs capture roughly every 20 seconds and cleanup hourly.

What a change table holds

One row per insert or delete, two rows per update, each stamped with its commit LSN.

__$operationMeaningRows written
2InsertOne, with the new values
3 and 4UpdateTwo: the row before, and the row after
1DeleteOne, with the last values
ColumnWhat it is
__$start_lsnCommit LSN of the transaction
__$seqvalOrder of the change inside its transaction
__$update_maskWhich columns changed
  • Full before image. Updates always carry the old row, because it is stored as its own row. Guaranteed
  • Ordered. Sort by __$start_lsn, then __$seqval, and you have commit order.
How many change-table rows does one UPDATE produce?
Two: operation 3 (before) and operation 4 (after).

Capture instances and turning CDC on

A capture instance is one frozen-shape capture of a table: a change table plus the functions to read it.

EXEC sys.sp_cdc_enable_db;
CREATE ROLE cdc_reader;

EXEC sys.sp_cdc_enable_table
    @source_schema        = N'dbo',
    @source_name          = N'Employee',
    @role_name            = N'cdc_reader',
    @capture_instance     = N'dbo_Employee_v1',
    @supports_net_changes = 1;
  • Frozen shape. New columns never appear in an existing instance. Guaranteed
  • Two at most. A table can have two capture instances, no more. Guaranteed
  • Leave columns out. @captured_column_list keeps large or sensitive columns out at the source.
Our decision: Versioned instance names (_v1, _v2) and an explicit gating role instead of NULL.

08

Retention, cleanup and the cost to the source

Change rows are deleted after a retention period, and that period is the one hard deadline in the whole pipeline.

If the reader is down longer than retention, the changes exist nowhere. The only fix is a new snapshot.
  • Stock retention is about 3 days. Default · check 2
  • Storage. Change tables live in the same database until cleanup removes them.
  • Double writes. Every captured change is written again into the change table.
  • Log growth. The log can’t be truncated past the point capture has reached.
Our decision: Raise retention to 7 days.
EXEC sys.sp_cdc_change_job @job_type = N'cleanup', @retention = 10080;  -- minutes
What happens if the reader is down longer than retention?
The change rows it needed are deleted. The only recovery is a new snapshot.

Part 3: Debezium

Changes become events

10

What Debezium adds

SQL Server CDC stops at tables inside the database. Debezium turns those tables into a stream.

SQL Server CDC captures database changes. Debezium converts those captured changes into a continuously consumable event stream.
  • Polls the change tables continuously, by LSN.
  • Orders changes from many tables into commit order.
  • Merges the two rows of an update into one event.
  • Remembers its position and survives restarts.
  • One task per database, because a log must be read in order. Guaranteed
Our decision: Debezium on Kafka Connect, deployed with Strimzi on AKS. Kafka and the schema registry on Confluent Cloud.

Snapshots: copying what already exists

Change tables only hold recent changes, so Debezium first copies the existing rows.

  1. Note the LSN. Record the current maximum LSN before reading anything.
  2. Scan. Read each table and emit every row with op = "r".
  3. Stream. Switch to streaming from the LSN noted in step 1.
SituationTypical choice
Small to medium tablessnapshot.mode=initial with snapshot isolation
Very large tablesno_data, then backfill incrementally
Adding or repairing one tableIncremental snapshot of that table
  • Nothing is lost. The LSN is noted first, so changes made during the scan arrive afterward.
  • Stock mode is initial. Default
  • Stock isolation blocks writers. repeatable_read is the default. Use snapshot instead. Default
  • A signal table triggers incremental snapshots. It is the only table Debezium writes to.

13

Offsets and schema history

A connector’s whole memory is two things: where it is in the log, and what the tables looked like along the way.

  • Names are permanent. The offset key contains the connector name and topic.prefix. Change either and you get a full re-snapshot. Guaranteed
  • Why history exists. After a restart the connector may read changes older than today’s table shape.
  • Keep them together. Back up, move or reset both, never one alone.
  • History topic rules. One partition, infinite retention, never shared.

Schema history is the Schema Registry.

Schema history is private to the connector. The registry describes messages for consumers.

What happens if you rename a connector?
Its offsets are stored under the old name, so it starts over with a full snapshot.

14

At-least-once: why duplicates happen

Offsets are saved after events are sent, and only now and then, so a crash means some events are sent twice.

Try it: crash before the bookmark is saved

Send a few events, then crash without saving the offset.
  1. Send. The task hands events to Connect, which produces them to Kafka.
  2. Acknowledge. Kafka confirms it has them.
  3. Save. Every offset.flush.interval.ms, Connect saves the offsets. Stock value: 60 s. Default · check 14
  • Nothing lost, some repeated. That is the at-least-once guarantee. Guaranteed
  • Replays are contiguous. You may see A, B, C, B, C, D. Never a scrambled history.
  • Exactly-once exists. It covers only the Debezium-to-Kafka hop, so consumers still need the guard below.
Rule of thumb. Upsert by key, and keep a change only if its (commit_lsn, change_lsn) is newer than what is stored.
If it breaks: A connector can show RUNNING while its task is FAILED. Kafka Connect does not restart a failed task for you. Watch the task state.

Part 4: Kafka, bytes and schemas

Transport and contract

15

Kafka: topics, partitions and keys

Kafka is a durable log of records, split into partitions, where the key decides which partition a record lands in.

WhatA replicated, append-only log that many readers share.
WhyIt buffers when Snowflake is down, feeds many consumers, and allows replay.
HowThe key’s hash picks a partition. Same key, same partition, same order.
  • Order is per partition. There is no global order across rows or tables. Guaranteed
  • Partition count is the ceiling on how many consumers can read in parallel.
Our decision: One topic per business table, shared by all tenant-group databases, keyed by database ID plus primary key.

The transform that builds the combined key is still to be chosen. ByLogicalTableRouter is the usual tool. Simplified · check 3

Why do all events for one row land in the same partition?
The key is hashed to pick the partition, and the key is the same for every event of that row.

Consumers, replay and retention

Each consumer group keeps its own bookmark, so readers never wait for each other and can rewind.

Into Snowflake: RAW first, then curated

  
The sink only appends, so RAW holds every change, and a merge turns that history into current state.


MERGE INTO CURATED.EMPLOYEE t
USING (
  SELECT * FROM RAW.EMPLOYEE_CHANGES_STREAM
  QUALIFY ROW_NUMBER() OVER (
    PARTITION BY DATABASE_ID, EMPLOYEEID
    ORDER BY __SOURCE_COMMIT_LSN DESC, __SOURCE_CHANGE_LSN DESC NULLS LAST) = 1
) s
ON t.DATABASE_ID = s.DATABASE_ID AND t.EMPLOYEEID = s.EMPLOYEEID
WHEN MATCHED AND s.__DELETED = 'true' THEN DELETE
WHEN MATCHED AND s.__SOURCE_COMMIT_LSN >= t.SRC_COMMIT_LSN THEN UPDATE SET ...
WHEN NOT MATCHED AND s.__DELETED <> 'true' THEN INSERT ...;
  • QUALIFY picks the newest event per key.
  • The LSN comparison makes replays harmless.
  • __DELETED turns delete events into real deletes.
  • New columns are added to RAW by the sink’s schema evolution, not by hand. Simplified · check 12
Our decision: Snowflake Kafka connector v4 with Snowpipe Streaming into RAW native tables. Curated current-state tables are Snowflake-managed Iceberg.
The merge above is a sketch, and whether events are flattened at the source or in Snowflake is open. Simplified · check 13

Part 6: Schema changes
When the shape moves




  
22
Why schema changes are hard

  
A row change flows through a pipe. A schema change alters the shape of the pipe, and the shape is stored in six places.


On SQL Server, ALTER TABLE alone changes nothing in the event stream. No error. No new column.
  • Silent. Forget the new capture instance and events keep the old shape for days.
  • Loud. A schema the registry rejects stops the connector.
  • Not atomic. Events in flight straddle the change, whatever you do.
You run ALTER TABLE ADD column and nothing else. What do events look like?
Unchanged, with no error. The capture instance is frozen, so a new one is needed.

Capture instance rotation: from v1 to v2

  
To pick up a new shape, create a second capture instance, let Debezium cross over, then drop the first.


WhatMoving a table to a new capture instance while data keeps flowing.
Whyv1 is frozen, and v2 only holds changes from the moment it was created.
HowRun both side by side until Debezium has passed v2’s start LSN.
Try it: drag through a rotation
No missed events

No duplicates
The handover is on one LSN boundary. Replays are absorbed by the merge.
Right shapes

Running it: monitoring, security and cost

  
A pipeline that stalls silently is worse than one that fails loudly, so most of operations is making stalls loud.


End-to-end freshness
Commit time at the source versus arrival in Snowflake. Catches a problem at any hop.
Heartbeat canary
A small row written on a schedule in each database. Tells a quiet database from a broken pipeline.
Retention headroom
How close Debezium’s position is to the cleanup horizon. The early warning for the one failure that loses data.
Reconciliation drift
Periodic source-versus-warehouse comparison. Catches silent divergence.
Our decision: These four monitors are first-class parts of the design. Simplified · check 15

  • Least privilege. Debezium needs SELECT on captured tables and the cdc schema, plus INSERT on the signal table. The operator needs more, so give it its own identity.
  • Keep secrets out of connector configs. They are readable through the REST API.

  • Cost drivers. Source tier, Kafka throughput and retention, Snowflake merge frequency, AKS workers.

Common misconceptions

  
Six beliefs that sound right and are not.


Reading the log misses updates and deletes.
Polling misses them. The log is the one place that has every committed change.
Debezium is a server you run.
It is code loaded inside a Kafka Connect worker.
A connector in state RUNNING is healthy.
Its task can be FAILED while the connector shows RUNNING. Watch the task.
ALTER TABLE flows through the pipeline by itself.
On SQL Server nothing changes until a new capture instance is created.
Schema history is the Schema Registry.
Schema history is the connector’s private memory. The registry serves consumers.
Binary messages describe themselves.
They carry only a schema ID. Without the registry they can’t be decoded.

Quick revision and glossary

  
Test yourself across the whole course, then look up any term.


Why is Debezium needed when SQL Server already has CDC?
CDC stops at change tables. Debezium polls them, keeps a bookmark, orders across tables, snapshots old data and publishes events.
What is the latency floor on Azure SQL Database?
About 20 seconds, the fixed capture interval.
Which Azure SQL Database tiers support CDC?
vCore, and DTU S3 and above.
Why does Debezium produce duplicates after a crash?
Offsets are saved after events are acknowledged, and only periodically.
What two pieces of state does a connector have?
Offsets and schema history. Keep them together.
Why is the Kafka key database ID plus primary key?
Topics are shared across databases. The combined key keeps each row in one partition without colliding.
What happens when the registry rejects a schema?
The task goes to FAILED. Nothing is lost, but the pipeline stops.
When is it safe to drop capture instance v1?
When Debezium’s committed commit_lsn is past v2’s start LSN.
Why might the registry show no new version right after a rotation?
The new schema registers with the first row change after the boundary. A quiet table has none.
Which single failure loses data?
CDC retention expiring before Debezium reads the changes.
Why does Snowflake need a merge?
The sink only appends. RAW holds every change, and the merge keeps the latest per key.
How does a stalled reader hurt PostgreSQL differently?
Its replication slot holds the log until the disk fills. SQL Server deletes the rows instead.
