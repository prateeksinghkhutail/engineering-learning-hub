Part 1: Foundations

Cluster, brokers, topics

01

The simplest mental model

Kafka is a shared notebook that programs append lines to, and that other programs read at their own pace.

Why it exists

Without Kafka

orders-apipayments, email, analytics

One slow receiver slows the sender. Add a 4th receiver and you change the sender.

With Kafka

orders-apiKafkapayments, email, analytics

Sender and receivers never meet. A receiver can be down for an hour and catch up.

Cluster and broker

A Kafka cluster is made up of multiple Kafka brokers. A broker is one Kafka server process.

What runs inside one broker

What is a Kafka cluster made of, and what is one of those things?
Brokers. A broker is one Kafka server process that stores partitions on its disk and answers client requests.

Follow order 101

orders-api has a new order. Instead of calling payments, email and analytics, it will write one record to Kafka and move on.

02

The broker

A broker stores partitions on its disk and answers requests about them.

WhatOne Kafka server with a unique number, its node.id (older docs say broker ID).
WhySomething has to hold the data and talk to clients.
HowIt appends producer records to files, serves them to consumers, and copies partitions to and from other brokers.
  • Takes writes from producers for partitions it leads
  • Serves reads to consumers
  • Stores partition replicas under its log.dirs folder
  • Replicates: follower replicas fetch from leaders on other brokers
  • Reports in to the controller with heartbeats

Why not one big server?

More room

One disk fills up. Three disks hold three times as much.

More speed

Writes and reads spread over machines instead of queueing at one.

Survival

If one broker dies, copies on the others keep the data available.

Does a single Kafka broker hold a whole topic?
Usually not. A broker holds only the partition replicas assigned to it, typically a few partitions from several topics.

Follow order 101

Our record will be handled by broker 1. This is the part of its config that makes it “broker 1”. Example value

WhySo order events and payment events don't mix, and each can have its own settings.

Part 2: The log itself

Partitions, records, offsets

04

Partitions

A partition is one append-only log. A topic is a set of them.

WhatAn ordered sequence of records that only grows at the end.
WhyOne log can sit on only one disk and be read by one worker in order. Many logs can sit on many brokers and be read in parallel.
HowEach record goes to exactly one partition and gets the next number in that partition.

What you get

Scale

3 partitions on 3 brokers means 3 disks and 3 machines taking writes.

Parallelism

3 partitions can be read by 3 consumers at once.

Order, per partition

In P0, Order98 is always read before Order101. Guaranteed · check 3

No global order. Kafka never promises that Order102 (in P1) is read before Order103 (in P2). The partitions are independent logs read by independent workers. Making them agree on one order would mean one queue again, and the scaling would be gone.
A topic has 3 partitions. Is a record in partition 1 guaranteed to be read before a later record in partition 2?
No. Order is guaranteed only inside one partition. Partitions are independent logs read by independent consumers.

Follow order 101

Order 101 will live in exactly one of these three partitions: partition 0. Output trimmed. Which broker leads which partition will differ on your cluster. Example value · check 2

05

The record

A record is a key, a value and a little metadata. To Kafka the key and value are plain bytes.

  • Key decides the partition (lesson 8). It is not a unique ID.
  • Value is your payload: JSON, Avro, anything.
  • Headers carry extras such as trace IDs.
Which parts of a Kafka record does your code set, and which does Kafka assign?
You set key, value, headers and usually the timestamp. The partition is picked by the producer's partitioner and the offset is assigned by the leader broker when it appends the record.

Follow order 101

This is the record as orders-api builds it. There is no partition or offset in it yet. 

String json = "{\"orderId\":101,\"customerId\":500,\"amount\":1200}";
var record = new ProducerRecord<>("orders", "customer-500", json);
record.headers().add("source", "web".getBytes(UTF_8));
06

Offsets

An offset is a record's seat number inside one partition.

  • Offsets only go up and are never reused. Guaranteed
  • Each partition counts on its own.
  • A record's full address is (topic, partition, offset), for example (orders, 0, 42) for order 101.
A topic named orders has 3 partitions. Which record is “offset 1 of orders”?
Trick question. There are three: one in each partition. You must name the partition.

Follow order 101

Order 101 becomes offset 42 of partition 0. The tool below prints each partition's next offset, so 43 means “42 was the last one written”. Example value · check 4

$ kafka-get-offsets.sh --bootstrap-server kafka-1:9092 --topic orders

Part 3: Writing and reading

Producers, consumers, groups

07

The producer

A producer finds out who leads the target partition, then sends straight to that broker.

  1. Connect. The producer dials any address in bootstrap.servers.
  2. Get metadata. It learns every broker, topic, partition and leader, and caches the map.
  3. Choose a partition. Done inside the producer, not by the broker (next lesson).
  4. Batch. Records for the same partition are grouped for a few milliseconds.
  5. Send to the leader. Directly. There is no router in the middle.
  6. Append. The leader writes the batch to its log and assigns offsets.
  7. Replicate and ack. Followers copy it. With acks=all the producer hears back once the in-sync copies have it.
If the leader moved: the broker answers “not the leader”, the producer refreshes metadata and retries on the new leader.
Does a producer send its records to the bootstrap broker?
No. The bootstrap broker only answers the first metadata request. Records go directly to the broker that leads the target partition.

Follow order 101

The producer only knew broker 2's address. Metadata told it broker 1 leads partition 0, so the record went there. The ack carries the address. 

// producer config: bootstrap.servers=kafka-2:9092, acks=all
RecordMetadata md = producer.send(record).get();
// md.topic() = "orders"   md.partition() = 0   md.offset() = 42

09

The consumer

A consumer asks for records starting at an offset. Kafka never pushes.

  • Pull, not push. A slow consumer simply asks less often. It cannot be flooded.
  • Reading deletes nothing. The records stay in the log. Guaranteed · check 6
  • Many readers, same records. Each has its own position.
A consumer reads a record. Is the record removed from the partition?
No. Reading never deletes. The record stays until the retention policy removes it, and other consumers can still read it.

Follow order 101

A payment-service consumer fetches from offset 42 and receives the record with its coordinates.

Consumer groups

A group is a team of consumers that splits a topic's partitions between its members.

Within one consumer group, a partition is read by only one consumer at a time. Guaranteed · check 7

Try it: resize the payment-service group

Consumers in the group:

Which consumer gets which partition depends on the assignor. The counts are what matter. Simplified · check 7

  • Why one consumer per partition? Two readers on one log would race, and order would be lost.
  • Partition count caps parallelism. A 4th consumer on 3 partitions waits as a spare.
  • Membership changes trigger a rebalance: partitions are handed out again.

A different group reads everything again

Rule of thumb. Same group = share the work. Different groups = each gets its own full copy of the stream.
A topic has 3 partitions and a consumer group has 5 members. How many members do work?
Three. Each partition goes to exactly one member, so two members sit idle as spares.

Follow order 101

Partition 0 belongs to consumer-1, so only consumer-1 charges this order. The analytics group gets its own copy through its own member. Output trimmed. Example value · check 7

Consumer offsets

A group saves its bookmarks in Kafka itself, in an internal topic named __consumer_offsets.

PositionWhere this consumer will read next. Lives in memory.
CommittedThe saved bookmark: the next offset the group should read after a restart.
GapRecords read but not yet committed. A crash replays them.

Try it: poll, commit, crash

committedread, not committednot read yet
  • Restart: the consumer resumes from the committed offset, not from where it was.
  • Replay: reset a group's offsets to an earlier point and it reads old events again. Possible because reading never deleted them. Guaranteed · check 9
  • Brand new group: auto.offset.reset decides: earliest or latest. The consumer default is latest. Default
What happens internally
A commit is just a record written to __consumer_offsets with key (group, topic, partition) and the offset as value. One broker acts as the group coordinator for each group and handles these commits and the group's membership.
A group's committed offset for a partition is 43. Which record did it last finish?
Offset 42. The committed offset is the next record to read, not the last one processed.

Part 4: Surviving failure

Replicas, leaders, ISR, failover

12

Replication

Every partition is copied to several brokers, so losing a machine does not lose data.

WhatReplication factor (RF) = how many copies of each partition exist. RF 3 is the usual choice.
WhyDisks die and servers reboot. One copy means one accident from data loss.
HowOne copy is the leader, the rest are followers that keep copying from it.
  • A copy on a broker is called a replica. Leader and followers are all replicas.
  • RF 3 can lose 2 brokers and still have the data, as long as the survivors were caught up.
  • RF cannot exceed the number of brokers: two copies on one machine protect nothing.
With replication factor 3, how many brokers can fail before a partition's data is gone?
Two, as long as the surviving replica was in sync. The third copy still has every acknowledged record.

Follow order 101

Order 101 is stored three times, in the same folder name on three machines. Example value · check 12

kafka-1:/var/lib/kafka/data/orders-0/    leader
kafka-2:/var/lib/kafka/data/orders-0/    follower
kafka-3:/var/lib/kafka/data/orders-0/    follower
13

The partition leader

One replica decides the order of records. Everyone else copies it.

  • Why a leader? If two brokers both accepted writes for P0, they could disagree on what offset 42 is. One writer means one order.
  • All writes go to the leader. Reads go there too by default. Default
  • High watermark: the last offset that every in-sync replica has. Consumers only see records up to it, so they never read something that could vanish in a failover.
What is the high watermark, and why can consumers not read past it?
It marks the last offset that every in-sync replica has. Records beyond it exist only on the leader and could vanish in a failover, so consumers are not shown them.

Follow order 101

Broker 2 asks broker 1 for whatever comes after its own last record. Broker 3 does the same. Once both have offset 42, the high watermark moves to 43. Real field names, most fields left out. Simplified

  replicaId: 2
  topic: orders   partition: 0   fetchOffset: 42

FetchResponse  broker 1 → broker 2
  highWatermark: 42
  records: [ offset 42 | key customer-500 | 46-byte value ]
14

ISR: in-sync replicas

The ISR is the list of replicas that are fully caught up with the leader right now.

  • Why track it? Kafka needs to know which copies are safe to promote.
  • Failover: a new leader is picked from the ISR, so no acknowledged record is lost.
  • Durability: with acks=all, a write is acknowledged only after every ISR member has it.
The classic safe setup. RF = 3, min.insync.replicas = 2, acks=all. Every acknowledged write is on at least 2 brokers, and one broker can be down without blocking writes. This is a recommendation: min.insync.replicas is 1 out of the box. Default · check 16 Guaranteed · check 11
A producer uses acks=all on a topic with replication factor 3 and min.insync.replicas 2. One broker is down. Does the write succeed?
Yes. Two replicas are still in sync, which meets the minimum. With two brokers down it would be rejected.

Follow order 101

When order 101 was written the ISR was full, so acks=all waited for all three brokers. Had broker 3 been lagging, the ISR would be 1,2 and the ack would still come, because 2 meets min.insync.replicas=2. Guaranteed · check 11

Partition: 0   Leader: 1   Replicas: 1,2,3   Isr: 1,2,3     ← as it was
Partition: 0   Leader: 1   Replicas: 1,2,3   Isr: 1,2       ← if broker 3 lags
15

When a broker crashes

Followers in the ISR already have the data. One of them is promoted and clients switch over.

Try it: click a broker to crash or restart it

All three brokers are up.
  1. Detect. Every broker sends heartbeats to the controller. Silence past the session timeout means down.
  2. Elect. For each partition the dead broker led, the controller picks another ISR member.
  3. Announce. The change is written to cluster metadata and every broker learns it.
  4. Producers get an error, refresh metadata, retry on the new leader.
  5. Consumers do the same and continue from the same offset. Offsets are identical on every replica.
  6. Return. The old broker restarts, catches up as a follower and rejoins the ISR.
Partition 0 is led by broker 1, its ISR is {1, 2} and broker 3 is lagging. Broker 1 dies. Who becomes leader?
Broker 2. It is the only live member of the ISR. Broker 3 is not eligible because it is missing records.

Follow order 101

Broker 1 dies after order 101 was acknowledged. The record is still at offset 42 on brokers 2 and 3. The controller writes one metadata record and broker 2 leads. Guaranteed · check 10

Why Kafka needs a controller

Someone has to make cluster-wide decisions. That someone is the controller.

Registers brokers

Knows who joined, who is alive.

Creates topics

Decides which brokers get which replicas.

Elects leaders

Picks a new partition leader when one dies.

Publishes changes

Makes sure every broker hears the update.

Brokers decide alonetwo leaders for P0
One controller decidesone answer for everyone

Older Kafka kept this metadata in a separate system, ZooKeeper. Modern Kafka keeps it inside Kafka, using KRaft.

Follow order 101

When orders was created, the controller chose replicas 1,2,3 for partition 0 and made broker 1 the leader. That decision is why order 101 went to broker 1.

18

KRaft, starting from the problem

KRaft (Kafka Raft) is how a few controller nodes agree on the metadata, even when one of them fails.

One controller is a single point of failure. So run three. But now three machines must agree, and messages between them can be late or lost.

Why majority? Any two majorities of the same group share at least one member. So two conflicting decisions can never both win.

Follow order 101

“Broker 1 leads orders-0” is exactly the kind of fact controllers must agree on. If two of them disagreed, order 101 could be appended to two different logs at offset 42.

19

Kafka before KRaft

Metadata lived in ZooKeeper, a separate cluster you had to run next to Kafka.

Why Kafka moved away

  • Two systems to operate: separate deploys, security, monitoring and upgrades.
  • Slow controller failover: a new controller had to load all metadata from ZooKeeper before it could act.
  • Scaling limits: clusters with very many partitions hit this hard.
  • Two sources of truth that could drift: ZooKeeper's state and the controller's memory.
Timeline. KRaft became production-ready in Kafka 3.3 (2022). Kafka 4.0 (2025) removed ZooKeeper completely.

Follow order 101

In the ZooKeeper era, the same fact sat in a znode instead of a Kafka log.

KRaft architecture

A small quorum of controllers owns the metadata. Brokers follow along and handle the data.

QuorumThe set of controller nodes that vote. Usually 3 or 5.
ActiveThe one controller currently leading. It makes every decision.
StandbyThe other controllers. They hold a full copy and can take over at once.
LogThe metadata log: every cluster change, in order.
What do KRaft controllers store, and what do they never store?
They store cluster metadata: brokers, topics, partitions, leaders, ISR and configs. They never store application records.

The metadata log

Kafka stores its own metadata the same way it stores your data: as an append-only log.

Why a log works so well here

  • One order of events. Everyone applies the same changes in the same sequence.
  • Easy to compare. “I am at record 4” tells you exactly how up to date a node is.
  • Cheap catch-up. A node that was away fetches only the records it missed.
  • Fast failover. A standby controller already has the log. Nothing to reload.
What happens internally
The log is an internal single-partition topic called __cluster_metadata. Controllers are its voters. Brokers are observers: they fetch the log and build an in-memory metadata cache from it. Periodic snapshots keep the log from growing forever.

Two. A majority of 3 is needed to commit a change.

Low-level design

The same system zoomed in on partition orders-0. Follow the numbers.

Data path

  1. Producer asks the bootstrap broker for metadata
  2. Produces to the leader of orders-0
  3. Followers copy the records, the ISR stays full
  4. Consumer fetches from the leader
  5. Consumer commits its offset to the group coordinator

Control path

  • Brokers register with the active controller on startup
  • Brokers heartbeat to stay “alive”
  • Controller appends every change to the metadata log
  • Other controllers replicate that log
  • Brokers fetch it into their metadata cache

Follow order 101

Steps 1 to 5 on the diagram are order 101's exact route. The dashed lines did their work earlier, when the topic was created and leaders were chosen.

Who opens the connection: the controller to the broker, or the broker to the controller?
The broker. Everything in Kafka pulls: clients call brokers, followers call leaders, brokers call the controller.

One message, start to finish

Ten steps take one order from the producer's code to a committed offset.

key:   customer-500
value: { "orderId": 101, "customerId": 500, "amount": 1200 }
  1. Producer creates the record. Key and value are serialized to bytes.
  2. Metadata lookup. The producer's cached map says: orders has 3 partitions, P0 is led by Broker 1.
  3. Partition selection. hash("customer-500") mod 3 gives P0. Try it in the lesson 8 demo.
  4. Send to the leader. The record waits a moment in a batch, then goes to Broker 1.
  5. Leader appends. Broker 1 writes it at the end of orders-0 and assigns offset 42.
  6. Followers replicate. Brokers 2 and 3 fetch offset 42 and append it to their copies.
  7. Committed. The high watermark moves past 42. The producer gets its ack, and consumers can now see the record.
  8. Consumer fetches. The payment-service member that owns P0 asks “from 42” and receives it.
  9. Consumer processes. It charges the customer.
  10. Consumer commits 43. Meaning “next time, start at 43”. Saved in __consumer_offsets.

Follow order 101

Part 7: Disk and promises

Storage, retention, guarantees

28

How a broker stores records

Each partition replica is a folder. Inside it, the log is cut into segment files.

orders-0/                        # topic name, dash, partition number
    00000000000000000000.log      # records from offset 0
    00000000000000000000.index    # offset to file position
    00000000000000000000.timeindex# timestamp to offset

    00000000000001000000.log      # records from offset 1,000,000
    00000000000001000000.index
    00000000000001000000.timeindex

Why append-only is fast

Sequential writes

Writing at the end of a file is the cheapest thing a disk does.

Page cache

The OS keeps recent data in RAM, so most reads never touch the disk.

Zero-copy

Bytes go from file to network socket without passing through the application.

Batches

Records are written, stored and sent in groups, not one at a time.

How does a broker find offset 1,500,000 of a partition quickly?
Segment files are named after their first offset, so it picks the right file by name, then uses that segment's index to jump close to the record.

Retention

Records are removed by policy, never because someone read them. Guaranteed · check 15

By time

Drop segments older than a limit. Default: 7 days. Default · check 16

By size

Drop the oldest segments once a partition exceeds a size. Off by default.

Compaction

Keep only the latest record for each key.

A record was never read by any consumer. Can Kafka still delete it?
Yes. Retention works on age, size or compaction. Whether anyone read the record plays no part.

What Kafka promises

Kafka makes promises about order, durability and delivery, each with a condition.

Order inside a partition

Records are read in the order they were appended.

No order across partitions

Need order for an entity? Give its records the same key.

Durability

A write acked with acks=all survives as long as one in-sync replica does.

Availability

A partition stays usable while any ISR member is alive.

Delivery semantics

ModeHow you get itOn a crash
At most onceCommit the offset, then processA record may be skipped. Never repeated.
At least onceProcess, then commitA record may be processed twice. Never lost. The usual default.
Exactly onceIdempotent producer plus transactionsResults appear once, for read-process-write flows that stay inside Kafka. Simplified
Idempotent producer. The broker spots a retried batch by its sequence number and stores it once. On by default since Kafka 3.0. It is the reason producer retries don't create duplicates. Default
Your consumer processes a record, then crashes before committing. Which delivery semantics did you get?
At least once. After restart it resumes from the last committed offset and processes that record again. Go back to the lesson 11 demo and press “Crash and restart” to see it.

Follow order 101

Customer 500 places order 104 next. Same key, so it lands in partition 0 at offset 43 and is always read after order 101. If consumer-1 crashes after charging order 101 but before committing 43, the order is delivered again. So the charge must be safe to repeat, for example by using orderId as an idempotency key.

Common misconceptions

Nine beliefs that sound right and are wrong.

One topic lives on one broker.

A topic's partitions are spread across brokers.

Every broker stores the whole topic.

A broker stores only the partition replicas assigned to it.

Kafka deletes a message once it is consumed.

Retention is independent of reads.

Kafka orders the whole topic.

Order is guaranteed within a partition only.

KRaft stores application messages.

KRaft stores cluster metadata. Brokers store messages.

Offsets are global to a topic.

Each partition numbers its records from 0.

More consumers always means more speed.

A group cannot use more consumers than partitions.

The broker pushes records to consumers.

Consumers pull, at their own pace.

Producers send to a load balancer.

Producers send directly to each partition's leader.

Four failures, four recoveries

Every failure has the same shape: detect, hand over, resume.

Broker 1 crashes

heartbeats stopcontroller marks it downISR followers become leadersclients refresh metadata, continue

Partitions run with fewer replicas until Broker 1 returns and catches up.

Controller leader crashes

active controller silenta standby asks for votesmajority elects itit continues from the metadata log

Producers and consumers do not notice. Only metadata changes pause for a moment.

Consumer crashes

consumer stops heartbeatingcoordinator removes itrebalance: its partitions go to othersthey resume from committed offsets

Records read but not committed by the dead consumer are processed again.

Producer loses its connection

send fails or times outproducer retriesbroker drops duplicates by sequence numberrecord stored once

If retries run past delivery.timeout.ms, the send fails and your code gets the error.

Follow order 101

In the four failures above: order 101 stays at offset 42 on brokers 2 and 3. Nothing happens to it when a controller dies. It is charged again if consumer-1 crashed before committing 43. It is stored once even if orders-api had to retry.

Three stacks. If you can redraw these from memory, you have Kafka.

Quick revision and glossary

Test yourself, then look up any term.

Name the two planes of a Kafka cluster and what travels on each.
The data plane carries your records between producers, brokers and consumers. The control plane carries metadata between brokers and the KRaft controllers.
Trace a Kafka record from producer to committed offset in five steps.
The producer hashes the key to pick a partition. It sends to that partition's leader. Followers copy the record and the high watermark moves. A consumer fetches and processes it. The consumer commits the next offset.
What replaced ZooKeeper in Kafka, and which version removed ZooKeeper?
KRaft, a quorum of controllers that keeps cluster metadata in a replicated log inside Kafka. ZooKeeper was removed in Kafka 4.0.
How do you keep all events for one customer in order?
Give them the same key. The same key always hashes to the same partition, and order is guaranteed inside a partition.
