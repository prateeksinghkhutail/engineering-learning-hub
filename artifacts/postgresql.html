Why a database at all?

In plain wordsImagine an online shop writing every order into one spreadsheet file. Two customers buy at once and one order overwrites the other. The power cuts while saving and the file is corrupted. Finding one order among ten million means reading the whole file. A database exists to solve exactly these three problems.

A database is a program whose job is to remember data safely, let many people change it at the same time, and find any piece of it quickly.

Client and server

  • PostgreSQL (“Postgres”) is a server program. It listens for connections on port 5432 by default. Default
  • Your code is the client. It connects, sends a request, and gets an answer.
  • It is free and open source, known for correctness and for many advanced features this course reaches later.
Name three problems a database solves that a plain file does not.
Many users changing data at once without losing changes; surviving a crash without half-written data; and finding one record quickly among millions.

Tables, rows and keys

In plain wordsThink of three spreadsheet tabs: customers, products and orders. An order row does not copy Asha’s name; it just says “customer 42”. That number is the link. Linking tables by numbers is what “relational database” means.

New words

tableA named grid of data, like a spreadsheet tab.
rowOne record: one user, one order.
columnOne fact every row has: name, quantity, total.
primary keyA column whose value is unique per row, used to find it. Usually id.
foreign keyA column holding another table’s primary key, linking the two rows.

PostgreSQL stores data in tables: each row is one thing, each column one fact about it, and keys link rows in different tables.

  • Foreign keys keep links valid: PostgreSQL refuses an order for a user that does not exist. Guaranteed
  • Columns have types: bigint for whole numbers, text, numeric(10,2) for money, timestamptz for times.
  • Constraints are rules the database enforces, such as “quantity must not go below 0”.
Why does the orders table store user_id 42 rather than Asha’s name?
So each fact is stored once. If Asha changes her name, only her users row changes; every order still points to her through 42.

Talking to PostgreSQL: five SQL statements

In plain wordsSQL reads almost like English: “select the name from users where the id is 42”. You describe what you want, and PostgreSQL works out how to get it. That “how” is much of this course.

SQL is the language for creating tables and adding, reading, changing and deleting rows; you type it into psql or send it from your app.

-- 1. Create a table
CREATE TABLE inventory (product_id bigint PRIMARY KEY, name text, quantity int CHECK (quantity >= 0));

-- 2. Add a row
INSERT INTO inventory VALUES (123, 'Widget', 5);

-- 3. Read rows
shop=# SELECT name, quantity FROM inventory WHERE product_id = 123;
  name  | quantity
--------+----------
 Widget |        5

-- 4. Change rows
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 123;
UPDATE 1

-- 5. Remove rows
DELETE FROM inventory WHERE product_id = 123;
  • WHERE picks the rows. Without it, UPDATE and DELETE touch every row.
  • shop=# is the psql prompt for the database named shop.
  • RETURNING makes a write hand back the row it wrote, which this course uses often.
What does UPDATE inventory SET quantity = 0 do without a WHERE clause?
It sets quantity to 0 on every row of the table. WHERE is what limits a change to the rows you mean.

Transactions: all or nothing

In plain wordsAsha’s purchase is two changes: take one Widget from stock, and create her order. A crash after the first would lose a Widget with no order to show for it. A transaction says “these belong together: finish both, or undo both.”

New words

transactionA group of statements that succeed or fail together.
COMMITMake the changes permanent; they survive a crash from now on.
ROLLBACKUndo everything since BEGIN.

A transaction groups statements so that either all of them take effect or none do, even if the server crashes halfway.

BEGIN;
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 123 AND quantity > 0;

A transaction changed the stock, then the app crashed before COMMIT. What does the stock show afterwards?
The old value. An uncommitted transaction is rolled back, so its changes disappear.

Indexes in one picture

In plain wordsTo find a word in a thick book you use the index at the back, sorted alphabetically, which gives the page. A database index is the same idea, kept up to date automatically.

New words

indexA sorted structure over some columns that points to the matching rows.
sequential scanReading every row of a table to find matches.

An index is a sorted copy of one or more columns with pointers to the rows, so PostgreSQL can jump to matches instead of reading the whole table.

CREATE INDEX orders_user_idx ON orders (user_id);
  • Indexes speed up reads and slow down writes a little, since every write updates them too.
  • Primary keys and unique constraints get an index automatically. Guaranteed
  • Part 3 covers the different kinds of index and when to use each.
Why does adding an index make writes slightly slower?
Each new or changed row must also be updated in every index on the table.

When one server is not enough

In plain wordsOne librarian can answer only so many questions. You can hire assistants who each hold a photocopy of every book (copies), put a receptionist at the door who queues visitors for the few librarians (a pooler), or split the library by subject (partitioning). This lesson only introduces the words; Part 4 explains them properly.

New words

primaryThe one server that accepts writes.
replicaA server holding a copy of the primary’s data, kept up to date, for reads and as a spare.
failoverMaking a replica the new primary when the primary dies.
connection poolerA program (here PgBouncer) that lets many app connections share a few database connections.
partitioningSplitting one big table into smaller pieces by a key such as date.

A growing app adds copies of the database to share reads and survive failures, a pooler to share connections, and only much later splits data up.

Why do replicas help a site with many page views but not one flooded with new orders?
Replicas only answer reads. Every new order is a write, and all writes still go to the single primary.

The path of one query

In plain wordsEvery SQL statement takes the same walk inside PostgreSQL: it is checked, a plan is chosen, and the plan is carried out by reading and writing pages, with every change written to a log first. The figure also shows two helpers you will meet properly in Part 4: a pooler in front and a replica behind.

New words

backend processThe PostgreSQL process that serves one client connection.
parserChecks the SQL and turns it into a structure the server can work with.
plannerChooses the cheapest way to run the query, for example which index to use.
executorCarries out the chosen plan.
WALWrite-ahead log: every change is written here before the data files. The next lesson explains it.

Every statement is parsed, planned and executed by one backend process, which reads pages through a shared cache and logs every change before it counts.

  • One process per connection. The server forks a backend for each client connection. Guaranteed
  • The planner chooses by cost. It uses table statistics to estimate each option, then picks the cheapest.
  • The executor never reads files directly. It asks the buffer manager for pages, which come from memory when possible.
  • Writes go to the primary only. Replicas are read-only copies fed by the WAL. Guaranteed
What happens internally

Besides the backends, a few helper processes run all the time. The checkpointer and background writer push changed pages to the data files. The WAL writer flushes the log. The autovacuum launcher starts cleanup workers.

Which part of PostgreSQL decides between an index scan and a sequential scan, and what does it base the decision on?
The planner (optimizer). It estimates the cost of each plan from table statistics (row counts, value frequencies) and cost settings, and picks the cheapest.

Pages, the buffer cache and the WAL

In plain wordsPostgreSQL does not rewrite data files on every change. It changes data in memory, appends a short record of the change to a log, which is fast, and writes the real files later in bulk. After a crash it replays the log. Like a chef writing each order on a ticket before cooking.

New words

pageThe 8 kB block PostgreSQL reads and writes; rows live inside pages.
shared buffersPostgreSQL’s memory cache of pages.
checkpointThe moment changed pages in memory are written to the data files.
LSNLog sequence number: a position in the WAL. It only goes up.

Tables are files of 8 kB pages. A change is made in memory and written to the WAL first; the data files catch up later.

WhatThe WAL is an append-only log of every change, in order.
WhyAppending to one log is fast. Rewriting scattered 8 kB pages on every commit is not.
HowCOMMIT returns once the WAL is flushed. Changed pages are written at the next checkpoint.
  1. Change the page in memory. The executor edits the page inside shared buffers. The page is now “dirty”.
  2. Append a WAL record. It describes the change well enough to redo it.
  3. COMMIT flushes the WAL. Only now does the client get its answer. Default · check 3
  4. Checkpoint, later. Dirty pages are written to the data files, every 5 minutes or sooner. Default · check 15
  • Page size is 8 kB. Fixed when the server is built. Default
  • Shared buffers is the page cache. 128 MB out of the box, usually raised to about a quarter of RAM. Default · check 15
  • The WAL does two jobs. Crash recovery here, and replication later.
If it breaks: on a crash, memory is lost. At restart the server replays the WAL from the last checkpoint and rebuilds every committed change. Nothing acknowledged is lost.
Durable means “the WAL record is on disk”, not “the table file is updated”.
A server loses power one millisecond after COMMIT returned, before the table file was updated. Why is the row still there after restart?
COMMIT only returns after the WAL records are flushed to disk. At startup PostgreSQL replays the WAL from the last checkpoint and redoes the change into the data pages.

ACID: the contract

In plain wordsA transaction is a promise with four parts, known as ACID. Each letter protects you from a different kind of disaster: a crash halfway, invalid data, two users interfering, and losing a commit after the fact.

New words

ACIDAtomicity, Consistency, Isolation, Durability: the four guarantees of a transaction.
constraintA rule the database enforces, such as CHECK (quantity >= 0).

A transaction is a promise of four things: all or nothing, always valid, as if alone, and never lost.

Atomicity

Stock goes down and the order appears, or neither happens. A crash in between rolls both back.

Consistency

Constraints hold at every commit: foreign keys, unique, CHECK. A violating statement is rejected.

Isolation

Concurrent transactions do not see each other’s half-done work. How strictly is a setting.

Durability

Once COMMIT returns, the change survives a crash. That is the WAL’s job.

  • Constraints are the C. The table says CHECK (quantity >= 0), so stock cannot go negative whatever the app does. Guaranteed
  • Isolation is the adjustable one. The next three lessons are about how much of it you buy.
  • Durability can be relaxed too. synchronous_commit = off trades the last few commits for speed. Default is on.
Which ACID letter does a CHECK (quantity >= 0) constraint serve, and which letter does the WAL serve?
The CHECK constraint serves Consistency: no commit can leave an invalid row. The WAL serves Durability (and it is also how Atomicity survives a crash: uncommitted changes are simply not treated as committed).

MVCC: every update writes a new row version

In plain wordsIf one transaction is reading a row while another is changing it, what should the reader see? PostgreSQL never edits a row in place: it writes a new version and keeps the old one, so the reader sees a consistent picture and nobody waits.

New words

MVCCMulti-version concurrency control: keeping several versions of a row so readers and writers do not block each other.
snapshotThe set of committed data a transaction is allowed to see.
xmin / xmaxHidden columns recording which transaction created and which ended each row version.

PostgreSQL never edits a row in place. An UPDATE writes a new version and marks the old one as ended, so readers and writers do not block each other.

WhatMulti-version concurrency control: several versions of a row exist at once.
WhyA reader keeps seeing the version that was current when it started, with no lock.
HowEach version carries xmin (who created it) and xmax (who ended it).
  • A snapshot decides what you see. A version is visible if its creator committed before your snapshot and nobody you can see has ended it. Guaranteed
  • Readers never block writers. And writers never block readers. Only two writers on the same row wait. Guaranteed
  • DELETE is the same trick. It only sets xmax. The bytes stay.
  • The bill comes later. Ended versions are dead rows that vacuum must clean up.

Isolation levels

In plain wordsWhen two transactions run at the same time, how much of each other’s just-finished work should they see? Seeing too much causes bugs; seeing too little forces waiting or retries. The isolation level picks the balance.

New words

isolation levelHow strictly concurrent transactions are kept apart.
dirty readSeeing another transaction’s change before it commits. PostgreSQL never allows it.
phantomA new row appearing in a repeated query because someone inserted it in between.

The isolation level decides when a transaction takes its snapshot: at every statement, or once at the start.

  • There are no dirty reads, ever. PostgreSQL accepts “read uncommitted” but runs it as read committed. Guaranteed · check 4

Serializable and the retry loop

In plain wordsThe strictest level, Serializable, promises that running transactions together gives the same result as running them one at a time. PostgreSQL keeps that promise by cancelling one of two conflicting transactions, so your code must be ready to try again.

New words

serializableConcurrent transactions behave as if they ran one after another.
serialization failureError 40001: PostgreSQL cancelled your transaction to keep that promise. Retry it.

Serializable guarantees the result matches some one-at-a-time order of the transactions. It does that by aborting one of them, so your code must retry.

  • No blocking, just detection. PostgreSQL tracks what each serializable transaction read and aborts one when the pattern is dangerous. Guaranteed
  • Repeatable read lets this through. In the same test at that level both commits succeeded. Guaranteed · check 6
  • Retry the whole transaction. Not the last statement. Start again from BEGIN with fresh reads.
  • All parties must use it. The guarantee only covers transactions that run at serializable.
# psycopg2. Written for this guide, not run.
def place_order(conn, user_id, product_id, total, retries=3):
    for attempt in range(retries):
        try:
            with conn:                                   # commit, or roll back on error
                with conn.cursor() as cur:
                    cur.execute("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
                    cur.execute("UPDATE inventory SET quantity = quantity - 1 "
                                "WHERE product_id = %s AND quantity > 0", (product_id,))
                    if cur.rowcount == 0:
                        raise OutOfStock()
                    cur.execute("INSERT INTO orders (user_id, product_id, total) "
                                "VALUES (%s, %s, %s) RETURNING id",
                                (user_id, product_id, total))
                    return cur.fetchone()[0]
        except psycopg2.errors.SerializationFailure:      # SQLSTATE 40001
            time.sleep(random.uniform(0.01, 0.1) * 2 ** attempt)
    raise TooManyRetries()

If it breaks: under heavy contention the same transaction can fail several times. Back off with jitter, cap the retries, and return a clear error. Never retry a transaction that already called an external service without an idempotency key.
Two transactions each count the orders for a product and then insert one. Which isolation level catches this, and how does the loser find out?
Serializable. The second COMMIT fails with SQLSTATE 40001 (“could not serialize access due to read/write dependencies among transactions”). The application retries the whole transaction. At repeatable read both commit.

Row locks: SELECT … FOR UPDATE

In plain wordsA normal read never waits and never blocks. But when you read a value in order to change it, such as checking stock before selling, you want to lock the row while you read so nobody changes it in between. That is what FOR UPDATE does.

New words

row lockA lock on one row that makes other writers wait.
race conditionA bug where the result depends on which of two simultaneous actions happens first.

When you must read a row, decide in the app, then write it back, lock the row as you read it so nobody changes it in between.

LockUse it whenBlocks
FOR UPDATEYou will update or delete the rowEvery other row lock, and writers
FOR NO KEY UPDATEYou will update non-key columnsWriters, but not foreign-key checks
FOR SHAREYou need the row to stay as it isWriters. Other sharers are fine
FOR KEY SHARETaken by foreign-key checksOnly deletes and key changes
  • Plain SELECT is never blocked. Row locks stop other lockers and writers, not readers. Guaranteed · check 7
  • NOWAIT fails fast. It raises an error instead of waiting.
  • SKIP LOCKED skips busy rows. That is how several workers share a job queue table.
  • The lock ends at COMMIT or ROLLBACK. Keep the transaction short.
Simplest of all. If the database can do the arithmetic, skip the lock: UPDATE … SET quantity = quantity - 1 WHERE quantity > 0 is atomic by itself.
If it breaks: two transactions that lock the same rows in opposite order deadlock. PostgreSQL detects it after about a second and aborts one. Default Lock rows in a fixed order, for example by id.
Does SELECT … FOR UPDATE on a row block another session’s plain SELECT of that row?
No. Plain reads use their snapshot and take no row lock. It blocks other FOR UPDATE / FOR SHARE requests and any UPDATE or DELETE of that row until the locker commits or rolls back.

B-tree: the default index

In plain wordsA B-tree is how PostgreSQL keeps an index sorted while rows keep arriving. Picture a library: a sign at the door says which floor holds which letters, each floor has signs for its shelves, and the shelves hold the books in order. Three signs find any book.

New words

B-treeA shallow, sorted tree; PostgreSQL’s default index type.
leafA bottom node of the tree, holding the actual entries and row pointers.
index scanUsing an index to find rows instead of reading the whole table.

Without an index PostgreSQL reads every page of the table. A B-tree keeps the keys sorted in a shallow tree, so a lookup reads a handful of pages.

WhatA balanced tree of sorted keys. Each leaf entry points at a row’s ctid.
WhyOne structure answers equality, ranges, sorting and prefix matches.
CostEvery insert and most updates must also update each index. Indexes take space.
  • Equality and ranges. =, <, >, BETWEEN, and ORDER BY … LIMIT with no sort step. Guaranteed
  • Prefix LIKE, with a catch. LIKE 'asha%' uses a plain B-tree only under the C collation. Otherwise build the index with text_pattern_ops. Simplified · check 10
  • Small tables skip it. With one row in orders the planner chose a sequential scan even though an index existed. Reading one page is cheaper.
  • Hash indexes exist. They only answer =, and are rarely worth giving up ranges and sorting for.
What happens internally

A binary search over 1,000,000 keys needs about 20 comparisons (log₂ of 1,000,000 is 19.9). A B-tree page holds hundreds of keys, so most of those comparisons happen inside one page. That is why the tree is only three levels deep.

A B-tree index on a table of one million rows: roughly how many pages does one lookup read, and why so few?
About four: root, one internal page, one leaf, then the table page. Each index page holds hundreds of keys, so the tree is very shallow. Measured here: 18 buffers for 12 matching rows, against 9,346 for the sequential scan.

BRIN: a tiny index for data stored in order

In plain wordsWhen a table is naturally stored in time order, like log rows, you do not need a full index. Remembering just the smallest and largest value in each block of pages lets PostgreSQL skip whole blocks, using almost no space.

New words

BRINBlock range index: stores a min and max per range of pages.
correlationHow closely the physical order of rows matches a column’s order.

When rows sit on disk in roughly the same order as a column’s values, it is enough to remember the minimum and maximum of each block of pages.

  • Very small. 24 kB here, against 21 MB for a B-tree on the same column: about 900 times smaller. Guaranteed · check 11
  • Imprecise by design. It returns whole ranges of pages. Every row in them is rechecked.
  • Only as good as the ordering. Order 9001 was inserted first but dated March 2026. Its range now spans two years, so it can never be skipped.
  • Good for append-only time data. Logs, events, measurements, queried by time window.
Rule of thumb. BRIN when the table is huge, append-only and queried by range. B-tree when you need single rows fast, or the data arrives out of order. Simplified
A BRIN scan for one day rechecked and threw away 26,174 rows that a B-tree scan never touched. Why?
BRIN only knows the minimum and maximum per block range (128 pages by default). It returns every page of each range that might match, and each row on those pages must be rechecked against the condition. A B-tree points at exactly the matching rows.

Partitioning: one table, many smaller ones

In plain wordsVery large tables get slow to maintain. Partitioning splits one big table into smaller child tables, for example one per quarter, while the application still sees a single table.

A partitioned table looks like one table to the application, but each row is stored in a smaller child table chosen by a key.

WhatThe parent holds no rows. Children hold them, split by range, list or hash.
WhyQueries skip children that cannot match. Maintenance and deletion work per child.
HowThe planner compares the WHERE clause with each child’s bounds: partition pruning.

Partition upkeep and limits

In plain wordsPartitions make deleting old data instant (drop a whole child table) and keep indexes small. In return they bring a few rules about keys and some regular housekeeping, which this lesson lists.

New words

DETACH / DROP partitionRemoving a whole child table at once instead of deleting rows one by one.

Partitions make old data cheap to remove, in exchange for a few rules about keys and some housekeeping.

  • Create partitions ahead of time. A row with no matching partition is rejected. A scheduled job, or a DEFAULT partition, avoids that.
  • Unique keys must include the partition key. Each child enforces uniqueness on its own. Guaranteed
  • Changing the key moves the row. An UPDATE of created_at across a boundary becomes a delete plus an insert, automatically. Older guides say it is not allowed. Guaranteed · check 13
  • Many partitions slow planning. Each one is another table the planner must consider.
If it breaks: the usual incident is “no partition found” at midnight on the first of the quarter, because nobody created the next one.
Why must the primary key of a table partitioned by created_at include created_at?
Uniqueness is enforced by an index in each partition separately. There is no index spanning all partitions, so the key must contain the partition column to guarantee that two equal keys always land in the same partition.

Optimistic locking and advisory locks

In plain wordsTwo ways to coordinate without holding a row lock. Optimistic: change the row only if its version has not changed since you read it. Advisory: lock an idea, such as “the nightly report”, rather than a row.

New words

optimistic lockingDetecting a conflict at write time using a version number, then retrying.
advisory lockAn application-defined lock on a number, managed by PostgreSQL.

Two ways to coordinate without holding a row lock: detect a conflict after the fact with a version number, or lock an idea instead of a row.

Optimistic locking

  • Detect, do not prevent. No lock is held while the user thinks. Best when conflicts are rare.
  • The check and the write are one statement. That is what makes it safe. Guaranteed

Advisory locks

  • For things that are not rows. “Only one payout job per user”, “only one migration at a time”.
  • Prefer the transaction-level form. pg_advisory_xact_lock releases itself at commit, and is the only form that is safe behind a transaction-mode pooler.
If it breaks: a session-level advisory lock is held until unlock or disconnect. A worker that forgets to unlock, on a pooled connection that never closes, blocks that key forever.
With optimistic locking, an UPDATE … WHERE id = 123 AND version = 5 reports “UPDATE 0”. What does that mean, and what should the application do?
Someone else updated the row first, so its version is no longer 5. Nothing was written. Reload the row, reapply the change (or show the user the conflict) and retry with the new version.

Idempotent writes: UPSERT and RETURNING

In plain wordsNetworks fail and clients retry. A write is safe to retry only if running it twice gives the same result as once. INSERT … ON CONFLICT (upsert) and RETURNING are the tools that make that easy.

New words

idempotentDoing it twice has the same effect as doing it once.
upsertInsert a row, or update it if it already exists.

Networks retry. A write is safe to retry when running it twice leaves the same result as running it once.

  • ON CONFLICT DO UPDATE. Insert, or update the existing row, in one atomic statement. EXCLUDED is the row you tried to insert.
  • ON CONFLICT DO NOTHING. Insert unless it is already there. The basis of idempotency keys and deduplication.
  • It needs a unique index. The conflict is detected by a unique or exclusion constraint. Guaranteed
  • RETURNING hands back what was written. Generated ids, defaults, new values, with no second query and no race.
What happens internally

Since PostgreSQL 15 there is also the standard MERGE statement. For a plain “insert or update one row” under concurrency, ON CONFLICT remains the safer tool, because it is built on the unique index.

How does an idempotency key with INSERT … ON CONFLICT DO NOTHING make a payment retry safe?
The key is the primary key (or has a unique index). The first attempt inserts the row. Any retry with the same key conflicts and inserts nothing, so the payment exists exactly once; the app checks the row count or reads the existing row.

No double-booking: exclusion constraints

In plain wordsTwo people trying to book the same room at the same time is a classic race. A unique constraint can stop exact duplicates; an exclusion constraint stops overlaps, and the database enforces it even when requests race.

New words

exclusion constraintA rule that no two rows may overlap according to an operator, such as overlapping time ranges.
range typeA column holding a span of values, such as a booking from 10:00 to 11:00.

A unique constraint says “no two rows are equal”. An exclusion constraint says “no two rows overlap”, and the database enforces it even when two requests race.

CREATE EXTENSION btree_gist;             -- lets "=" on a bigint join the GiST index
CREATE TABLE reservations (
  id          bigserial PRIMARY KEY,
  resource_id bigint    NOT NULL,
  time_range  tstzrange NOT NULL,
  user_id     bigint    NOT NULL,
  EXCLUDE USING gist (resource_id WITH =, time_range WITH &&)
);
  • Read it as a sentence. No two rows may have an equal resource and overlapping time ranges.
  • It is backed by a GiST index. The check is an index lookup, not a table scan.
  • It cannot be bypassed. No application bug or race can insert an overlap. Guaranteed
In an interview. For a booking system, say “the constraint lives in the database” before describing any application-level locking. It is the strongest answer and the shortest.
With range bookings, why does [10:00, 11:00) followed by [11:00, 12:00) not count as an overlap?
The ranges are half-open: the start is included, the end is not. The first booking ends just before 11:00 and the second starts at 11:00, so they share no instant.

Vacuum: cleaning up dead row versions

In plain wordsBecause updates and deletes leave old row versions behind (MVCC), someone has to clean them up. That is vacuum. If it falls behind, tables fill with dead rows and get slower and bigger.

New words

dead tupleAn old row version no transaction can see any more.
vacuumThe process that marks dead row versions’ space as reusable.
bloatWasted space from dead rows that vacuum has not cleaned.

MVCC leaves the old version of every updated or deleted row behind. Vacuum marks that space reusable; if it falls behind, the table bloats.

  • Autovacuum does it for you. It vacuums a table once dead rows exceed 50 plus 20% of the table: 200,050 dead rows for our million orders. Default · check 15
  • Space is reused, not returned. The file stays the same size and fills up again from inside.
  • VACUUM FULL does shrink it. By rewriting the whole table under an exclusive lock. Avoid on a live system.
  • On busy tables, vacuum sooner. Lower autovacuum_vacuum_scale_factor per table so cleanup starts earlier.
If it breaks: one forgotten open transaction pins every row version newer than its snapshot. Vacuum runs but reports them “dead but not yet removable”, and the table keeps growing. Try it in the MVCC demo.
What happens internally

Vacuum has a second job. Transaction IDs are 32-bit and wrap around, so old rows are “frozen” to mark them visible to everyone. If vacuum is blocked for long enough, PostgreSQL stops accepting writes to protect the data.

VACUUM finished and removed 221,476 dead rows, yet the table file did not get smaller. Why, and is that a problem?
Plain VACUUM marks the space as free for reuse inside the same table; it only gives space back to the operating system when the empty pages are at the very end. It is not a problem: later inserts and updates fill the free space. Only VACUUM FULL (or pg_repack) rewrites the table smaller.

Common misconceptions

In plain wordsThese are beliefs that sound right and are wrong in ways that matter. Each card gives the belief and the correction.

Eight beliefs that sound right and cost marks in interviews.

Read uncommitted lets you see uncommitted data in PostgreSQL.

It runs as read committed. There are no dirty reads at any level.

An UPDATE changes the row in place.

It writes a new version and ends the old one. The old one stays until vacuum.

COMMIT means the table file was written.

It means the WAL was flushed. The table file follows at a checkpoint.

VACUUM makes the table smaller.

It makes dead space reusable. Only VACUUM FULL shrinks the file, and it locks the table.

More indexes make the database faster.

Faster for the reads that use them, slower for every write. Here seven indexes were twice the size of the table.

A replica gives me the same data as the primary.

It gives the primary’s data from a moment ago. With async replication, a failover can lose the last commits.

Need more connections? Raise max_connections.

Each connection is a process. Put PgBouncer in front and keep the number of backends small.

You cannot update the partition key.

You can. PostgreSQL moves the row to the right partition.

Quick revision and glossary

In plain wordsTest yourself with every quick check from the course, then look up any word you have forgotten in the glossary.

Test yourself, then look up any term.

At repeatable read, T1 reads a row, T2 updates it and commits, then T1 tries to update the same row. What happens?
T1’s UPDATE fails with SQLSTATE 40001, “could not serialize access due to concurrent update”. T1 must roll back and retry. At read committed the UPDATE would simply apply on top of T2’s value.
What do xmin and xmax on a row version record?
xmin is the ID of the transaction that created the version. xmax is the ID of the transaction that ended it (by UPDATE or DELETE), or that locked it; 0 means nobody has.
When would you choose a BRIN index over a B-tree?
On a very large, append-only table whose physical order follows the column (typically a timestamp), queried by range. BRIN is hundreds of times smaller but returns whole block ranges that must be rechecked.
In streaming replication, which side opens the connection: the primary or the replica?
The replica. Its walreceiver connects to the primary and asks for WAL from the position it has reached; the primary’s walsender answers.
Name three ways to stop two shoppers both buying the last unit of stock.
One atomic statement (UPDATE … SET quantity = quantity - 1 WHERE quantity > 0, backed by a CHECK constraint); SELECT … FOR UPDATE before deciding; optimistic locking with a version column; or serializable isolation with a retry loop.
What does the planner need in order to choose a good plan, and what do you run when it is choosing badly after a bulk load?
Up-to-date statistics about each table (row count, distinct values, most common values). Run ANALYZE on the table; autovacuum normally does this in the background.

Who does FOR UPDATE block?		A: BEGIN; SELECT * FROM inventory WHERE product_id = 123 FOR UPDATE; B: a plain SELECT, then the same with FOR UPDATE NOWAIT.The plain SELECT returns at once. NOWAIT fails with “could not obtain lock on row”.
8Index changes the plan
Does the planner use my index?		Load at least 100,000 orders. EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42; before and after CREATE INDEX ON orders(user_id, created_at);Seq Scan becomes an index or bitmap scan, and Buffers drops sharply.
9Leading column
What does my version do without it?		EXPLAIN SELECT * FROM orders WHERE created_at > '2026-03-31'; with only the composite index present. Also SELECT version();On 17 and earlier: Seq Scan. On 18 or later you may see the index used via skip scan. Note which.
10Prefix LIKE

11BRIN size

12Pruning

13Moving a row

14Replication mode and lag
