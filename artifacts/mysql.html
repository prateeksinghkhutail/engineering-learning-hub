01

Why a database at all?

In plain wordsImagine an online shop that writes every order into a spreadsheet file. Two customers buy at the same moment and one order overwrites the other. The power cuts halfway through saving and the file is corrupted. Finding one order among ten million means reading the whole file. A database solves exactly these three problems.

A database is a program whose whole job is to remember data safely, let many people change it at the same time, and find any piece of it quickly.

Client and server

  • MySQL is a server program. It runs all the time and waits for connections, on port 3306 by default. Default
  • Your code is a client. It connects, sends a request, and gets an answer back.
  • MySQL is free and open source and one of the most used databases in the world, from tiny websites to Facebook-sized systems.
Name three problems a database solves that a plain file on disk does not.
Many users changing data at the same time without losing changes; surviving a crash without half-written data; and finding one record quickly among millions.

02

Tables, rows and keys

In plain wordsThink of three spreadsheet tabs: one listing customers, one listing products, one listing orders. Each order row does not copy Asha’s name; it just says “customer number 123”. That number is the link. Linking tables by numbers is what “relational database” means.

New words

tableA named grid of data, like a spreadsheet tab.
rowOne record in a table: one user, one order.
columnOne fact every row has: name, price, quantity.
primary keyA column whose value is unique per row, used to find that row. Usually id.
foreign keyA column that holds another table’s primary key, linking the two rows.

MySQL stores data in tables, like spreadsheet tabs: each row is one thing, each column one fact about it, and keys link rows in different tables together.

  • Every table should have a primary key. It is how MySQL finds and stores each row.
  • Foreign keys keep links valid. MySQL refuses an order for user 999 if no user 999 exists. Guaranteed with InnoDB
  • Columns have types: BIGINT for whole numbers, VARCHAR(100) for text up to 100 characters, DECIMAL(10,2) for money, DATETIME for times.
Why does the orders table store user_id 123 instead of Asha’s name and email?
So each fact is stored once. If Asha changes her email, only her users row changes; every order still points to her through the key 123.

03

Talking to MySQL: five SQL statements

In plain wordsSQL reads almost like English: “select the name from users where the id is 123”. You describe what you want, and MySQL works out how to get it. That “how” is what most of this course is about.

SQL is the language you use to ask MySQL to create tables, add rows, read them, change them and delete them.

-- 1. Create a table
CREATE TABLE inventory (product_id BIGINT PRIMARY KEY, name VARCHAR(100), quantity INT);

-- 2. Add a row
INSERT INTO inventory VALUES (501, 'Keyboard', 10);

-- 3. Read rows
SELECT name, quantity FROM inventory WHERE product_id = 501;
+----------+----------+
| name     | quantity |
+----------+----------+
| Keyboard |       10 |
+----------+----------+

-- 4. Change rows
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 501;
Query OK, 1 row affected

-- 5. Remove rows
DELETE FROM inventory WHERE product_id = 501;
  • WHERE picks the rows. Without it, UPDATE and DELETE touch every row in the table.
  • Reads use SELECT; writes are INSERT, UPDATE and DELETE. Later lessons treat reads and writes very differently.
  • You type SQL in the mysql command-line client, or your app sends it through a library (a driver).
What happens if you run UPDATE inventory SET quantity = 0 with no WHERE clause?
Every row in the table gets quantity 0. WHERE is what limits a change to the rows you mean.

Transactions: all or nothing

In plain wordsAsha’s purchase is two changes: take one keyboard from stock, and create her order. If the server crashed after the first, the shop would lose a keyboard with no order to show for it. A transaction says: “treat these as one. Finish both, or undo both.”

New words

transactionA group of statements that succeed or fail together.
COMMIT“Make it permanent.” After this, the change survives a crash.
ROLLBACK“Undo everything since START TRANSACTION.”

A transaction groups several statements so that either all of them happen or none of them do, even if the server crashes in the middle.

START TRANSACTION;
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 501;
INSERT INTO orders (id, user_id, product_id, status, total, created_at)
VALUES (7001, 123, 501, 'paid', 49.99, '2026-10-04 10:00:00');
COMMIT;      -- or ROLLBACK; to cancel both

ACID, in plain words

Atomic

All or nothing, as above.

Consistent

Rules always hold: stock never negative, orders always point to real users.

Isolated

Others never see your half-finished work.

Durable

After COMMIT, a power cut cannot undo it.

A transaction updated the stock and then the app crashed before COMMIT. What does the stock show after MySQL restarts?
The old value. An uncommitted transaction is rolled back, so the stock change disappears along with everything else in it.

Indexes in one picture

In plain wordsTo find “replication” in a 600-page book you do not read every page; you look in the index at the back, which is sorted alphabetically and gives the page number. A database index is the same idea, kept up to date automatically.

New words

indexA sorted copy of one or more columns that points to the rows.
full table scanReading every row to find matches. Fine for 100 rows, terrible for 100 million.

An index is a sorted list of one column’s values with pointers to the rows, so MySQL can jump to the right rows instead of reading the whole table.

CREATE INDEX idx_user ON orders (user_id);
  • Indexes speed up reads and slow down writes a little, because each write must update the index too.
  • The primary key always has an index. Guaranteed
  • Part 3 explains how indexes really work, and which ones to create.
Why does adding an index make INSERTs slightly slower?
Every new row must also be added, in sorted position, to each index on the table. More indexes means more work per write.

When one server is not enough

In plain wordsOne librarian can only answer so many questions. You can hire assistants who each hold a photocopy of every book and answer questions (copies), or split the library into wings by subject, each with its own librarian (splitting). Copies are easy; splitting is hard. This lesson only introduces the words; Parts 5 and 6 explain them properly.

New words

primaryThe one server that accepts writes.
replicaA server holding a copy of the primary’s data, kept up to date, used for reads and as a spare.
replicationCopying every change from the primary to the replicas.
proxyA program between the app and the databases that sends each query to the right server.
shardOne slice of the data when it is split across several primaries.

A growing app first adds copies of the database to share the reading and survive failures, and only much later splits the data across several databases.

  • Copies scale reads, not writes: every write still goes to the one primary.
  • Splitting scales writes but makes some queries harder, because the data is no longer in one place.
Adding replicas helps a site with lots of page views. Why does it not help a site that is overwhelmed by new orders?
Replicas only take read queries. Every new order is a write, and all writes still go to the single primary, so it remains the bottleneck.

When to choose MySQL

In plain wordsEvery database is good at some jobs and poor at others. MySQL shines when your data fits naturally into linked tables, most traffic is reading, and you want something dependable that many engineers already know how to run.

New words

read-heavyFar more reads (SELECT) than writes (INSERT, UPDATE, DELETE).

MySQL trades some advanced SQL features for operational simplicity and fast reads, so pick it when the workload is relational, read-heavy and must be run reliably by ordinary teams.

Read-heavy web apps

Profiles are written once and read thousands of times. Add replicas to scale reads; keep one primary for writes.

Operational simplicity

Decades in production. Failure modes, backups and tooling are well understood at 3 AM.

Related data

Users have orders, orders have items. Joins beat denormalising everything into documents.

ACID transactions

InnoDB either reserves stock and creates the order, or does neither. Built into the engine.

Existing ecosystem

Your ORM, dashboards and team already speak MySQL. Switching has hidden costs.

The path of one query

In plain wordsThink of a restaurant. A waiter takes your order (the connection), checks it is something on the menu (the parser), the head chef decides the quickest way to cook it (the optimizer), the cooks follow that plan (the executor), and they fetch ingredients from the fridge and the store room (the storage engine). Every SQL statement takes this same walk.

New words

parserChecks the SQL is valid and turns the text into a structure MySQL can work with.
optimizerChooses the cheapest way to run the query, for example which index to use.
executorCarries out the chosen plan step by step.
storage engineThe part that actually stores and fetches rows on disk and in memory. In this course: InnoDB.

Inside one MySQL server every statement passes through the same stages: a connection, a parser that checks the SQL, an optimizer that picks a plan, an executor that runs it, and a storage engine that touches the data.

  1. Connect. The app opens a connection; MySQL gives it a thread that serves it.
  2. Parse. The SQL text is checked for mistakes and turned into a tree.
  3. Plan. The optimizer estimates the cost of each way to run it, using statistics about the tables, and picks the cheapest.
  4. Execute. The executor follows the plan and asks InnoDB for each row it needs to read or change.
  5. Store. InnoDB serves rows from memory when it can, and records every change in its log before saying “done”.
  • Two layers. The server layer (connections, parser, optimizer, executor) sits on top of a swappable storage engine. Guaranteed
  • The optimizer is why SQL is declarative: you say what you want, it decides how. When a query is slow, the plan it chose is the first thing to look at (Part 7).
  • Later, more servers join. Your notes’ first diagram also shows a proxy and replicas; Part 5 adds those once copies have been explained. Added
Which component decides whether a query uses an index, and which one actually reads the rows?
The query optimizer decides (it builds the plan). The execution engine runs the plan and asks the storage engine, InnoDB, for the rows.

In plain wordsMySQL is built in two halves: a front half that understands SQL, and a back half, the storage engine, that actually keeps the data. You can choose the back half per table. Almost everyone today uses one engine, InnoDB, and this lesson shows why.

MyISAMMySQL’s older engine, without transactions.

Why can a MyISAM table be corrupted by a crash when an InnoDB table is not?

InnoDB architecture

In plain wordsWriting every change straight to its final place on disk would be slow. InnoDB changes data in memory, writes a short note of the change to a log first, which is fast, and copies the real data to disk later in bulk. After a power cut it replays its notes. The next four lessons zoom in on each piece.

New words

pageThe 16 KB block InnoDB reads and writes; rows and index entries live inside pages.
buffer poolInnoDB’s area of memory holding copies of pages.
redo logThe log of changes used to recover after a crash.
undo logWhere the previous versions of changed rows are kept.
dirty pageA page changed in memory but not yet written to disk.
checkpointThe point up to which dirty pages have been written to disk.

InnoDB changes pages in memory, writes a small redo record to survive a crash, keeps old versions in an undo log, and writes the real data files later.

WhatThe storage engine under almost every MySQL table.
WhyRandom writes to data files are slow; one sequential log write is fast and enough to be durable.
HowPages live in the buffer pool. Changes go to the redo log at commit. Dirty pages reach disk at checkpoints.
  • Pages are 16 KB. Everything (rows, index entries, undo records) is stored in pages. Default
  • Durable means logged. A committed change may exist only in memory and the redo log for a while. Guaranteed
  • Undo serves two jobs. Rolling back, and giving readers old versions (MVCC).
If it breaks: on a crash, the buffer pool is gone. At restart InnoDB replays the redo log from the last checkpoint, then uses undo to roll back anything that never committed.
The doublewrite buffer

A 16 KB page written over a 4 KB disk sector can be torn by a power cut. InnoDB first writes each page to a doublewrite area (#ib_16384_0.dblwr files since 8.0.20), then to its real place, so a torn page can be repaired from the copy. Added

Why can InnoDB report a commit as done before the changed data pages are written to the data files?
Because the change is already in the redo log on disk. After a crash InnoDB replays the redo log to rebuild the pages.

The buffer pool

In plain wordsReading from memory is roughly a thousand times faster than reading from disk. The buffer pool is the memory where InnoDB keeps copies of disk pages. If the page you need is already there, you never wait for the disk.

New words

hit / missA hit finds the page in memory; a miss has to read it from disk.
working setThe data your app actually touches regularly.
LRULeast recently used: when memory is full, throw out what was used longest ago.

The buffer pool is InnoDB’s page cache in RAM, and a read that finds its page there never touches the disk.

  • Size it to the working set. 70 to 80% of RAM on a dedicated server, about 50% on a shared one. Simplified
  • The stock size is tiny: 128 MB until you change it. Default · check 3
  • Aim for a hit ratio above 99%. Hit ratio = 1 − (disk reads ÷ read requests).
  • The adaptive hash index is off in 8.4. It used to be on by default. Default · check 16 Added
# my.cnf
innodb_buffer_pool_size = 12G      # 70-80% of RAM on a dedicated 16 GB server
innodb_buffer_pool_instances = 8   # split the pool to reduce contention
What happens internally: the LRU with a midpoint

Pages are kept on a list ordered by use. A page read for the first time is inserted 3/8 of the way from the tail (the “old” sublist, 37% of the pool). Only if it is touched again after a second does it move to the young end. A one-off table scan therefore cannot flush the whole hot set. Default · check 3 Added

A server reports 1,250,000 buffer pool read requests and 3,100 disk reads. What is the hit ratio, and is it healthy?
1 − 3,100 ÷ 1,250,000 = 0.9975, so 99.75%. Above the 99% guideline: healthy.

The redo log (write-ahead log)

In plain wordsBefore changing anything for real, InnoDB writes a short note of the change at the end of a log file. Adding to the end of a file is very fast. If the server crashes, it rereads the notes and redoes the changes. It is like a chef writing each order on a ticket before cooking: if the kitchen is interrupted, the tickets say what was promised.

New words

write-ahead logA log written before the real data changes, so changes can be replayed after a crash.
fsyncForcing data out of memory buffers onto the physical disk.
LSNLog sequence number: a record’s position in the log. It only goes up.

At commit InnoDB appends a compact description of the change to the redo log and flushes it, which is one sequential write instead of many random ones.

The undo log and MVCC

In plain wordsIf one transaction is reading the stock while another is changing it, what should the reader see? InnoDB keeps the old version around for a while, so the reader sees a consistent picture from when it started, and nobody has to wait for anybody.

New words

MVCCMulti-version concurrency control: keeping several versions of a row so readers and writers do not block each other.
snapshotThe set of committed data a transaction is allowed to see, also called a read view.

When a row changes, InnoDB keeps the old version in the undo log, so a reader sees the version that fits its snapshot and nobody waits.

WhatMulti-version concurrency control: a row can have several versions at once.
WhyLocking every row a reader touches would kill concurrency; showing uncommitted data would be wrong.
HowEach row carries the ID of the transaction that last changed it and a pointer to its previous version in undo.
  • Readers do not block writers, and writers do not block readers. Guaranteed
  • Each transaction sees a consistent snapshot (a read view) of committed data.
  • Writers see their own uncommitted changes.
  • Old versions stay in undo until no open read view can need them, then purge threads remove them.
If it breaks: one transaction left open for hours pins every old version since it started. The undo log grows (watch “History list length”) and reads slow down as they walk longer version chains.
What happens internally: the hidden columns

Every clustered index row has hidden fields: DB_TRX_ID (6 bytes, last writer) and DB_ROLL_PTR (7 bytes, pointer to the undo record). Nobody. B writes a new version and keeps the old one in the undo log; A reads the version that matches its snapshot.

The clustered index

In plain wordsIn InnoDB the table itself is stored sorted by its primary key, like a phone book sorted by surname where the entries are the data. Looking up by primary key is therefore the fastest read there is, and your choice of primary key affects every other part of the table.

The B+tree

In plain wordsA B+tree is how MySQL keeps an index sorted while rows keep arriving. Picture a library: a sign at the entrance says which floor holds which letters, each floor has signs for its shelves, and the shelves hold the books in order. You read three signs to find any book, however big the library.

New words

nodeOne box in the tree: a page holding sorted keys.
root / leafThe root is the top node; leaves are the bottom nodes that hold the actual entries.
O(log N)The work grows very slowly with the data: doubling the data adds about one extra step.

Every standard MySQL index is a B+tree: a few levels of sorted signposts above a chain of linked leaves that hold the keys.

  • All values live in the leaves, and the leaves are linked in key order. Guaranteed
  • Lookups cost O(log N). Each 16 KB node holds hundreds of keys, so even a billion rows is three or four levels deep. Simplified
  • Good at equality and ranges: =, <, BETWEEN, LIKE 'abc%', ORDER BY on the indexed columns.
  • Useless for leading wildcards: LIKE '%abc' has no sorted starting point.
Indexes are not free. Every INSERT, UPDATE and DELETE also changes every affected index. Index for the queries you run, not the ones you might.
Why can a B+tree answer “orders with id between 7001 and 7005” without visiting the root more than once?
The leaves are linked in key order. After one descent to 7001, the scan follows the leaf links until it passes 7005.

Primary vs secondary indexes

In plain wordsThe primary key index holds the rows themselves. Any other index, for example on email, holds only the email and the primary key. So finding a row by email takes two steps: find the key in the email index, then fetch the row by that key.

New words

secondary indexAny index other than the primary key.

A secondary index stores the primary key, not a row address, so reading a whole row through it is two lookups.

  1. Search the secondary index. Find asha@example.com, read its primary key: 123.
  2. Search the clustered index. Walk down to id 123 and read the full row.
  • Why a key, not an address? Rows move when pages split. A primary key never goes stale, so secondary indexes need no rewrite. Added
  • The cost: a second tree walk per row. Covering indexes (two lessons on) remove it.

The row’s primary key value. The full row is then fetched from the clustered index.

InnoDB lock types

In plain wordsSnapshots take care of readers, but two writers changing the same row must take turns. InnoDB puts locks on index entries, and sometimes on the gaps between them, so that a range it is working on cannot change underneath it.

New words

lockA marker saying “this is mine for now”; others who want it must wait.
gapThe space between two neighbouring index entries, where a new row could be inserted.

InnoDB locks index records, and also the gaps between them, so a range it has read cannot gain new rows behind its back.

-- Record lock on id = 10
SELECT * FROM users WHERE id = 10 FOR UPDATE;

-- Range: locks the records and the gaps, so nobody can insert id = 15
SELECT * FROM users WHERE id BETWEEN 10 AND 30 FOR UPDATE;

Deadlocks

In plain wordsTwo people each hold one key and each wait for the other’s key: they would wait forever. MySQL notices this circle of waiting and cancels one of the two transactions so the other can finish.

New words

deadlockTwo or more transactions each waiting for a lock another holds.
victimThe transaction MySQL rolls back to break the deadlock.

A deadlock is two transactions each holding a lock the other needs; InnoDB spots the cycle at once and rolls one of them back.

  • Detected automatically, as soon as the cycle forms. Default
  • The victim is the cheaper transaction (fewer rows changed or locked). Simplified
  • Your code must retry. The error says so: “try restarting transaction”.

How to have fewer of them

  1. Same order everywhere. Lock rows in a fixed order, for example by product_id.
  2. Short transactions. Do no slow work between BEGIN and COMMIT.
  3. Lowest safe isolation. READ COMMITTED takes fewer gap locks.
  4. Good indexes. Fewer rows scanned means fewer rows locked.
Two transactions keep deadlocking on the same two rows. What is the simplest code change that removes the cycle?
Make both lock the rows in the same order (for example, sorted by primary key). Then the second transaction waits instead of forming a cycle.

Optimistic vs pessimistic locking

In plain wordsTwo styles of avoiding conflicts. Pessimistic: lock first, just in case, like booking a meeting room. Optimistic: do not lock, but check at the end that nobody changed it meanwhile, like a shared document that warns you if someone edited it since you opened it.

New words

version columnA number stored in the row and increased on every change, used to detect that someone else changed it.

Pessimistic locking takes the lock before reading; optimistic locking reads freely and checks a version number at write time.

-- Optimistic: read with the version
SELECT quantity, version FROM inventory WHERE product_id = 501;   -- quantity 10, version 5

-- Write only if nobody changed it since
UPDATE inventory
   SET quantity = quantity - 1, version = version + 1
 WHERE product_id = 501 AND version = 5;
-- 1 row affected: you won. 0 rows: someone else did; re-read and retry.

PessimisticHigh contention: flash sales, seat bookingBlocks other transactions
OptimisticLow contention: profile editsRetry work when a conflict happens
Rule of thumb. Many users fighting for the same row: lock early. Conflicts rare: skip the lock and handle the odd retry.

How replication works

In plain wordsThe primary writes down every committed change in a log called the binary log. Each replica downloads that log and replays it, so its copy follows the primary a fraction of a second behind.

New words

binary log (binlog)The primary’s log of committed changes, which replicas copy.
relay logThe replica’s local copy of the binlog events it has downloaded.
GTIDGlobal transaction ID: a unique name for every transaction, so a replica can say exactly which ones it has.
threadA unit of work inside a program that runs alongside others.

The primary records every committed change in its binary log, and each replica pulls that log, stores it in a relay log and replays it on its own copy.

  1. Source writes the change and appends it to the binlog.
  2. Receiver thread on each replica streams new binlog events from the source.
  3. Relay log. The replica writes those events to a local file first.
  4. Applier threads read the relay log and apply the changes to the replica’s data.
  • Asynchronous by default. The primary does not wait for any replica. Default
  • Parallel apply. 4 applier workers by default since 8.0.27, keeping commit order. Default · check 14 Added
  • GTIDs make position simple. Each transaction gets an ID server_uuid:number, so a replica can say “send what I don’t have” instead of tracking file offsets. Added
Name the three threads involved in classic MySQL replication and say what each does.
The binlog dump thread on the source sends events; the receiver (I/O) thread on the replica writes them to the relay log; the applier (SQL) thread or threads on the replica apply them.

Replication lag

In plain wordsReplicas are always a little behind the primary: usually milliseconds, sometimes seconds. A user who saves something and immediately reads it back from a replica might not see it yet. This lesson is about living with that delay.

New words

replication lagHow far a replica is behind the primary.
read-your-writesThe promise that a user always sees their own latest changes.

Replicas are always a little behind, and the app must decide which reads can tolerate that.

Why lag happens

  • Large transactions take long to apply
  • Sustained write load
  • Slower disks or CPU on replicas
  • Network latency or throttling

What to do about it

  • Read your writes: send a user’s reads to the primary for a few seconds after they write
  • Causal reads: wait until the replica has the GTID you wrote
  • Accept staleness: feeds and dashboards can be seconds behind
  • Seconds_Behind_Source is a rough number. It compares event timestamps, so it reads 0 when the replica is idle and can jump after a long transaction. Simplified · check 12
  • Causal reads are a real function: WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout) returns 0 once the replica has applied it. Added
Production note. “Order placed, now show my orders” must not read from a lagging replica. Route it to the primary, or wait for the GTID.
A user pays and is redirected to “my orders”, which reads from a replica. Why might the new order be missing, and what are two fixes?
Replication is asynchronous, so the replica may not have applied the order yet. Fix it by reading from the primary for a short time after a write, or by waiting on the replica until it has applied the transaction’s GTID.

Why shard, and when not to

In plain wordsCopies help with reading, but every write still goes to one primary. When one machine can no longer hold all the data or take all the writes, you split the data so that each server owns part of it.

New words

vertical scalingBuying a bigger machine.
shard keyThe column that decides which shard a row belongs to.

Sharding splits the data across several primaries so storage and write throughput add up, at the price of complexity you own forever.

Shard when at least one is true

  • The data no longer fits one server: storage, indexes and working set.
  • Writes exceed one primary. Replicas add no write capacity.
  • Replicas cannot keep up, or lag becomes unacceptable.
  • Geography: data residency or regional latency.

Why do read replicas not help when the bottleneck is write throughput?
Every write still has to go through the single primary, and every replica must also apply every write. Only sharding splits the writes.

Range, hash and directory sharding

In plain wordsOnce the data is split, every query must know which shard to ask. There are three common rules: by ranges of the key, by a hash of the key, or by looking it up in a directory.

New words

hashA function that turns a value into a number that looks random but is always the same for the same input.
modulo (mod)The remainder after division: 10 mod 4 = 2.

A router needs a rule to map a key to a shard: by range, by hash, or by looking it up in a table.

Range

Shard 1: user_id 1–1,000,000
Shard 2: 1,000,001–2,000,000
Shard 3: 2,000,001–3,000,000

+ easy, range queries stay on one shard. − hotspots: the newest range gets the traffic.

Hash

shard = hash(user_id) % 4
123 → 2,   456 → 1

+ even spread, no “newest is hottest”. − range queries hit every shard; adding a shard moves most keys.

Directory

lookup(user_id 123) → shard 3

+ move one tenant at a time, custom placement. − the lookup service is critical: it needs HA and caching.

Try it: route a user, then add a shard

Pagination without OFFSET

In plain wordsShowing results page by page with OFFSET makes MySQL count past every earlier row each time. Remembering where the last page ended, and starting from there, is far cheaper.

New words

keyset paginationFetching the next page with WHERE key > last-key-seen instead of OFFSET.

OFFSET makes MySQL read and throw away every skipped row; a cursor on the last key seen jumps straight to the next page.

-- Bad: scans 10,010 rows to return 10
SELECT * FROM products ORDER BY id LIMIT 10 OFFSET 10000;

-- Good: keyset (cursor) pagination
SELECT * FROM products WHERE id > 10000 ORDER BY id LIMIT 10;

-- Ties in the sort column: use a composite cursor
SELECT * FROM orders
 WHERE (created_at, id) < ('2026-10-04 10:00:00', 7001)
 ORDER BY created_at DESC, id DESC
 LIMIT 20;
  • Cost grows with the page number for OFFSET; it stays flat for a cursor. Guaranteed · check 15
  • The trade: cursors give “next page”, not “jump to page 500”.
Why does LIMIT 10 OFFSET 100000 get slower as the offset grows?
MySQL still has to find and step over all 100,000 earlier rows before it can return the next 10. A keyset cursor (WHERE id > last_id) starts directly at the right place.
