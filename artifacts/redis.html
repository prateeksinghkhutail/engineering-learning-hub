Part 1: Why Redis

Memory, one thread, and when to say no

01

A data structure server in RAM

Redis keeps every key in memory and stores values as ready-made data structures, so most commands finish in microseconds and the network trip is the slow part.

Think first. A disk-backed database answers in 5 to 50 ms. Redis answers in well under 1 ms. Before reading on, guess where the difference comes from.
WhatAn in-memory key-value store whose values are strings, hashes, lists, sets, sorted sets, streams and more.
WhyMemory is about a thousand times faster than an SSD, and smart value types let the server do the work instead of the app.
HowA client sends a command such as ZINCRBY; Redis changes the structure in place and replies.
  • Values are structures, not blobs. You can add one member to a set without reading the whole set back. That is why the notes call it more than a key-value store.
  • Memory is the limit. The whole dataset must fit in RAM. Persistence (Part 3) is for surviving restarts, not for holding more data than RAM. Guaranteed
  • Network is the cost. Batch commands with pipelining or MGET when you can. Added
A Redis GET takes 0.3 ms end to end. Roughly how much of that is the command itself?
Almost none: a few microseconds. Nearly all of it is the network round trip and the client library. That is why batching (pipelining, MGET) helps so much.

02

Why one thread is fast, and safe

Redis runs every command on a single thread, one after another, which removes locking costs and makes every single command atomic for free.

  • I/O multiplexing. The event loop asks the OS (epoll on Linux) which connections have data, then serves them in turn.
  • Every command is atomic. Nothing can run in the middle of an INCR. Guaranteed
  • “Mostly” single-threaded. Since 6.0, extra I/O threads can read and write sockets, but commands still run on one thread. Background threads free memory and fsync files. Added
  • The price: one slow command (KEYS *, a long Lua script) stalls every client. Guaranteed · check 1

Try it: two buyers, one stock counter

stock:501 = 10. Asha (web-1) and Bob (web-2) each buy one keyboard at the same moment.
One command is atomic. A sequence of commands from your app is not, unless you use MULTI, a Lua script, or a single command that does it all.
Why can two app servers both doing GET stock then SET stock−1 oversell, even though Redis is single-threaded?
Each command is atomic, but the pair is not: Redis can run Bob’s GET between Asha’s GET and SET. Both read 10 and both write 9. A single DECR does the read and write inside one command.

03

When to choose Redis, and when not to

Choose Redis when you need very fast access to data that fits in memory and can be rebuilt; refuse it when the data is your only copy or needs real queries.

Good fits

  • Cache in front of a database
  • Rate limiting and counters
  • Leaderboards and rankings
  • Sessions with expiry
  • Light messaging, locks, coordination

Poor fits

  • Ad-hoc queries, joins, aggregations
  • Data bigger than RAM
  • Money and orders: loss is not acceptable
  • Rich relationships and integrity rules
  • The only copy of anything critical
Interview systemThe Redis feature that fits
Rate limiterAtomic counters with TTL, or a sorted-set sliding window
Session storeHash per session, TTL for expiry
LeaderboardSorted set: O(log N) update and rank
Distributed cacheEviction policies, Cluster for size
Real-time analyticsHyperLogLog, Streams, Pub/Sub
Distributed lockSET … NX PX

Feature flagsHash, fast lookups
In an interview. Weak: “Redis, because it is fast.” Strong: name the structure, the command, its cost, and what you give up. “A sorted set; ZINCRBY updates a score in O(log N); we accept losing up to a second of scores on a crash.”
Why is “Redis as the only copy of order data” a weak design, even with persistence turned on?
With the usual settings Redis can lose about the last second of writes on a crash, and replication is asynchronous so a failover can lose more. Orders need a database built for durability; Redis can sit in front of it.

Part 2: Data structures

Pick the shape, get the speed

04

Keys, TTLs and how expiry really works

Every value lives under a string key, any key can carry a time to live, and Redis removes expired keys both when you touch them and with a small background sweep.

  • Name keys like paths: type:id:field, e.g. cache:product:501. Colons are only a convention, but they make keys readable and scannable.
  • An expired key is never returned. Even if it still sits in memory, a read deletes it first. Guaranteed
  • Writes can clear a TTL. A plain SET on an existing key removes its TTL unless you pass KEEPTTL or a new EX. Guaranteed · check 2 Added
SET cache:product:501 "{…}" EX 300     # value and a 300 s TTL in one command
TTL cache:product:501                   # seconds left, -1 = no TTL, -2 = no such key
EXPIRE session:9f2c7a 1800              # (re)set a TTL
PERSIST session:9f2c7a                  # remove the TTL
A key’s TTL passed five minutes ago but nobody has read it. Is it still using memory?
Possibly, for a short while. Lazy expiry only deletes it on access; the active sweep samples keys with TTLs about ten times a second and will find it soon. It is never returned to a client either way.

05

Strings and counters

A string holds any bytes up to 512 MB, and if those bytes look like an integer Redis can add to it atomically.

SET user:123:name "Asha"
GET user:123:name                    # "Asha"
INCR page:views                      # atomic +1, creates the key at 0 first
INCRBY stock:501 -1                  # same as DECR
SET lock:product:501 a7f3e1 NX EX 30 # set only if absent, expire in 30 s
  • O(1) for GET, SET, INCR. MGET and MSET cost O(N) for N keys, but one round trip.
  • Counters are the superpower. INCR with a TTL is a complete rate limiter in two commands (lesson 29).
  • SET … NX is a primitive lock: only one client can create the key. Guaranteed
Why is storing a whole user object as one JSON string awkward when you often change a single field?
To change one field you must read the whole JSON, edit it in the app, and write it all back, which is two round trips and a race between clients. A hash lets you change one field with HSET.

Hashes

A hash is a small map of fields to values under one key, which is how you store an object and change one field at a time.

HSET session:9f2c7a user_id 123 name "Asha" cart_items 1
HGET session:9f2c7a name              # "Asha"
HINCRBY session:9f2c7a cart_items 1   # 2, atomic
HGETALL session:9f2c7a                # every field: O(N)
  • O(1) per field; HGETALL is O(N).
  • One TTL per key, not per field in classic Redis. Redis 7.4 added field-level expiry (HEXPIRE). Added
  • Use it for profiles, sessions, per-field counters.
Why does a small hash use less memory than the same fields stored as separate string keys?
Each separate key carries its own key object, hash-table entry and metadata. A small hash stores all its fields in one compact listpack block under a single key.

Lists and queues

A list is an ordered sequence you push and pop at either end in O(1), which makes it a natural queue or a “latest N” feed.

LPUSH queue:emails "email:7001"
BRPOP queue:emails 30                  # wait up to 30 s for a job
LPUSH feed:user:123 "ordered keyboard"
LTRIM feed:user:123 0 99               # keep only the latest 100
LMOVE queue:emails queue:emails:busy RIGHT LEFT   # safer: move instead of pop
  • Ends are O(1), the middle is O(N). LINDEX on a long list walks it.
  • Inside, it is a quicklist: a linked list of compact listpack blocks, not one node per item. Added
  • A popped job is gone. If the worker crashes mid-job, it is lost. LMOVE to a “busy” list, or Streams, fix that.
A worker BRPOPs a job and crashes before finishing it. What happens to the job, and how can you avoid that?
It is lost: BRPOP removed it. Use LMOVE (or BLMOVE) to move it to an in-progress list and delete it when done, or use a Stream with a consumer group, which keeps it pending until acknowledged.

Sets

A set holds unique members with no order, so “is X in it?” and “add X once” are O(1), and sets can be intersected and unioned on the server.

SADD wishlist:123 product:310 product:501 product:777
SISMEMBER wishlist:123 product:501      # 1
SINTER wishlist:123 wishlist:25         # product:501, product:777
SCARD wishlist:123                      # 3, O(1)
  • Add, remove, check: O(1). SMEMBERS and SINTER grow with set size.
  • Exact unique counting costs memory: a set of a million user IDs is tens of megabytes. Lesson 10 counts the same thing in 12 KB.
  • Small integer sets are stored as a sorted array (intset) to save space. Added
You need “friends in common” for two users. Which structure and command?
A set of friend IDs per user and SINTER on the two keys. The server returns only the common members.

Sorted sets and the skip list

A sorted set keeps unique members ordered by a numeric score, and a skip list inside lets Redis insert, rank and range-read in O(log N).

WhatA set where each member has a score; reads come back in score order.
WhyRankings change constantly; re-sorting a list on every update would be O(N log N).
HowA skip list orders members by score; a hash table maps member → score for O(1) lookups.

Try it: the best-sellers board during the sale

CommandDoesCost
ZADD key score memberAdd or updateO(log N)
ZINCRBY key n memberAdd to a score, atomicallyO(log N)
ZREVRANK key memberRank, highest first, from 0O(log N)
ZREVRANGE key 0 9 WITHSCORESTop 10O(log N + M)
ZRANGEBYSCORE key min maxMembers in a score rangeO(log N + M)
  • Scores can be timestamps, which turns a sorted set into a time index: sliding-window rate limits, delayed jobs, recent feeds.
  • Ties sort by member name, byte by byte. Guaranteed Added
  • Small sorted sets are a listpack (up to 128 members) and switch to skip list + hash table beyond. Default · check 4
Why a skip list and not a balanced tree?

Both give O(log N). A skip list is simpler to implement, and range reads are just a walk along the bottom lane. Each node is promoted to the next lane with probability 1/4, up to 32 lanes, so lanes thin out geometrically without any rebalancing. Added

Why can a sorted set return a player’s rank in O(log N) while a plain list would need O(N)?
The skip list keeps members ordered and stores how many nodes each link skips, so Redis can add up spans on the way down and know the rank without walking every member.

HyperLogLog: counting without remembering

HyperLogLog estimates how many distinct items it has seen using at most 12 KB, by remembering patterns in hashes instead of the items themselves.

The intuition: rare coin streaks

Hash every visitor ID to random-looking bits. A hash starting with 10 zeros happens about once in 1,024 items, so seeing one hints you have seen around a thousand distinct items. Repeats hash the same, so they change nothing. HyperLogLog splits hashes into 16,384 buckets, keeps the longest run of zeros per bucket (6 bits each, about 12 KB), and averages them to cut the noise. Simplified Added

PFADD uv:product:501:2026-10-04 user:123 user:25
PFADD uv:product:501:2026-10-04 user:123      # already seen: no change
PFCOUNT uv:product:501:2026-10-04             # the estimate
PFMERGE uv:product:501:week uv:product:501:2026-10-04 uv:product:501:2026-10-05
  • Standard error about 0.81%. Guaranteed
  • Merging is free of double counting: a visitor seen on two days is counted once in the week.
  • You cannot list members or ask “was user 123 here?”. Use a set when you need that.
Why does adding the same visitor ID to a HyperLogLog twice not change the count?
The ID hashes to the same bucket and the same run of zeros both times, so the stored maximum does not change.

Streams: a log with consumer groups

A stream is an append-only log of entries with time-based IDs, and consumer groups let several workers share it with acknowledgements, so nothing is lost when one crashes.

  • IDs are milliseconds-sequence, so entries are ordered by time and you can read by time range.
  • Unlike Pub/Sub, entries persist. A worker that was down reads what it missed.
  • Crash safety: unacknowledged entries stay in the pending list; XAUTOCLAIM hands them to a healthy worker. Added
  • Cap the length with XADD … MAXLEN ~ 100000, or it grows forever.
What is the difference between two consumers in the same group and two consumers in different groups?
In the same group they share the work: each entry goes to one of them. In different groups each group receives every entry.

Part 3: Surviving restarts

Snapshots, logs, and what a crash costs

13

RDB snapshots: fork and copy-on-write

To save a snapshot without pausing, Redis forks a child process that writes the data to dump.rdb while the parent keeps serving clients, and the OS copies only the memory pages that change meanwhile.

Think first. Writing 10 GB to disk takes many seconds. How can Redis keep answering writes during that time and still save a consistent point-in-time picture?
# redis.conf: save after N seconds if at least M keys changed
save 3600 1 300 100 60 10000          # the default since Redis 7: 1h/1, 5min/100, 1min/10000
dbfilename dump.rdb
  • Point in time. Everything written after the last snapshot is lost on a crash. Guaranteed
  • Fast restarts. Loading one compact binary file is much quicker than replaying a log.
  • Fork is not free. Copying the page table takes roughly 10 ms per GB of RAM, and a write-heavy workload can nearly double memory during the save. Simplified
  • Your notes show the older defaults (900/300/60 seconds). Redis 7 changed them to the line above. Default · check 5 Added
If it breaks: with too little free RAM for copy-on-write pages, the OS may kill Redis or the fork fails (“Can’t save in background”). Leave headroom and set vm.overcommit_memory = 1 on Linux.
During a BGSAVE the parent process changes a key. Does the snapshot contain the old value or the new one, and why?
The old value. The child sees memory as it was at fork time; when the parent writes, the OS copies that page for the parent, leaving the child’s view unchanged.

AOF: logging every write

With the append-only file on, Redis writes every change command to a log and replays it at startup, and one setting, appendfsync, decides how much a crash can lose.

appendfsyncfsync happensA crash can loseSpeed
alwaysAfter every writeNext to nothingSlowest
everysec (default)Once a second, in a background threadAbout 1 second (up to 2 in a disk stall)Good
noWhen the OS decides, often ~30 sMany secondsFastest
# redis.conf
appendonly yes            # off by default
appendfsync everysec
  • AOF is off by default. Default · check 5
  • The file is the commands themselves in Redis’s wire protocol (RESP), readable with a text editor.
  • Damaged tail? redis-check-aof --fix truncates a half-written last command.
  • Costs: bigger files than RDB and slower restarts, because every command is replayed.
With appendfsync everysec, a power cut hits 0.6 s after Asha’s DECR returned. Is the DECR on disk?
Probably not. It was written to the OS page cache, but the once-a-second fsync may not have run yet, so it can be lost. With appendfsync always it would be on disk before Redis replied.

AOF rewrite and hybrid persistence

An AOF grows forever, so Redis periodically rewrites it as the shortest set of commands that rebuilds today’s data, and stores that base as an RDB snapshot for fast loading.

# redis.conf
aof-use-rdb-preamble yes            # hybrid: the base is RDB (the default)
auto-aof-rewrite-percentage 100     # rewrite when the log doubles…
auto-aof-rewrite-min-size 64mb      # …and is at least 64 MB
  • Hybrid = fast load + small loss window. Load the RDB base quickly, replay only the short tail. Default
  • Rewrites fork too, so the copy-on-write memory note from lesson 13 applies.
Why does an AOF rewrite read the in-memory data rather than compacting the old log file?
The current data already is the final state. Writing one command per key from memory produces the shortest possible log, without parsing millions of old commands.

Part 4: Replication and failover

Copies, and who decides who is in charge

17

Replication: full sync and partial resync

A replica first copies a full snapshot from the primary, then receives every write as a stream; after a short disconnect it asks only for what it missed.

  • Replication ID + offset name a position in the primary’s history, like a bookmark. Added
  • The backlog is a ring buffer, 1 MB by default. Disconnected too long and the bytes are overwritten: back to a full sync. Default · check 6 Added
  • Replicas are read-only by default, and serve slightly stale data.
# redis.conf on redis-2 and redis-3
replicaof redis-1 6379
repl-backlog-size 64mb        # bigger backlog: survive longer blips without a full sync
A replica was disconnected for ten minutes under heavy write load and now does a full resync. Why not a partial one?
The bytes it missed had already been overwritten in the primary’s fixed-size replication backlog, so the primary could not continue from the replica’s offset.

Asynchronous writes, and what WAIT really buys

The primary replies before replicas have a write, so a crash can lose it; WAIT lets one client block until replicas confirm, which narrows that window but does not close it.

DECR stock:501
WAIT 1 100        # block until 1 replica acknowledges, or 100 ms pass; returns how many did
  • WAIT returns a count, not an error. Check it: 0 means no replica confirmed in time. Guaranteed · check 13
  • It is not strong consistency. Redis’s own docs say so: a failover can still pick a replica that had not received the write. Added

Sentinel: automatic failover

Sentinels are separate processes that watch the primary, agree when it is really down, promote the best replica, and tell clients the new address.

  1. Subjectively down. One Sentinel gets no valid reply for down-after-milliseconds.
  2. Objectively down. A quorum of Sentinels agree.
  3. Elect a leader among Sentinels; it needs a majority.
  4. Pick the best replica: priority, then least lag (highest offset).
  5. Promote and repoint. The rest follow the new primary; the old one rejoins as a replica.
  6. Clients ask Sentinel for the current primary and reconnect.
# sentinel.conf
sentinel monitor shop 10.0.2.11 6379 2      # name, address, quorum
sentinel down-after-milliseconds shop 5000  # stock default is 30000
sentinel failover-timeout shop 60000
sentinel parallel-syncs shop 1
  • Failover takes seconds, not milliseconds: detection time plus election plus promotion, often 10 to 30 s. Simplified
  • Use three or five Sentinels: an odd number avoids tied votes and survives one or two failures.
With 5 Sentinels and quorum 2, can just two Sentinels trigger a failover on their own?
They can mark the primary objectively down, but the failover needs a leader elected by a majority of all Sentinels, so at least 3 of the 5 must take part.

MOVED, ASK and smart clients

Any node answers “not mine, ask that one” for a key it does not own, and smart clients cache the slot table so that almost every command goes to the right node first time.

-MOVED slot host:portThat slot belongs to another node, permanentlyUpdate its slot table and retry there

  • Nodes never proxy. They redirect; the client does the second hop. Guaranteed
  • ASK exists for resharding: during a slot move some keys are on the old node and some on the new. Added
  • Nodes gossip on port + 10000 (16379), the cluster bus, to share slot ownership and failure reports. Added
What is the difference between a MOVED and an ASK redirect?
MOVED means the slot now lives on another node: update the routing table. ASK means the slot is mid-migration and only this key has moved: go there once (with ASKING) but keep the table as it is.

maxmemory and eviction policies

When Redis reaches its memory limit, the eviction policy decides whether to reject writes or delete some keys to make room.

volatile-lru (or volatile-lfu), with a TTL on every cache key and no TTL on the stock counters. Only keys with a TTL can be evicted, so the counters are safe.

LRU vs LFU

LRU keeps what was used recently; LFU keeps what is used often, and the difference shows the moment something reads a lot of data once.

Try it: a batch job scans the catalog while shoppers browse

Cache holds 4 products. 501 and 777 are the hot sale items; s1 to s6 are a one-off scan. Green is a hit, red a miss. Exact LRU and LFU, for clarity. Simplified

  • LRU fails on scans: each scanned key becomes “most recent” and pushes out the hot ones.
  • LFU fails on shifts: yesterday’s hot key keeps a high count, so counters decay over time (lfu-decay-time, 1 minute).
  • Redis approximates both. It samples 5 keys and evicts the best candidate, instead of keeping a perfect ordering. Default · check 10 Added
What happens internally

Each key carries 24 bits of metadata. For LRU it is a coarse last-access clock. For LFU it is an 8-bit logarithmic counter (a key needs more and more hits to raise it) plus a decay timestamp. On eviction Redis samples maxmemory-samples keys, keeps a small pool of the best candidates, and evicts the worst. More samples means closer to exact and more CPU. Added

A nightly report reads a million products once each. Which policy protects the daytime hot set, and why?
LFU. The scanned products are read once, so their frequency stays low and they are evicted first. Under LRU they would be the most recently used and push out the popular products.

Memory hygiene: big keys, hot keys, and KEYS

Most Redis incidents come from three habits: one huge key, one overloaded key, and one command that walks every key while everyone waits.

Big key

A hash with 5 million fields. DEL or HGETALL on it blocks the thread. Split it, and use UNLINK to delete in the background.

Hot key

One key read 200,000 times a second lands on one node. Cache it in the app for a second, or keep copies under several keys.

KEYS *

O(N) over the whole keyspace on the single thread. Use SCAN, which walks in small batches between other commands.

SCAN 0 MATCH cache:product:* COUNT 100      # returns a cursor; repeat until it is 0
MEMORY USAGE session:9f2c7a                 # bytes for one key
redis-cli --bigkeys                         # sample the keyspace for the largest keys
INFO memory                                 # used_memory, maxmemory, fragmentation

Saving memory

  • Group small fields in a hash rather than many keys (lesson 06).
  • Set TTLs on everything that is a cache.
  • Compress large values in the app before SET.
  • Short key names help only at huge key counts. Readability usually wins. Simplified
Why is KEYS * dangerous on a production Redis but SCAN is fine?
KEYS walks every key in one command, blocking the single thread for as long as that takes. SCAN returns a small batch and a cursor, so other clients’ commands run between batches.

Cache-aside, and how caches go wrong

The app checks Redis first, falls back to the database on a miss and fills the cache for next time; the hard parts are keeping it fresh and surviving a burst of misses.

def get_product(pid):
    cached = redis.get(f"cache:product:{pid}")
    if cached:
        return json.loads(cached)                     # hit
    row = db.query("SELECT * FROM inventory WHERE product_id = %s", pid)
    ttl = 300 + random.randint(0, 30)                 # jitter: don't expire together
    redis.set(f"cache:product:{pid}", json.dumps(row), ex=ttl)
    return row

def update_price(pid, price):
    db.execute("UPDATE inventory SET price = %s WHERE product_id = %s", price, pid)
    redis.delete(f"cache:product:{pid}")              # delete, don't overwrite

Three ways it goes wrong Added

Stampede

A hot key expires and 5,000 requests miss at once, all hitting MySQL. Fix: one request rebuilds under a short lock while the rest wait or serve the stale copy.

Stale data

The database changed but the cache did not. Fix: delete the key after every write, and keep TTLs short enough to bound staleness.

Synchronised expiry

Ten thousand keys cached at deploy time all expire together. Fix: add random jitter to TTLs.

  • Delete rather than update the cache on writes: two concurrent updates can otherwise leave the older value in Redis.
  • The TTL is your safety net: whatever goes wrong, staleness ends when the key expires.
After updating a product’s price, why delete the cache key instead of writing the new price into it?
Two updates racing could write their cache values in the opposite order to their database writes, leaving the old price cached. Deleting means the next read loads whatever the database holds.

Rate limiting: three algorithms

Every rate limiter counts requests in a window of time; fixed windows are cheapest, sliding windows are exact, and token buckets allow controlled bursts.

Fixed window

INCR rl:123:202610041000
EXPIRE rl:123:202610041000 60

One counter per minute. Cheap, but a burst at 10:00:59 plus one at 10:01:00 gets double the limit.

Sliding window log

ZREMRANGEBYSCORE rl:checkout:123 0 now-60000
ZCARD rl:checkout:123
ZADD rl:checkout:123 now req-id

Exact: counts requests in the last 60 s. Memory grows with the limit.

Token bucket

tokens = min(cap, tokens + elapsed × rate)
if tokens ≥ 1: tokens −= 1, allow

Allows a burst up to the bucket size, then a steady rate. Needs a Lua script.

Try it: 5 checkouts per 10 seconds

  • Check, then count, atomically. Run the three sliding-window commands in one Lua script, or two API servers can both see 4 and both allow a 5th. Added
  • Your notes add the request before counting, which also counts rejected requests. Fine for abuse control, unfair for honest users: count first, add only if allowed. Added
Why can a fixed-window limiter of 100 requests per minute let through 200 requests in two seconds?
100 at the end of one window and 100 at the start of the next both fit their own window’s counter, even though they are two seconds apart. A sliding window counts the last 60 seconds from now, so it would reject the second hundred.

Distributed locks and Redlock

A Redis lock is a key that only one client can create, with a token so only the owner can release it and a TTL so a crashed owner cannot hold it forever.

# acquire: only if absent, auto-expire after 30 s, value = a random token
SET lock:product:501 a7f3e1c9 NX PX 30000

# release: delete only if the token is still mine (Lua, so check + delete is atomic)
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
  • NX makes it exclusive; PX makes it safe from crashes; the token stops you deleting someone else’s lock after yours expired.
  • A lock is a lease, not a guarantee. If your process pauses longer than the TTL (GC, swap), the lock expires and a second client gets it while you still think you own it.
  1. Note the time and try SET … NX PX on all 5 instances with a short per-node timeout.
  2. Count successes. Need at least 3.
  3. Subtract elapsed time from the TTL; that is how long the lock is really valid.
  4. Failed? Release on every instance, then retry after a random delay.
The debate. Martin Kleppmann showed that pauses and clock jumps can still give two holders. If correctness depends on the lock, have the protected resource check a fencing token, a number that increases with each grant, and reject older ones. Use Redis locks for efficiency (avoid duplicate work), not as the only guard of correctness. Added
Why must a lock release check the token instead of just calling DEL?
Your lock may have expired and been taken by another client. A blind DEL would remove their lock. Comparing the stored token with yours, in one Lua script, deletes only your own.

MULTI, EXEC and WATCH

MULTI queues commands and EXEC runs them back to back with nothing in between, and WATCH cancels the whole batch if a key changed since you read it.

  • Queued, not run: inside MULTI every command replies QUEUED, so you cannot branch on a value.
  • No rollback. If one command fails at run time (wrong type), the others still apply. Guaranteed · check 12
  • Syntax errors abort the batch: a command rejected while queuing makes EXEC fail with EXECABORT. Added
Inside MULTI you run INCR on a key that holds a list. What happens to the other commands in the transaction?
They still run. The INCR fails at execution time with a WRONGTYPE error in its slot of the reply, but Redis has no rollback, so the rest are applied.

Lua scripts

A Lua script runs on the server as one atomic step, so you can read, decide and write in a single round trip with no retries.

-- reserve.lua: one unit per buyer, never below zero
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return -1                                   -- already bought one
end
if stock < 1 then
  return 0                                    -- sold out
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1                                      -- reserved
SCRIPT LOAD "…reserve.lua…"                   # returns the script's SHA1

  • Conflicts mean retries
  • Several round trips

  • Logic on the server
  • Never conflicts: nothing interleaves
  • One round trip
  • Atomic because single-threaded: nothing else runs while the script does. Guaranteed

  • Pass every key in KEYS[] so Cluster can check they share a slot.
  • Redis 7 Functions (FUNCTION LOAD, FCALL) store named scripts on the server, persisted and replicated. Added
When would you choose a Lua script over WATCH/MULTI/EXEC?
When you must read a value and decide what to write based on it, especially under contention. The script does it atomically in one round trip with no retries; WATCH needs retry logic every time someone else touches the key.

Quick revision and glossary

Test yourself, then look up any term.

Explain in one sentence why Redis is fast and why a single slow command hurts everyone.
All data is in RAM and one thread runs commands without locks, so each is microseconds; but because there is one thread, a slow command makes every other client wait.
What can be lost if the primary crashes with appendfsync everysec and asynchronous replication?
Up to about a second of writes not yet fsynced locally, and any writes not yet replicated if a replica is promoted. That is why Redis should not be the only copy of critical data.
Name the data structure for each: unique visitor estimate, top 10 products, latest 100 events, object with fields.
HyperLogLog, sorted set, list (LPUSH + LTRIM) or stream, hash.
Why does adding a node to Redis Cluster not require rehashing every key?
Keys map to one of 16,384 fixed slots; adding a node moves whole slots to it, and keys follow their slots.

SentinelA separate process that monitors Redis, votes on failures and promotes a replica.
quorumHow many Sentinels must agree the primary is down before a failover starts.
hash slotOne of 16,384 buckets in Redis Cluster; each key belongs to exactly one.
hash tagThe part of a key inside braces; only it is hashed, so related keys share a slot.
MOVEDA cluster reply telling the client which node owns a slot.
evictionDeleting keys to free memory once maxmemory is reached.
cache-asideThe app reads the cache, loads from the database on a miss, and fills the cache.
stampedeMany requests missing the same expired key and hitting the database together.
fencing tokenAn increasing number issued with a lock, so a resource can reject stale lock holders.
RedlockA lock taken on a majority of independent Redis instances.
