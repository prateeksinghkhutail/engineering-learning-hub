01

Why a database at all?

In plain wordsImagine an online shop keeping every order in one text file. Two customers buy at once and one order overwrites the other; the power cuts mid-save and the file breaks; finding one order among millions means reading it all. A database solves these problems. Different databases organise data differently: MongoDB keeps each order as one self-contained document, a bit like one filled-in form per order.

New words

databaseA program that stores data safely and answers questions about it.
server / clientThe database runs as a server program; your app is a client that connects to it over the network.
documentOne record in MongoDB: a set of named fields, like a form.
NoSQLDatabases that do not use SQL tables as their main model. MongoDB is one.

A database is a program whose job is to remember data safely, let many people change it at once, and find any piece of it quickly; MongoDB is a database that stores data as documents.

Name three problems a database solves that a plain text file does not.
Many users changing data at once without losing changes; surviving a crash without half-written data; and finding one record quickly among millions.

02

Documents, fields and JSON

In plain wordsJSON is a simple way to write data that both people and programs can read. Curly braces mean “an object with named fields”, square brackets mean “a list”. A MongoDB document is one such object, and it can contain lists and smaller objects, so related data can sit together in one place.

New words

JSONA text format for data: objects in { }, lists in [ ], text in quotes, numbers as is.
fieldA name and its value inside a document, like "amount": 1200.
arrayA list of values in square brackets.
nested documentA document inside another document.
collectionA group of documents, like a folder. Orders go in the orders collection.

A MongoDB document is written like JSON: curly braces holding named fields, whose values can be text, numbers, lists, or other documents nested inside.

{
  "_id": "order_5001",               // field: a unique ID
  "customer_id": "customer_101",     // field: text
  "amount": 1200,                    // field: a number
  "status": "created",
  "items": [                         // field: an array (a list)…
    { "name": "Laptop", "price": 999, "quantity": 1 },   // …of nested documents
    { "name": "Mouse",  "price": 29,  "quantity": 2 }
  ]
}
  • Every document has an _id, unique in its collection. Guaranteed
  • Documents in one collection need not have the same fields. That flexibility is MongoDB’s headline feature, and also a responsibility.
In the document above, what kind of value is “items”, and what is inside it?
An array (a list). Each element is a nested document describing one item with a name, price and quantity.

Your first MongoDB commands

mongoshMongoDB’s command-line shell for typing commands.
filterA document describing which documents you want.
$setAn update operator meaning “set these fields to these values”.

In the mongosh shell you insert, find, update and delete documents with short commands that take documents as their arguments.

04

One server, then many

In plain wordsOne server can break, and one server can get full. Keep identical copies on other servers so one can take over if the first breaks; and when the data is too big, split it so each group of servers holds part of it, with a router in front that knows who holds what. This lesson only introduces the words; Parts 2 and 3 explain them properly.

New words

replica setA group of servers holding the same data: one primary and its secondaries.
primaryThe member that accepts writes.
secondaryA member that copies the primary and can take over if it fails.
shardingSplitting a collection’s documents across several replica sets.
shardOne replica set holding one part of the data.
mongosThe router apps connect to in a sharded cluster.

Real deployments run MongoDB on several servers: copies for safety (a replica set), and, when data outgrows one machine, a split across groups of servers (sharding).

Do secondaries let you store more data than fits on one server?
No. Every member of a replica set holds all the data. Storing more needs sharding, which splits documents across several replica sets.

MongoDB is a document database

In plain wordsThis lesson picks up where Part 0 left off and makes the structure precise: databases hold collections, collections hold documents, documents hold fields, and fields can hold lists and smaller documents.

New words

BSONThe binary form of JSON that MongoDB actually stores, with extra types like dates and exact decimals.
ObjectIdA 12-byte ID MongoDB generates for _id when you do not give one.

A database holds collections, a collection holds documents, and a document is a set of fields that can nest.

{
  "_id": "user_101",
  "name": "Prateek",
  "email": "prateek@example.com",
  "skills": ["Java", "Kafka", "MongoDB"]   // an array lives inside the document
}
SQLMongoDBThe difference that matters
DatabaseDatabaseSame idea.
TableCollectionNo fixed column list.
RowDocumentCan hold nested objects and arrays.
ColumnFieldTwo documents may have different fields.
  • Every document has an _id. It is the primary key, unique within the collection, and always indexed. Guaranteed Added
  • If you do not supply _id, the driver generates a 12-byte ObjectId. Added
  • You write JSON, MongoDB stores BSON. BSON is a binary encoding of the same shape with more types: dates, 64-bit integers, decimals, binary data. Added
  • One document is at most 16 MB. This limit shapes every modelling decision later. Guaranteed · check 14
JSON and BSON, conceptually

JSON is text: easy to read, slow to scan, and it has only one number type. BSON is length-prefixed binary: the server can skip over a field without parsing it, and it knows an int64 from a double from a Date. You rarely see BSON directly. Drivers convert both ways. Added

Key idea: think in documents, not rows. A document is one self-contained thing your application uses.
What are the MongoDB equivalents of a SQL table, row and column?
Collection, document and field. The difference is that documents can nest and need not share the same fields.

06

Why MongoDB exists

In plain wordsDatabases sit on a spectrum. Simple key-value stores are fast but can only fetch by key; relational databases are strict and powerful. MongoDB sits in between: flexible documents, rich queries, and built-in ways to spread data over many servers.

New words

key-value storeA database that only stores and fetches values by a key.
schemaThe shape of the data: which fields exist and what types they have.
horizontal scalingHandling more data or load by adding servers.

MongoDB sits in the middle: richer queries than a key-value store, more schema flexibility than a relational database, and horizontal scaling built in.

Document-shaped data

Profiles, carts, activity feeds and content metadata are already self-contained objects.

Flexible, evolving schemas

Adding a field needs no schema migration.

Hierarchical, nested data

Items inside an order, comments inside a post: no joins to reassemble them.

Rapid development

The stored shape matches the object in your code.

Rich queries

Aggregations, full-text search and geospatial queries, beyond key lookups.

Horizontal scaling

Built-in sharding spreads data across servers.

Schema-less means I do not need to design a schema.

The database will not stop you, so the design burden moves to you. You cannot ignore data modelling and hope the flexibility saves you.

System design insight. You also cannot use it like a relational database and expect good results. Most of this course is about what to do instead.

When not to choose MongoDB

In plain wordsEvery strength has a cost. Data with many relationships, constant multi-record transactions, or strict schema rules fits a relational database better. Saying where you would not use MongoDB makes your “yes” believable.

New words

transactionSeveral changes that succeed or fail together.
referential integrityThe guarantee that a reference always points to something that exists.

Each weak spot is the other side of a trade MongoDB made on purpose.

You needThe trade-offOften cleaner
Complex multi-table transactionsTransactions exist but the engine is not optimised for workloads that use them constantly.PostgreSQL
Highly relational dataMany relationships and frequent joins fight the document model. Foreign keys do this better.PostgreSQL
Strong schema enforcementFlexibility was bought by giving up strict constraints.PostgreSQL
Simple key-value accessYou pay for query features you never use.DynamoDB or Redis

  • Every write crosses entities. A transfer changes two accounts, a ledger and a payment record.
  • Integrity is the product. Foreign keys and constraints catch mistakes the application missed.
  • So a relational primary is cleaner. MongoDB can do it, but you would be using its least-optimised path all day.
System design insight. Saying where you would not use MongoDB is what makes your “yes” credible.
MongoDB supports ACID transactions. Why might a banking ledger still go on PostgreSQL?
Because nearly every operation is a multi-entity transaction with strict integrity rules. MongoDB supports that but is not optimised for it as the main workload; a relational database is.

One MongoDB server

In plain wordsBefore any cluster, follow one request through one MongoDB server: it arrives, the server picks a plan, uses an index if one fits, reads or changes the document, and records the change on disk.

New words

mongodThe MongoDB server program.
WiredTigerMongoDB’s storage engine: the part that keeps data in memory and on disk.
journalA log of changes written to disk so a crash can be recovered.

Before any cluster, a single mongod process takes a request, uses an index if it can, touches the document and answers.

  1. Request arrives. The driver sends a command over a pooled connection.
  2. Query is parsed and planned. The server decides whether an index helps.
  3. Index may be used. If none fits, it scans the whole collection.
  4. Document is read or updated. A change is also written to the journal on disk.
  5. Result is returned.
What happens internally

The storage engine is WiredTiger. It keeps recently used data in an in-memory cache, stores collections and indexes as B-trees, writes changes to a journal (a write-ahead log), and periodically checkpoints the cache to the data files. Added Simplified

If it breaks: one server is one point of failure. If it dies, the database is down until it restarts. That is the problem the next lesson solves.

Replica sets

In plain wordsOne server is one point of failure. A replica set keeps the same data on several servers: one primary takes every write, the others copy it, and if the primary dies they choose a new one.

New words

replica setA group of servers holding the same data.
primary / secondaryThe member that takes writes / the members that copy it.
electionThe vote that chooses a new primary.

A replica set is one primary that takes writes and secondaries that keep copies, so the database survives losing a server.

WhatA group of mongod servers holding the same data.
WhyAvailability and redundancy: no single server is a point of failure.
HowThe primary handles all writes. Secondaries replicate from it. If it fails, they elect a new primary automatically.
  • One primary at a time. All writes go to it. Guaranteed
  • Secondaries can serve reads if you configure it. By default reads go to the primary. Default
  • Elections need a majority. That is why sets have an odd number of voting members, usually three. Added check 2

Adding secondaries lets MongoDB hold more data.

Every member holds all the data. Replica sets solve availability and redundancy. Spreading data out is sharding, in Part 3.

Key idea: replica set = availability + redundancy. Not horizontal data distribution.
A three-member replica set stores 300 GB. How much data does each member hold?
All 300 GB. Replication makes copies; it does not divide the data. Dividing is sharding.

The oplog

In plain wordsThe primary keeps an ordered diary of every change it makes, called the oplog. Secondaries read the diary and repeat each entry, which keeps their copies in step.

New words

oplogOperations log: the primary’s ordered list of changes.
replication lagHow far a secondary is behind the primary.

The oplog is an ordered log of every change the primary made, and replaying it is how secondaries stay in sync.

db.users.updateOne(
  { _id: 101 },
  { $set: { city: "Bengaluru" } }
)

// the oplog entry it produces, conceptually
{ op: "u", ns: "app.users", o2: { _id: 101 }, o: { set: { city: "Bengaluru" } } }
  • Ordered. Entries have a strict order and secondaries apply them in that order. Guaranteed
  • It records results, not commands. “Set city to Bengaluru on _id 101”, so replaying an entry twice is harmless. Added
  • Secondaries pull. Each secondary fetches new entries from another member and applies them. Added
  • Change streams read it too. The same log powers real-time notifications in lesson 48.
What happens internally

The oplog is a capped collection named local.oplog.rs: fixed size, oldest entries fall off the end. A secondary that is offline for longer than the oplog covers cannot catch up and needs a full resync. Added Simplified · check 3

What is the oplog and who reads it?
An ordered log of the changes applied on the primary. Secondaries read it to replicate, and change streams read it to notify applications.

A write in a replica set

In plain wordsA write goes to the primary, which applies it and adds it to the oplog; secondaries copy it soon after. The question this lesson answers: at which moment should the app be told “saved”?

New words

acknowledgementThe server telling the client the write succeeded.
write concernHow many members must have a write before it is acknowledged. Part 6 covers it fully.

The primary applies the write and logs it, secondaries copy it, and the client hears “done” at a point you choose.

LookOne client, one primary, two secondaries, and time running downward.
StepsClient writes to the primary. Primary changes the document and logs it. Secondaries fetch and apply. The primary acknowledges.
WhyOne writer means one order of events. Everyone else just replays it.
RiskAn early acknowledgement can be for a write that only the primary has. If the primary dies right then, the write is lost.
  • w: 1 acknowledges once the primary has it. Fast, but not yet safe from failover.
  • w: "majority" waits until most members have it. Slower, survives failover.
  • Full detail is in lesson 41.

Reads in a replica set

In plain wordsReads can go to the primary, which always has the latest data, or to a secondary, which spreads the load but may be slightly behind.

New words

read preferenceWhich member a read is sent to.
stale readReading data that has since been changed on the primary.

Reading from the primary is always current; reading from a secondary spreads load but may return slightly old data.

  • Read preference picks the member. The default is primary. Default
  • Secondary reads add capacity. Analytics and reports can move off the primary.
  • The price is staleness. Replication is asynchronous, so a secondary can be behind. Simplified · check 6
Production note. “Read your own write” breaks on secondaries. A user who pays and immediately reloads may see the order unpaid. Keep such reads on the primary.
Why can a read from a secondary return stale data?
Replication is asynchronous. The secondary may not yet have applied the latest oplog entries from the primary.

Primary failure and election

In plain wordsWhen the primary stops responding, the other members notice, vote, and promote one of themselves. Writes continue within seconds without anyone doing anything.

New words

heartbeatRegular “I am alive” messages between members.
majorityMore than half the voting members, needed to win an election.

When the primary disappears, the remaining members elect a new one and writes continue without a human.

  1. Primary becomes unavailable. Crash, restart or network cut.
  2. Members detect it. They exchange heartbeats and notice the silence.
  3. Election happens. A secondary asks for votes and needs a majority.
  4. An eligible secondary becomes primary. One with the most recent data wins.
  5. Clients discover the new primary. The driver monitors the set and reconnects.
  6. Writes continue.
  • Heartbeats every 2 seconds, election after 10 seconds of silence. Added Default · check 4
  • Writes pause during the election. Typically a few seconds on top of the timeout. Simplified · check 5
  • Drivers retry a failed write once by default, which hides most failovers from the application. Added Default

Try it: write, then kill the primary

Write a few times with w: 1, then kill the primary before the secondaries catch up.

Green cells are on a majority. Yellow cells are on fewer. Simplified · check 5

If it breaks: a write acknowledged with w: 1 that never reached a secondary is rolled back when the old primary rejoins. The client was told “done” and the write is gone.
The primary of a three-member replica set crashes. What happens next, and can it still accept writes?
The two remaining members detect the missing heartbeats, hold an election, and one becomes primary because two of three is a majority. Writes pause during the election, then continue on the new primary.

Replica set: the big picture

In plain wordsThis lesson zooms out to show all the traffic in a replica set at once: apps talking to members, and members talking to each other to copy data and check health.

New words

driverThe library your app uses to talk to MongoDB; it finds the primary automatically.

Two kinds of traffic share the same servers: client traffic that the driver sends, and replication traffic the members send each other.

LookOne application, one driver, three members. Three line styles.
StepsThe driver sends writes to the primary. The oplog flows to the secondaries. Heartbeats run between all members all the time.
WhySeparating “who serves clients” from “who copies whom” lets a secondary take over without clients changing anything.
RiskLose two of three members and no majority exists: no primary, no writes.
Production note. Put the three members in different racks or availability zones. Three copies on one failed rack are zero copies. Added

Part 3: Sharding

Splitting data across servers

16

Why sharding

In plain wordsA replica set copies data but does not split it: every member holds everything. When data or writes outgrow one machine, sharding splits one collection’s documents across several replica sets.

New words

shardOne replica set holding part of the data.
vertical scalingBuying a bigger machine, which eventually stops being possible.

Sharding distributes one collection's documents across several servers, because one server cannot grow forever.

  • Replication copies, sharding divides. Each shard holds a different part of the data.
  • It scales data size and throughput. More shards means more disks and more primaries taking writes.
  • It is not free. You add routers, metadata servers and one decision you can barely undo: the shard key.
System design insight. Do not shard by reflex. Say “a replica set is enough until data or write volume outgrows one primary; then we shard on X”. Added

Sharded cluster architecture

In plain wordsA sharded cluster has three kinds of parts: routers that apps connect to, shards that hold the data, and config servers that remember which shard holds what.

New words

mongosThe router in front of a sharded cluster.
config serversA small replica set storing the cluster’s map.

Three kinds of component: mongos routers in front, shards holding data, config servers remembering which shard holds what.

LookOne router, three shards that are each a replica set, and a separate replica set of config servers.
StepsThe app sends an operation to mongos. mongos consults the metadata and forwards it to the right shard or shards.
WhyThe app sees one database. Where data lives can change without the app knowing.
RiskA query that mongos cannot aim at one shard goes to all of them.
ComponentJobHolds
mongosStateless front door. Accepts requests and routes each one.Only a cached copy of the routing table.
Config serversStore the sharding configuration. Run as a replica set.Which collections are sharded, shard key ranges (chunks), which shard owns each chunk.
ShardStores a portion of the data. Is itself a replica set.Your documents and indexes.
Key idea: replication within each shard gives availability. Sharding across shards gives horizontal scale. Production uses both.
Name the three kinds of component in a sharded cluster and what each one holds.
mongos routers hold nothing durable, only a cached routing table. Config servers hold the cluster metadata. Shards hold the application data, each as a replica set.

mongos, the query router

In plain wordsApps never talk to shards directly. They talk to mongos, which looks up where the data lives, forwards each request there, and combines answers when several shards reply.

New words

statelessKeeping no data of its own, so any copy can be restarted or added freely.
routing tableThe cached map of which shard owns which data.

mongos is the stateless front door: it knows where data lives, sends each operation there, and merges results when several shards answer.

WhatA lightweight routing process. Applications connect to it as if it were the database.
WhySo application code never needs to know how many shards exist or what is on them.
HowIt reads cluster metadata from the config servers, picks the shard from the shard key in the query, and forwards.
  • Stateless. It stores no data. Lose one and you lose nothing. Guaranteed
  • Run several. Because they hold no state, you add routers freely for capacity and availability.
  • It caches the routing table. It does not ask the config servers on every query; it refreshes when a shard says the cached copy is out of date. Added Simplified
  • It merges. For multi-shard queries it combines, sorts and limits the partial results.
If it breaks: the driver switches to another mongos in its connection string. A cluster with a single mongos has a single point of failure for no reason.

Config servers

In plain wordsConfig servers hold the cluster’s map: which collections are sharded, on which field, and which shard owns each range of values. Routers read and cache this map.

New words

chunkA range of shard-key values; the unit that is moved between shards.
metadataData about the data, such as where each chunk lives.

Config servers store the map of the cluster: which collections are sharded, on what key, and which shard owns each range of that key.

  • A range of shard key values is a chunk. The metadata is a list of chunks and their owners.
  • They run as a replica set (cfg1, cfg2, cfg3) so the map survives a server failure. Guaranteed
  • A background balancer moves chunks between shards to even them out, and updates the map. Added Default · check 11
What happens internally

The metadata lives in a database called config: config.shards, config.collections, config.chunks. Since MongoDB 6.0 the balancer aims for even data size per shard, and the default range size is 128 MB. Added

What is the difference between what config servers store and what shards store?
Config servers store cluster metadata: sharded collections, shard key ranges (chunks) and which shard owns each. Shards store the application's documents.

What exactly is a shard?

In plain wordsEach shard is just a normal replica set, with a primary and secondaries, that happens to hold only part of the collection.

A shard is a replica set that holds one portion of the data.

  • Everything from Part 2 still applies inside each shard: primary, oplog, elections.
  • Three shards of three members is nine data servers. Plus three config servers and at least two mongos.
  • Each shard fails independently. A failover in shard2 does not disturb shard1.

A shard is one server.

In production a shard is a replica set. One server per shard would mean losing part of your data whenever any server fails.

Targeted and scatter-gather reads

In plain wordsIf a query includes the shard key, mongos knows exactly which shard to ask. If not, it must ask every shard and merge the answers, which is much more expensive.

New words

targeted queryA query sent to one shard because it includes the shard key.
scatter-gatherSending a query to every shard and combining the results.

A query that includes the shard key goes to one shard; a query that does not goes to every shard.

  • Targeted cost stays flat as you add shards.
  • Scatter-gather cost grows with the cluster. Every shard does work, and the query is as slow as the slowest shard.
  • mongos must merge. Sorting and limiting across partial results happens on the router.
  • Some scatter is fine. A rare admin report can fan out. Your hottest query must not.

Shard keys

In plain wordsThe shard key is the most important decision in a sharded design. It decides where every document lives, whether load spreads evenly, and which queries can go to a single shard.

New words

cardinalityHow many distinct values a field has.
frequencyHow often the most common value appears.

The shard key is the field (or fields) that decides which shard every document lives on and which queries can be targeted.

High cardinality

Many distinct values, so data can be cut into many chunks.

Even distribution

Values appear with similar frequency, so no shard is overloaded.

Query isolation

Your common queries include it, so they hit one shard.

Write distribution

New writes spread across shards instead of piling onto one.

Stable

Choose a field whose value does not change. A changing key means moving the document.

  • The source calls it effectively immutable. Changing it means migrating data to a new collection.
  • Newer versions soften this. You can add fields to a key (4.4) or reshard a collection online (5.0). It is still slow and expensive, so treat the key as permanent. Added
  • Unique is not enough. A unique, ever-increasing ID has perfect cardinality and terrible write distribution.
Key idea: design the shard key from your query patterns and write pattern first. Everything else follows.
Name four properties of a good shard key.
High cardinality, even distribution, query isolation (common queries include it) and write distribution. A fifth: it should not change.

Hashed sharding

In plain wordsHashed sharding scrambles the key first, so neighbouring values land on different shards. Load spreads evenly, but range queries must ask every shard.

New words

hashA function that turns a value into a number that looks random but is always the same for the same input.

Hashed sharding runs the key through a hash first, so neighbouring values scatter evenly and ranges stop being useful.

sh.shardCollection("app.users", { user_id: "hashed" })
AdvantagesDisadvantages
Even distribution whatever the key pattern.Range queries become scatter-gather.
Safe for monotonically increasing keys (ObjectId, timestamp).Cannot target a range to one shard.

Best for: write-heavy workloads with point queries. An exact-match query on the key is still targeted: mongos hashes the value the same way.

With a hashed shard key on user_id, is find({ user_id: 42 }) targeted? Is find({ user_id: { $gt: 40, $lt: 50 } })?
The exact match is targeted: mongos hashes 42 and finds one shard. The range is scatter-gather, because hashing destroyed the ordering, so values 41 to 49 could be anywhere.

The bucket pattern

In plain wordsStoring every sensor reading as its own document creates millions of tiny documents. The bucket pattern groups readings into one document per time window instead.

Compound indexes and the ESR rule

In plain wordsAn index on several fields is sorted by the first, then the second, and so on. The order you choose matters; the ESR rule says: fields compared for equality first, then the sort field, then range conditions.

New words

compound indexOne index over several fields in a fixed order.
ESREquality, Sort, Range: the recommended field order for compound indexes.

Order the fields of a compound index Equality, then Sort, then Range.

db.orders.find({
  status: "shipped",           // Equality
  total: { $gt: 100 }          // Range
}).sort({ order_date: -1 })    // Sort

db.orders.createIndex({ status: 1, order_date: -1, total: 1 })   // E, S, R
  1. Equality narrows the candidates to one contiguous slice of the index.
  2. Sort comes free: within that slice the entries are already in order, so there is no in-memory sort.
  3. Range filters what is left, entry by entry.
What can go wrong: put the range field before the sort field and the matches come out in total order, not date order. MongoDB then has to sort them in memory.
A query filters status = "shipped" and total > 100, sorted by order_date descending. What compound index, and why that order?
{ status: 1, order_date: -1, total: 1 }. Equality first to jump to one slice, sort second so results come out already ordered, range last to filter within the slice.

Write concern

Journaling

In plain wordsEven one server can keep a write safe from a crash by writing it to its on-disk journal before replying. j: true asks for exactly that.

New words

j: trueAcknowledge only after the write is in the on-disk journal.

j: true adds one more condition: the write must be in the on-disk journal before it is acknowledged.

  { order_id: "123", total: 99 },
  { writeConcern: { w: "majority", j: true } }
)
  • Without it, an acknowledged write may exist only in a server's memory for a moment. A power loss at that moment loses it on that server.
  • With it, the server can replay the journal after a crash and recover the write.
  • With w: "majority", journaling is already on by default. Added Default
What happens internally

The journal is a write-ahead log. The storage engine flushes it to disk roughly every 100 ms; j: true makes the acknowledgement wait for the flush that includes your write. Added Default

Single-document atomicity

Eight mistakes, each with the correction.

Treat MongoDB like SQL: one collection per relational table.

Embed arrays that can grow without limit.

Documents slow down and eventually hit 16 MB. Reference, bucket or use the outlier pattern.

Choose a shard key because it is unique.

Uniqueness gives cardinality only. You also need even distribution, write spread and queries that include it.

Use a monotonically increasing shard key as is.

Every new write lands on one shard. Hash it or lead with a distributed field.

Add an index for every field.

Each index slows every write and uses memory. Index the queries you actually run.

Schema-less means no schema design.

The design work moves from the database to you. Skipping it is the most expensive shortcut.

Use transactions to make up for poor document modelling.

You pay transaction overhead on every request. Put what changes together in one document.

Ignore scatter-gather queries.

They are fine at two shards and painful at twenty. Know which of your queries lack the shard key.
