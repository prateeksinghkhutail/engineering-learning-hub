Part 0: Start here

You do not have to know about monitoring

01

Why do systems need monitoring?

In plain wordsA car has a dashboard. It shows the speed, the fuel and the engine temperature. A warning light comes on when there is a problem. Without the dashboard, you find the problem only when the car stops. Software services must have the same: numbers that show their condition, and warnings before customers see a problem. This is monitoring.

New words

monitoringThe continuous measurement of systems, with warnings to people when a problem occurs.
observabilityHow well you can understand a system from the data that it sends.
metricA number that you measure again and again, for example requests each second.
logA text record of one event, for example one error message.
traceThe path of one request through many services, with times.

Monitoring changes a system into numbers that you can see and use for alerts. Metrics, logs and traces are the three types of data for monitoring. Prometheus is for metrics.

  • Metrics cost little. One counter is one number, for any quantity of requests.
  • Alerts use metrics. “Error rate more than 5% for 5 minutes” is a question about numbers in time.
Which type of data is best for the alert “tell me when more than 5% of requests fail”? Why?
Metrics. Metrics are numbers in time, and Prometheus can calculate and compare them continuously at low cost. Logs and traces are better to find the cause after the alert.

Follow the checkout

Before QuickCart had monitoring, it found failed payments in angry customer emails, hours later. This course shows how to find the 10:07 incident in minutes.

02

What a metric is: numbers in time

In plain wordsRead a thermometer each minute and write down the time and the temperature. The result is a list of pairs. Draw the pairs and the result is a graph. A metric is the same: a number with a name that you record again and again. Each recorded value is a sample. The full list is a time series.

New words

sampleOne measurement: a value at a time.
time seriesA list of samples for one item, in time order.
labelA key–value tag that tells which item a series is about, for example instance="checkout-1".

A metric is a measurement with a name. Each combination of the name and its labels is one time series. A time series is a list of samples, each with a time.

  • Values are numbers (floating point). Text is not possible in a value. Put text in labels or in logs. Guaranteed
  • Labels divide one metric into many series: one series for each instance, status code or path.
A metric has one label, instance. The service has 3 instances. How many time series are there?
Three. There is one series for each different value of the instance label.

Follow the checkout

The checkout service counts all requests that it receives. Prometheus records this count each 15 seconds. This is the metric that we follow.

03

What Prometheus is

In plain wordsPrometheus is a program. Each few seconds, it goes to each of your services and asks for the current numbers. It writes the answers into its database. You can ask questions about the numbers with a query language. Prometheus also examines rules, for example “are errors more than 5%?”. It works like a person who reads the electricity meter in each house. The houses do not send their readings by mail.

New words

scrapeThe action of Prometheus when it reads the current metric values from a service through HTTP.
targetOne endpoint that Prometheus scrapes, for example checkout-1:8080/metrics.
TSDBTime-series database: the storage in Prometheus.
PromQLThe query language of Prometheus.

Prometheus is an open-source monitoring server. It reads metrics from targets through HTTP and keeps them in its time-series database. You query the data with PromQL, and Prometheus examines alert rules.

  • SoundCloud made Prometheus in 2012. It was the second project to complete the Cloud Native Computing Foundation program, after Kubernetes.
  • Prometheus is one program without an external database. It operates correctly on a laptop or on a large server. Guaranteed
  • Its web interface and API use port 9090. Default
Does a service send its metrics to Prometheus, or does Prometheus read them from the service?
Prometheus reads them. On a schedule, it sends an HTTP request to the /metrics endpoint of each target.

Follow the checkout

QuickCart has one Prometheus server, prom-1. It scrapes the three checkout instances each 15 seconds.

In plain wordsThe fastest way to understand Prometheus is to look at it. Start it. Open its /metrics page to see the data that a service shows. Then do one query in its web interface.

New words

/metricsThe HTTP page where a service shows its current metric values as text.
upA metric that Prometheus makes for each target: 1 if the last scrape was correct, 0 if it failed.

The other words, in one diagram

In plain wordsSome helper programs operate around Prometheus. Exporters change the metrics of systems that cannot use the Prometheus format. Alertmanager decides which person to tell. Grafana shows dashboards. This lesson only gives their names. Later parts explain each one.

New words

exporterA small program that reads metrics from a system (a machine, a database) and shows them on /metrics.

alerting ruleA PromQL condition. When it stays true for a time, Prometheus sends an alert.

Part 1: The data model

Series, labels and the four types of metric

06

Time series and labels

In plain wordsIn Prometheus, the metric name and all its labels identify a series. If you change one label value, you have a different series. Thus http_requests_total is not one series. It is a family of series: one for each instance, method, path and status code that occurred.

New words

metric nameThe name of the measurement, for example http_requests_total.
label setAll the key–value labels on a series.
job / instanceTwo labels that Prometheus adds to each series that it scrapes. They tell the group of targets and the one target.

The metric name and the full set of labels identify a time series. Each series is a list of samples. Each sample has a time and a floating-point value.

  • The name is also a label. Prometheus keeps it as the label __name__. Guaranteed
  • Prometheus adds job and instance during the scrape. The values come from the configuration and the target address.
  • A series starts when a label combination occurs for the first time. An example is the first 500 error on POST /checkout.
Are http_requests_total{status="200"} and http_requests_total{status="500"} the same series?
No. A different label value makes a different series. Thus these are two separate lists of samples.

Follow the checkout

Before 10:07, checkout-1 did not return a 500 error on POST /checkout. Thus this series did not exist. The first failed payment started it.

How to read a /metrics page

In plain wordsA service shows its metrics on a simple text page. A line that starts with # describes a metric. Each other line is one series with its current value. Prometheus reads this page at each scrape. It adds the time of the scrape to each value.

New words

exposition formatThe text format of a /metrics page.
# HELP / # TYPEComment lines that give the description and the type of a metric.
OpenMetricsA standard version of the same format.

The exposition format gives the help text and the type of each metric. Then it gives one line for each series, with its labels and current value. Prometheus adds the time when it scrapes the page.

$ curl -s checkout-1:8080/metrics

  • The page does not contain job or instance. Prometheus adds them. Guaranteed
  • A client library writes this page for you. Usually, you do not write it yourself.
Usually, where does the time of a scraped sample come from?
It comes from Prometheus, at the time of the scrape. Usually, the lines on the page contain only labels and a value.

08

Counters

In plain wordsA counter is like the odometer of a car. Its value only increases. The total value (“18,342 requests since the service started”) is usually not important. The important value is the speed of the increase: requests each second. Thus you almost always use counters with rate().

New words

counterA value that only increases. It goes back to zero when the process starts again.
resetThe return of a counter to zero, because its process started again.
_totalThe usual last part of a counter name.

A counter only increases, or it goes back to zero after a restart. Thus you read it through functions such as rate() and increase(). These functions calculate the change each second or in a time period.

  • Use counters for events: requests, errors, bytes that the service sends.
  • Do not use the total value of a counter in an alert. Use its rate.
Why do you almost never draw a graph of the total value of http_requests_total?
The value is a total since the process started. It only increases, and it goes back to zero after a restart. The useful data is the speed of the increase. rate() gives this speed.

Follow the checkout

Our 500 counter changed from 0 to 37 to 121 in two minutes. This is approximately 1.4 failures each second. Part 4 does the full calculation.

09

Gauges

In plain wordsA gauge is like a speedometer or a thermometer. Its value increases and decreases. The current value is the important value. Examples are memory in use, requests in progress, queue length and temperature.

New words

gaugeA value that can increase and decrease. You read it as it is.

A gauge shows a current level that can increase and decrease. You use its value directly in graphs and alerts, frequently with avg, max or min over a time period.

  • Do not use rate() on a gauge. To find its change, use deriv() or delta().
  • Prometheus reads a gauge each 15 s. Thus it can miss short peaks between scrapes. Simplified
Is “quantity of items in the job queue” a counter or a gauge?
It is a gauge, because the queue length increases and decreases. “Jobs completed in total” is a counter.

10

Histograms

In plain wordsYou want to know how slow requests are. An average hides the very slow requests. A histogram puts each request into a bucket by its duration: less than 0.1 s, less than 0.25 s, less than 0.5 s, and more. It counts the requests in each bucket. From these counts, you can calculate an approximate value for “95% of requests were faster than X”.

New words

histogramA metric that counts observations into buckets by their value.
bucketA counter of the observations that are equal to or less than a limit. You write it as le="0.5" (less than or equal).
quantile / percentileThe value that a given part of the observations is below. p95 means that 95% are faster.

A histogram shows cumulative bucket counters with le labels, and also a _sum and a _count. With these, PromQL can calculate rates, averages and approximate percentiles across many instances.

# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{path="/checkout",le="0.1"}   14210
http_request_duration_seconds_bucket{path="/checkout",le="0.25"}  17520
http_request_duration_seconds_bucket{path="/checkout",le="0.5"}   18010
http_request_duration_seconds_bucket{path="/checkout",le="1"}     18190
http_request_duration_seconds_bucket{path="/checkout",le="2.5"}   18290
http_request_duration_seconds_bucket{path="/checkout",le="+Inf"}  18379
http_request_duration_seconds_sum{path="/checkout"}   2861.4
http_request_duration_seconds_count{path="/checkout"} 18379
  • Buckets are cumulative. Guaranteed
  • Average latency = _sum ÷ _count. Here, 2861.4 ÷ 18379 ≈ 0.156 s (we calculated this value).
  • Select bucket limits near your target. Prometheus calculates a percentile inside one bucket, thus the result is approximate. The default limits of client libraries go from .005 to 10 seconds.
  • Native histograms are a newer type. They select their buckets automatically and are much more accurate. Simplified
For latency, why is a histogram better than an average?
An average hides the slow requests. Some requests of 3 seconds change the average very little. With histogram buckets, you can calculate percentiles such as p95 and p99. These show the experience of the users with the slowest requests.

Follow the checkout

After 10:07, the 2.5 s bucket and the +Inf bucket increase fastest. These are payments that wait for the timeout of the provider. 89 requests took more than 2.5 s (18379 − 18290, calculated).

11

Summaries, and why histograms are usually better

In plain wordsA summary calculates percentiles inside the service and shows the results. This looks easy, but you cannot add percentiles. The p95 of three servers is not the average of their three p95 values. A histogram shows the bucket counts. You can add these counts across servers and then calculate a correct percentile for all servers.

New words

summaryA metric. Its client library calculates the quantiles in the service.
aggregateTo combine values from many series, for example to add them.

A summary calculates exact quantiles for each instance, but you cannot combine them across instances. You can combine histograms. Thus histograms are the usual selection.

HistogramSummary
Where the calculation of quantiles occursIn Prometheus (PromQL)In the service
Combine across instancesYesNo

Three servers each show a p99 latency. Can you calculate their average to find the p99 of the full service?
No. You cannot calculate an average of quantiles. The result changes with the quantity of requests on each server and with their distribution. Add the histogram buckets across the servers, then calculate the quantile.

12

Cardinality: the quantity of series

In plain wordsEach new combination of label values makes a new series. Each series uses memory and disk. A label with few values is satisfactory. A label with a value for each user, order or request ID can make millions of series. Prometheus can then stop. This is the most frequent cause of a Prometheus failure.

New words

cardinalityThe quantity of different series in a metric or in a full server.
active seriesSeries that received a sample a short time ago. Prometheus keeps them in memory.
unbounded labelA label with a quantity of values that always increases, for example user_id.

The series count of a metric is the product of the counts of different values of its labels. Thus one label with very many values, for example a user ID, can increase memory use by 1000 times or more.

Try it: how many series does http_requests_total make?

This is the worst case: all combinations occur. The memory value uses approximately 4 KB for each active series. Simplified

  • Do not put IDs, email addresses, URLs with parameters or times in labels. Put them in logs or traces.
  • Find the largest metrics on the TSDB status page (/tsdb-status). Guaranteed · check 4
Why is a user_id label on http_requests_total dangerous?
Each user makes new series for each combination of the other labels. Thus the series count increases with the quantity of users, possibly to millions. Prometheus can use all its memory, and queries become slow.

Follow the checkout

Names for metrics and labels

In plain wordsGood names make queries easy to read. They also prevent errors, for example a mix of milliseconds and seconds. Prometheus has simple rules. Say what the metric measures. Put the unit at the end, in base units. Put _total at the end of counter names.

New words

base unitSeconds, bytes, and ratios from 0 to 1. Do not use milliseconds or kilobytes.
namespace prefixThe first word of a name. It tells the system that the metric comes from, for example checkout_ or node_.

Metric names use snake_case with a namespace prefix and a base unit at the end. Counter names end with _total. Labels show dimensions, and each label has a small, fixed set of values.

GoodDo not useWhy
http_request_duration_secondshttp_latency_msBase unit, and it tells the type of duration
node_memory_used_bytesmem_used_mbBytes, with a namespace
http_requests_total{status="500"}http_500_errors_totalStatus is a dimension. Thus it is a label, not part of the name
Must failed payments and correct payments be two metrics, or one metric with a label?
Use one metric with a label, for example result="failed" / "succeeded". Then you can add them to find the total. You can also divide one by the total to find the failure ratio.

Part 2: Collection of metrics

Scrapes, discovery, exporters

14

The pull model and the scrape loop

In plain wordsPrometheus has a list of targets. It goes to each target on a fixed schedule, for example each 15 seconds. Prometheus starts each scrape. Thus it always knows when a target stops. The scrape fails and up changes to 0. The targets do not have to know about Prometheus.

New words

scrape intervalThe time between two scrapes of a target.
scrape timeoutThe maximum time for one scrape. After this time, the scrape fails.
pull vs pushPull: the server reads the data. Push: the clients send the data.

Prometheus scrapes the /metrics endpoint of each target at a fixed interval. It records the result of each scrape in up. It keeps each line with the time of the scrape.

# prometheus.yml
global:
  scrape_interval: 15s          # stock default is 1m
  evaluation_interval: 15s      # how often rules run; stock default 1m
scrape_configs:
  - job_name: checkout
    static_configs:
      - targets: ['checkout-1:8080', 'checkout-2:8080', 'checkout-3:8080']
  • Standard settings: a scrape each 1 minute, a timeout after 10 seconds, and rule examination each 1 minute. Default · check 1
  • With pull, you receive health data at no cost. Prometheus finds a stopped target at the next scrape. Guaranteed
  • Prometheus also records these values for each scrape: scrape_duration_seconds and scrape_samples_scraped.
Why is it easy to find a stopped service with the pull model?
Prometheus starts each scrape. Thus the next scrape of a stopped service fails, and up changes to 0. With push, no data can mean “stopped” or “no data to send”.

How to find targets: service discovery

In plain wordsYou can write the address of each server in a file when you have three servers. You cannot do this for three hundred containers that start and stop each hour. Service discovery asks a different system for the current list of targets. This system can be Kubernetes, AWS, Consul or a file that your tools write. Service discovery updates the list automatically.

New words

service discoveryA method to receive the list of targets from a different system. You do not write the list yourself.
static configA fixed list of targets that a person writes.
meta labelsTemporary labels from discovery, for example __meta_kubernetes_pod_name. You use them for relabeling.

Service discovery methods such as Kubernetes, EC2, Consul and file discovery keep the target list current. They add metadata labels. You can use these labels to filter targets and to give labels to targets.

scrape_configs:
  - job_name: checkout
    kubernetes_sd_configs:
      - role: pod                    # ask the Kubernetes API for pods
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_label_app]
        regex: checkout
        action: keep                 # only pods labelled app=checkout
  • Prometheus has many discovery methods: Kubernetes, EC2, Azure, GCE, Consul, DNS, file, HTTP and more.
  • Meta labels go away after relabeling. To keep their values, copy them into usual labels. Guaranteed
Why is a static configuration not good for containers on Kubernetes?
Kubernetes starts and removes pods frequently, and their addresses change. Service discovery asks the Kubernetes API for the current pods. Thus the targets stay correct, and you do not edit the configuration.

Follow the checkout

Relabeling

In plain wordsRelabeling is a small language of rules that change labels. Before a scrape, you can remove targets that you do not want. You can also change discovery metadata into useful labels. After a scrape, you can remove unwanted metrics or labels, before Prometheus keeps them.

New words

relabel_configsRules that Prometheus applies to targets before the scrape.
metric_relabel_configsRules that Prometheus applies to the scraped series before it keeps them.
actionThe function of a rule: keep, drop, replace, labelmap, labeldrop, hashmod and more.

relabel_configs change or filter targets before a scrape. metric_relabel_configs change or filter samples after the scrape. With these rules, you control the labels and decrease the cardinality.

relabel_configs:
  - source_labels: [__meta_kubernetes_namespace]
    target_label: namespace                    # copy metadata into a real label
metric_relabel_configs:
  - source_labels: [__name__]
    regex: 'go_gc_.*'
    action: drop                               # throw away noisy runtime metrics
A target shows thousands of series that you do not use. Which configuration can remove them, and when does it operate?
Use metric_relabel_configs with the action drop. It operates after the scrape and before storage. Thus Prometheus does not keep the series that you do not want.

Exporters and instrumentation

In plain wordsThere are two methods to make metrics. For your own code, you add a client library and count events where they occur. For example, one line counts each request, and a timer measures each payment call. For software that you cannot change, for example Linux or MySQL, you operate an exporter near it. The exporter reads the statistics of the software and shows them in the Prometheus format.

New words

client libraryThe Prometheus library for your language (Go, Java, Python and more). It makes metrics and shows the /metrics page.
node_exporterThe standard exporter for machine metrics: CPU, memory, disk, network.
blackbox_exporterAn exporter that tests endpoints from outside (HTTP, TCP, ping).

You add client libraries to your own services. For systems from other companies, you use exporters such as node_exporter. Exporters change the statistics of these systems into the Prometheus format.

# Python: instrumenting the checkout handler
from prometheus_client import Counter, Histogram, start_http_server
REQUESTS = Counter('http_requests_total', 'Total HTTP requests.', ['method', 'path', 'status'])
LATENCY  = Histogram('http_request_duration_seconds', 'Request duration.', ['path'])

def checkout(request):
    with LATENCY.labels(path='/checkout').time():
        status = handle(request)
    REQUESTS.labels(method='POST', path='/checkout', status=str(status)).inc()

start_http_server(8080)     # serves /metrics
  • node_exporter uses port 9100. Default
  • There are hundreds of exporters: for databases, queues, proxies, hardware and cloud services.
You want metrics from a PostgreSQL database that you cannot change. Do you use instrumentation or an exporter?
Use an exporter (postgres_exporter). It connects to the database and reads its statistics. Then it shows them on /metrics, and Prometheus scrapes them.

Follow the checkout

Short jobs and the Pushgateway

In plain wordsA batch job can operate each night for 30 seconds and then stop. Prometheus possibly does not scrape it in that time. The Pushgateway is a small service that operates continuously. The job sends its last values to the Pushgateway, and Prometheus scrapes the Pushgateway. Use it only for batch jobs. Do not use it to monitor usual services.

New words

PushgatewayA service that holds metrics from short jobs until Prometheus scrapes them.
batch jobA program that starts, does a task, and stops.

With the Pushgateway, short batch jobs can send their metrics, and Prometheus scrapes them later. It is for batch jobs at the service level, not for services that operate continuously.

  • The Pushgateway does not forget. A job that stopped still shows its last push. Thus make alerts on a “last success” time. Guaranteed
  • It is a single point of failure for all jobs that send to it. Also, you do not receive the automatic up health signal.
Why must a web service that operates continuously not send its metrics to the Pushgateway?
Prometheus does not receive the health of each instance (up). Old values stay after the service stops. The Pushgateway also becomes a bottleneck. Prometheus must scrape these services directly.

Follow the checkout

The payout job of QuickCart operates each night and sends payout_last_success_timestamp_seconds. Prometheus scrapes the checkout service directly.

Part 3: Storage

The time-series database in Prometheus

19

Inside the TSDB

In plain wordsPrometheus first writes new samples to memory. It also writes them to a log on the disk, thus Prometheus does not lose data if it stops suddenly. Each two hours, Prometheus puts the samples of the last two hours into a small block on the disk. You cannot change this block. Later, Prometheus combines small blocks into larger blocks. When a block is older than the retention period, Prometheus deletes it.

New words

head blockThe part in memory that holds the newest samples.
WALWrite-ahead log. Prometheus first writes each sample here. After a crash, Prometheus makes the head again from the WAL.
blockA directory of compressed samples for a time range (2 hours at the start). You cannot change it.
compactionThe combination of smaller blocks into larger blocks.

The newest samples are in the head in memory, and a write-ahead log protects them. Each two hours, Prometheus cuts them into blocks on the disk that do not change. Compaction combines these blocks later, and retention deletes them.

  • Each sample becomes approximately 1–2 bytes after compression. For compression, Prometheus uses the delta method for times and the XOR method for values (the “Gorilla” method). Simplified
  • Blocks do not change. To delete old data, Prometheus removes full directories. This costs little.
  • One server, local disk. Prometheus does not copy its data to other servers. Part 6 tells you what to do about this. Guaranteed
Prometheus stops suddenly. How does it recover the samples that were only in memory?
When it starts again, it reads the write-ahead log. This log contains each sample that Prometheus added to the head block.

Follow the checkout

Our 10:07 samples stay in the head. Some minutes after 12:00, prom-1 cuts the 10:00–12:00 block. Simplified

Retention and disk size

In plain wordsPrometheus keeps data for a set time, then deletes it. The default time is 15 days. The disk size that you must have is a simple calculation. Multiply the samples each second by the bytes for each sample. Then multiply by the number of seconds that you keep the data.

New words

retentionThe time that Prometheus keeps data before it deletes the data.
ingestion rateThe samples that Prometheus keeps each second: active series ÷ scrape interval.

Necessary disk ≈ retention seconds × samples each second × bytes for each sample. Samples each second ≈ active series ÷ scrape interval.

  • You can also set a size limit. When the data is at one of the two limits, Prometheus deletes the oldest blocks first.
  • Do you have to keep data for months or years? Send the data to long-term storage (Part 6). Do not make one server larger.

The disk use becomes approximately two times larger, because each series makes two times more samples each second.

Staleness and missing data

In plain wordsSamples come each 15 seconds, but a query can ask about any time. Prometheus gives the newest sample that is not older than 5 minutes. When a target goes away, Prometheus writes a special “stale” marker. Thus the series stops at once. It does not stay for 5 more minutes.

New words

lookback deltaThe maximum age of the newest sample that a query uses: 5 minutes by default.
stale markerA special sample that means “this series stopped”.

An instant query gives the newest sample of each series inside the 5-minute lookback window. A stale marker stops a series immediately when its target or the series goes away.

  • The lookback is 5 minutes. Default
  • Missing data is not zero. For an alert on a series that went away, use absent() or an alert on up == 0.
Kubernetes deletes a checkout pod. Why do queries stop to show its series almost immediately, and not after 5 minutes?
When the target goes away, Prometheus writes stale markers for its series. Thus queries know at once that the series stopped. They do not use the last sample for the full 5-minute lookback.

How to select series

In plain wordsThe simplest query is only a metric name. It gives all series with that name. Curly brackets select series by their labels, almost like a WHERE clause. You can use an exact value, remove a value, or use a pattern.

New words

instant vectorA set of series with one sample each, at one time.
label matcherA condition on a label: =, !=, =~ (regex), !~ (not regex).
regexA text pattern, for example 5.. for each code of three characters that starts with 5.

A selector gives a metric name and filters its series with label matchers. The result is an instant vector: the newest sample of each series that agrees with the matchers.

http_requests_total                                         # every series of the metric
http_requests_total{job="checkout"}                         # exact match
http_requests_total{job="checkout", status=~"5.."}          # regex: any 5xx
http_requests_total{job="checkout", path!="/health"}        # exclude a path
Which series does the matcher status=~"5.." select?
It selects the series with a status label of three characters that starts with 5 (500, 502, 503 and more). A Prometheus regex must agree with the full value.

Range vectors and rate()

In plain wordsThe value of a counter only tells you a total. rate() examines the samples in a time window, for example the last 5 minutes. It calculates how fast the counter increased, each second. It also sees when a counter went back to zero because the service started again. It counts this as a reset, not as negative traffic.

New words

range vectorFor each series, all samples in a time window: [5m].
rate()The average increase of a counter each second in the window. It corrects for resets.
increase()The total increase in the window (rate × window length).
irate()The increase each second from only the last two samples. It changes quickly and is for fast graphs.

rate(counter[5m]) changes a counter into an average rate each second over the last five minutes. It corrects for counter resets. Almost all useful queries use it.

Try it: calculate rate() over 2 minutes of samples

The reset correction is real. The real rate() also extrapolates a small quantity to the edges of the window. This demo does not do that. Simplified

rate(http_requests_total{job="checkout", status=~"5.."}[5m])        # failures per second
increase(http_requests_total{job="checkout", status=~"5.."}[1h])    # failures in the last hour
  • Always use rate() first and sum second. Do not sum first and then use rate(). A reset on one instance makes the total incorrect. Guaranteed · check 8
  • Make the window a minimum of 4 × the scrape interval. Then it always holds sufficient samples: [1m] or more at 15 s. Simplified
A counter shows 100, 150, 20 and 60 in four samples, because the process started again. Which increase does rate() use?
90. First +50 (100→150). Then a reset, which counts as +20 (from 0 to 20). Then +40 (20→60). A simple “last minus first” gives −40.

Aggregation: sum, avg, topk and more

In plain wordsUsually, you do not want one line for each instance, method and status. You want one number for each service, or one line for each status code. Aggregation operators add series, calculate their average or put them in order. They keep only the labels that you name.

New words

by (…)Keep these labels in the result. Combine across all other labels.
without (…)Remove these labels. Keep all other labels.
topkThe k series with the highest values.

Aggregation operators such as sum, avg, max, count and topk combine series. The words by and without tell which labels stay in the result.

sum(rate(http_requests_total{job="checkout"}[5m]))                       # total requests/s
sum by (status) (rate(http_requests_total{job="checkout"}[5m]))           # one line per status
sum by (instance) (rate(http_requests_total{job="checkout",status=~"5.."}[5m]))
topk(3, sum by (path) (rate(http_requests_total[5m])))                    # 3 busiest paths
What is the difference between sum by (instance) and sum without (instance)?
The query sum by (instance) keeps only the instance label and adds all other labels together. The query sum without (instance) removes the instance label, keeps all other labels, and adds across instances.

Percentiles with histogram_quantile()

In plain wordsTo find the 95th-percentile latency, do these steps. Calculate the rate of each histogram bucket. Add the buckets across instances. Then ask PromQL for the duration that 95% of requests were less than. PromQL finds the bucket that contains the 95% point. It thinks that the requests in that bucket have an equal distribution.

New words

histogram_quantile()Calculates an approximate quantile from the rates of histogram buckets.
leThe label for the upper limit of the bucket (“less than or equal”).
linear interpolationThe assumption that values have an equal distribution between the lower and upper limit of a bucket.

histogram_quantile(φ, sum by (le) (rate(…_bucket[5m]))) calculates an approximate latency percentile from bucket rates. It uses linear interpolation inside the bucket that contains the percentile.

Try it: calculate a percentile from buckets

This demo uses the same algorithm as Prometheus: it finds the bucket and uses linear interpolation inside it. We made the bucket rates for the example. Guaranteed · check 5

histogram_quantile(0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="checkout", path="/checkout"}[5m])))
  • Keep the le label when you combine series. Without it, no buckets stay for the calculation.
  • The accuracy of the result is the same as the accuracy of the buckets. If p95 is in the 1–2.5 s bucket, the true value can be at any point in that range.
When you combine instances, why must you write sum by (le) inside histogram_quantile?
histogram_quantile must have the bucket limits. These limits are the le label. The expression sum by (le) adds each bucket across instances and keeps the buckets separate.

Ratios and vector matching

In plain wordsThe most useful numbers for alerts are ratios: failures divided by all requests. PromQL can do arithmetic between two sets of series. It makes pairs of series that have the same labels. When the label sets are different, you tell PromQL which labels to use for the pairs.

New words

binary operatorArithmetic or a comparison between two values or vectors: + − * / > < ==.
vector matchingThe method that makes pairs of series from the two sides of an operator, by their labels.
on / ignoringUse only these labels for the pairs / use all labels but these.
group_leftLet many series on the left agree with one series on the right.

Binary operators combine vectors. They make pairs of series that have the same labels. When the label sets are different, the keywords on, ignoring and group_left control the pairs.

# error ratio of the whole service
  sum(rate(http_requests_total{job="checkout", status=~"5.."}[5m]))
/ sum(rate(http_requests_total{job="checkout"}[5m]))

# per instance: both sides keep the instance label, so they pair up
  sum by (instance) (rate(http_requests_total{job="checkout", status=~"5.."}[5m]))
/ sum by (instance) (rate(http_requests_total{job="checkout"}[5m]))

# comparison as a filter: only return instances above 5%
(…the ratio above…) > 0.05
Why does a comparison such as ratio > 0.05 give fewer series, and not true/false values?
In PromQL, a comparison is a filter by default. It removes the series that do not agree with the condition. The other series keep their values. To receive 0/1 values, add the bool modifier.

Recording rules

In plain wordsSome queries use much CPU, and dashboards and alerts do them again and again. A recording rule does a query on a schedule. It keeps the result as a new series that costs little to read. Dashboards then read this calculated series. They do not calculate from the raw data each time.

New words

recording ruleA query that Prometheus calculates at regular intervals and keeps as a new series.
rule groupRules that Prometheus calculates together, in sequence, at the same interval.

Recording rules calculate expressions that are expensive or frequent at each evaluation interval. They keep the results as new series. The names of these series use the rule level:metric:operations.

# rules/checkout.yml
groups:
  - name: checkout
    rules:
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))
      - record: job:http_errors:ratio_rate5m
        expr: |
          sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
          / sum by (job) (rate(http_requests_total[5m]))
What does the name job:http_errors:ratio_rate5m tell you?
The name rule tells you three items. The query combines the data to the job level. It is about HTTP errors. It is a ratio of 5-minute rates.

What to measure: golden signals, RED and USE

In plain wordsYou can measure a thousand values. Three known checklists tell you the few values that are most important. For a service that receives requests, measure the quantity, the failures and the duration (RED). For a resource such as a disk or a CPU, measure the use, the overload and the errors (USE). The “four golden signals” of Google combine the two.

New words

REDRate, Errors, Duration: the most important metrics for a service that receives requests.
USEUtilization, Saturation, Errors: the most important metrics for a resource.
golden signalsLatency, traffic, errors, saturation.
saturationThe quantity of work that waits because a resource is full.

RED (rate, errors, duration) is for services. USE (utilization, saturation, errors) is for resources. The four golden signals combine them and tell you what to put on each dashboard.

Alerting rules

In plain wordsAn alerting rule is a PromQL condition with a wait time. Prometheus examines it at each evaluation interval. When the condition becomes true, the alert is “pending”. If the condition stays true for the full wait time, the alert becomes “firing”. Then Prometheus sends it to Alertmanager. A short problem does not cause a page.

New words

forThe time that a condition must stay true before the alert fires.
pending / firingPending: the condition is true, and the alert waits. Firing: the condition was true for sufficient time, and Prometheus sends the alert.
annotationsText for persons on an alert: summary, description, runbook link.

An alerting rule fires when its expression gives results continuously for the for duration. The alert goes from inactive to pending to firing. While it is firing, Prometheus sends it to Alertmanager.

groups:
  - name: checkout-alerts
    rules:
      - alert: CheckoutHighErrorRate
        expr: job:http_errors:ratio_rate5m{job="checkout"} > 0.05
        for: 5m
        labels:
          severity: page
          team: payments
        annotations:
          summary: "Checkout errors at {{ $value | humanizePercentage }}"
          runbook_url: "https://wiki.quickcart.example/runbooks/checkout-errors"

Try it: when does the alert fire?

Here, Prometheus examines the rule one time each minute, to make the demo clear. QuickCart examines it each 15 s. Simplified

  • States: inactive → pending → firing. Guaranteed · check 6
  • The for clause makes alerts slower but more stable. A longer wait gives fewer incorrect pages, but real pages come later.
A rule has for: 5m. The condition is true from 10:07, and Prometheus examines it each 15 s. At approximately which time does the alert fire?
At approximately 10:12, when the condition was true continuously for 5 minutes. Before that time, the alert is pending.

Alertmanager: grouping, routing, silencing

In plain wordsPrometheus only says “this alert is firing”. Alertmanager decides what persons receive. It puts related alerts into one message. It sends each message to the pager or chat of the correct team. It stops alerts that a larger alert explains. It also stops messages during planned maintenance.

New words

groupingThe combination of alerts with the same selected labels into one notification.
route / receiverRoute: the tree of rules that selects a destination. Receiver: the destination (pager, Slack, email).
inhibitionAlertmanager stops some alerts while a more important alert is firing.
silenceA temporary stop for alerts with given labels.

Alertmanager removes duplicate alerts from Prometheus. It also groups, routes, inhibits and silences alerts. It sends notifications to receivers such as pagers and chat.

# alertmanager.yml
route:
  receiver: checkout-chat
  group_by: ['alertname', 'job']
  group_wait: 30s          # wait to batch the first notification
  group_interval: 5m       # wait before notifying about changes in a group
  repeat_interval: 4h      # re-send while still firing
  routes:
    - matchers: [ 'severity="page"' ]
      receiver: oncall-pager
inhibit_rules:
  - source_matchers: [ 'alertname="CheckoutDown"' ]
    target_matchers: [ 'alertname="CheckoutHighErrorRate"' ]
    equal: ['job']
  • Standard timers: group_wait 30 s, group_interval 5 m, repeat_interval 4 h. Default · check 7
  • Alertmanager uses port 9093. Many Alertmanagers can make a cluster that removes duplicate notifications. Default
The database stops, and fifty services start to send error alerts. Which Alertmanager functions prevent fifty pages?
Grouping (by alertname or cluster) and inhibition. A “database down” alert can inhibit the error alerts of the services that use the database. Thus the on-call engineer sees the root cause, not fifty symptoms.

Good alerts, SLOs and burn rates

In plain wordsAn alert must mean “a person must act now”. Send a page for problems that users see (errors, slow responses). Do not send a page for each internal cause (high CPU). A service level objective tells the minimum good level, for example 99.9% correct checkouts each month. The best alerts fire when you use this small quantity of permitted failures too quickly.

New words

SLIService level indicator: the measured number, for example the success ratio.
SLOService level objective: the target for the SLI, for example 99.9% in 30 days.
error budgetThe failures that the SLO permits: 0.1% of requests for a 99.9% SLO.
burn rateThe speed at which you use the error budget, compared with “exactly on budget”.

Good alerts send pages for symptoms that users see, and they connect to service level objectives. Burn-rate alerts fire when you use the error budget so quickly that it is important.

Why send a page for the checkout error ratio and not for high CPU?
Users see the error ratio, and it always makes an action necessary. High CPU can be safe (the service still answers correctly). A page for it can call persons for no reason.

High availability

In plain wordsOne Prometheus is a single point of failure. If it stops, no person receives alerts. The simple solution is two identical copies. They scrape the same targets and examine the same rules. Both send alerts to a cluster of Alertmanagers. The cluster makes sure that each alert goes out only one time.

New words

HA pairTwo identical Prometheus servers that scrape the same targets.
deduplicationThe same alert from the two servers becomes only one notification.
gossipThe method that the members of an Alertmanager cluster use to share their state.

For high availability, you operate identical Prometheus replicas. Each replica scrapes and sends alerts independently. A cluster of Alertmanagers removes the duplicate notifications.

  • The data of the two copies is not exactly the same. Their scrapes occur at slightly different times. Dashboards use one copy, or a query layer combines the two (see the next lessons).
  • Connect Prometheus to all Alertmanagers, not to a load balancer. Then deduplication operates correctly. Simplified
Two Prometheus servers find CheckoutHighErrorRate. Why does Sam receive one page, not two?
Both servers send the alert to the Alertmanager cluster. The cluster sees that the two alerts are the same, because they have the same labels. The members share their state by gossip and send one notification.

Federation

In plain wordsA large company operates one Prometheus for each cluster or region, near its targets. To see the full system, a global Prometheus can scrape a summary from each of these servers. Usually, the summary is only the calculated recording rules, not each raw series.

New words

federationOne Prometheus scrapes selected series from other servers through their /federate endpoint.
hierarchicalIn levels: local servers below, a global server above.

With federation, a Prometheus at a higher level scrapes selected series from servers at a lower level through /federate. Usually, these series come from recording rules that combine data.

scrape_configs:
  - job_name: federate
    honor_labels: true
    metrics_path: /federate
    params:
      'match[]': ['{__name__=~"job:.*"}']     # only recording-rule aggregates
    static_configs:
      - targets: ['prom-eu:9090', 'prom-us:9090']
Why do you federate only recording-rule series, and not all series?
If one global server collects all raw series, it has the same limits as one single server. Federation must prevent these limits. Aggregates are small, and they are sufficient for a global view.

In plain wordsOne Prometheus keeps two weeks of data on one disk. You can want one year of history, one location to query all clusters, and protection if a disk fails. These systems keep the data in object storage that costs little.

global viewThe metrics of all clusters in one location for queries.

remote_write sends samples to long-term stores that scale horizontally, such as Thanos, Mimir, Cortex or VictoriaMetrics. These stores add long retention, a global query view, and deduplication of HA pairs.

Why add a long-term store, and not set the Prometheus retention to one year?

Write the PromQL for the error ratio of the checkout service over 5 minutes.
sum(rate(http_requests_total{job="checkout", status=~"5.."}[5m])) / sum(rate(http_requests_total{job="checkout"}[5m]))
Why does an alert with for: 5m not send a page for a peak of one minute?
The condition must stay true continuously for 5 minutes. A peak of one minute only makes the alert pending. When the condition stops, the alert goes back to inactive.
What are the two main risks of one single Prometheus, and the usual solutions?
First, it is a single point of failure for alerts. The solution is an HA pair and an Alertmanager cluster. Second, it keeps limited history on one disk. The solution is remote write to a long-term store such as Thanos or Mimir.
