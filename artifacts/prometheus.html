Part 0: Start here

No monitoring knowledge needed

01

Why monitor at all?

In plain wordsA car has a dashboard: speed, fuel, engine temperature, and a warning light when something is wrong. Without it you would only find out about trouble when the car stops. Software services need the same: numbers that show how they are doing, and warnings before customers notice. That is monitoring.

New words

monitoringContinuously measuring how systems behave, and warning people when something is wrong.
observabilityHow well you can understand what a system is doing from the data it emits.
metricA number measured over time, such as requests per second.
logA text record of one event, such as one error message.
traceThe path of one request through several services, with timings.

Monitoring turns a running system into numbers you can watch and alert on; metrics, logs and traces are the three kinds of data used for it, and Prometheus handles metrics.

  • Metrics are cheap: a counter is a single number however many requests it counts.
  • Alerts need metrics: “error rate above 5% for 5 minutes” is a question about numbers over time.
Which of the three (metrics, logs, traces) is best for “alert me when more than 5% of requests fail”, and why?
Metrics: they are numbers over time that can be computed and compared cheaply and continuously. Logs and traces are better for investigating why, after the alert fires.

Follow the checkout

Without monitoring, QuickCart learned about failed payments from angry customer emails, hours later. This course is about catching the 10:07 incident within minutes.

02

What a metric is: numbers over time

In plain wordsA thermometer read every minute gives a list of (time, temperature) pairs. Draw them and you have a graph. A metric is exactly that: a named number recorded again and again. Each recorded value is a sample, and the whole list is a time series.

New words

sampleOne measurement: a value at a timestamp.
time seriesA list of samples for one thing over time.
labelA key–value tag that says which thing a series is about, such as instance="checkout-1".

A metric is a named measurement; each combination of the name and its labels is one time series, a list of timestamped samples.

  • Values are numbers (floating point). No text: text belongs in labels or logs. Guaranteed
  • Labels split one metric into many series: per instance, per status code, per path.
A metric has one label, instance, and runs on 3 instances. How many time series is that?
Three: one per distinct value of the instance label.

Follow the checkout

The checkout service counts every request it handles. That running count, recorded every 15 seconds, is the metric we follow.

03

What Prometheus is

In plain wordsPrometheus is a program that, every few seconds, visits each of your services and asks “what are your numbers right now?”. It writes the answers into its own database, lets you ask questions about them in a query language, and checks rules you write, such as “are errors above 5%?”. Like a meter reader who walks round every house, instead of each house mailing in its reading.

New words

scrapePrometheus fetching the current metric values from a service over HTTP.
targetOne endpoint Prometheus scrapes, such as checkout-1:8080/metrics.
TSDBTime-series database: Prometheus’s built-in storage.
PromQLPrometheus’s query language.

Prometheus is an open-source monitoring server that pulls metrics from targets over HTTP, stores them in its own time-series database, queries them with PromQL and evaluates alerting rules.

  • Born at SoundCloud in 2012, the second project to graduate in the Cloud Native Computing Foundation, after Kubernetes.
  • One binary, no external database. It runs fine on a laptop or a large server. Guaranteed
  • Listens on port 9090 for its web UI and API. Default
Does a service send its metrics to Prometheus, or does Prometheus fetch them?
Prometheus fetches them (pulls), by sending an HTTP request to each target’s /metrics endpoint on a schedule.

Follow the checkout

QuickCart runs one Prometheus server, prom-1, that scrapes the three checkout instances every 15 seconds.

Your first metrics, hands on

In plain wordsThe quickest way to understand Prometheus is to look at it. Start it, open its own /metrics page to see what a service exposes, then run one query in its web UI.

New words

/metricsThe HTTP page where a service lists its current metric values as text.
upA metric Prometheus creates per target: 1 if the last scrape worked, 0 if not.

The rest of the vocabulary, in one picture

In plain wordsAround Prometheus are a few helpers. Exporters translate metrics from systems that cannot speak Prometheus. Alertmanager decides who to notify. Grafana draws dashboards. This lesson only names them; later parts explain each.

New words

exporterA small program that reads metrics from something (a machine, a database) and exposes them on /metrics.
instrumentationCode inside your own service that counts and times things.
alerting ruleA PromQL condition that, when true long enough, sends an alert.
AlertmanagerThe separate service that groups alerts and sends notifications.

Exporters and instrumented services expose metrics, Prometheus scrapes and evaluates rules, Alertmanager notifies people, and Grafana shows dashboards.

Who sends the page to the on-call engineer: Prometheus or Alertmanager?

Part 1: The data model

Series, labels and the four metric types

06

Time series and labels

In plain wordsIn Prometheus a series is identified by its metric name plus every label on it. Change any label value and it is a different series. So http_requests_total is not one series but a family: one per instance, per method, per path, per status code that has actually happened.

New words

metric nameWhat is measured, such as http_requests_total.
label setAll the key–value labels on a series.
job / instanceLabels Prometheus adds to every scraped series: which group of targets and which single target.

A time series is identified by its metric name together with its full set of labels, and each series is a stream of (timestamp, float) samples.

  • The name is just a label too: internally it is stored as __name__. Guaranteed
  • job and instance are added at scrape time from the configuration and the target address.
  • A series is created the first time a label combination appears, for example the first 500 on POST /checkout.
Are http_requests_total{status="200"} and http_requests_total{status="500"} the same series?
No. Any difference in label values makes a different series, so they are two separate streams of samples.

Follow the checkout

Before 10:07, checkout-1 had never returned a 500 on POST /checkout, so this series did not exist. The first failed payment created it.

07

Reading a /metrics page

In plain wordsA service shows its metrics as a simple text page. Lines starting with # describe the metric; every other line is one series and its current value. Prometheus reads this page on every scrape and stamps each value with the time it read it.

New words

exposition formatThe text format of a /metrics page.
# HELP / # TYPEComment lines giving a metric’s description and its type.
OpenMetricsA standardised version of the same format.

The exposition format lists each metric’s help text and type, then one line per series with its labels and current value; Prometheus adds the timestamp when it scrapes.

$ curl -s checkout-1:8080/metrics
# HELP http_requests_total Total HTTP requests handled.
# TYPE http_requests_total counter
http_requests_total{method="POST",path="/checkout",status="200"} 18342
http_requests_total{method="POST",path="/checkout",status="500"} 37
# HELP checkout_in_flight_requests Requests being handled right now.
# TYPE checkout_in_flight_requests gauge
checkout_in_flight_requests 12
  • No job or instance in the page: Prometheus adds them. Guaranteed
  • A client library writes this page for you; you rarely produce it by hand.
Where does the timestamp of a scraped sample come from, normally?
From Prometheus, at the moment it scrapes the page. The exposition lines usually carry only labels and a value.

08

Counters

In plain wordsA counter is like a car’s odometer: it only goes up. The raw number (“18,342 requests since the service started”) is rarely interesting by itself. What you want is how fast it is going up: requests per second. That is why counters are almost always used with rate().

New words

counterA value that only increases, and resets to zero when the process restarts.
resetA counter dropping back to zero because its process restarted.
_totalThe conventional ending for counter names.

A counter only goes up (or resets to zero on restart), so you read it through functions like rate() and increase() that turn it into a per-second or per-period change.

  • Use counters for things that happen: requests, errors, bytes sent.
  • Never alert on the raw value of a counter; alert on its rate.
Why is the raw value of http_requests_total almost never what you graph?
It is a running total since the process started, so it only grows and resets on restart. The useful information is how quickly it grows, which rate() gives.

Follow the checkout

Our 500 counter went 0 → 37 → 121 in two minutes: about 1.4 failures per second, which Part 4 computes properly.

09

Gauges

In plain wordsA gauge is like a speedometer or a thermometer: it goes up and down, and its current value is the interesting thing. Memory in use, requests in flight, queue length, temperature.

New words

gaugeA value that can go up and down, read as it is.

A gauge reports a current level that can rise and fall, and you graph or alert on its value directly, often with avg, max or min over time.

  • Do not use rate() on a gauge; use deriv() or delta() if you need its change.
  • A gauge sampled every 15 s can miss short spikes between scrapes. Simplified
Is “number of items in the job queue” a counter or a gauge?
A gauge: the queue grows and shrinks. “Jobs processed so far” would be a counter.

Follow the checkout

At 10:07 in-flight requests on checkout-1 jump from about 12 to 47: requests are piling up waiting for the slow payment provider. Example value

10

Histograms

In plain wordsTo know how slow requests are, an average hides the painful ones. A histogram sorts every request into buckets by duration: under 0.1 s, under 0.25 s, under 0.5 s, and so on, and counts each bucket. From those counts you can estimate “95% of requests were faster than X”.

New words

histogramA metric that counts observations into buckets by value.
bucketA counter of observations at or below a bound, written le="0.5" (less than or equal).
quantile / percentileThe value below which a given share of observations fall: p95 = 95% are faster.

A histogram exposes cumulative bucket counters (le labels), plus a _sum and a _count, so PromQL can compute rates, averages and estimated percentiles across many instances.

# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{path="/checkout",le="0.1"}   14210
http_request_duration_seconds_bucket{path="/checkout",le="0.25"}  17520
http_request_duration_seconds_bucket{path="/checkout",le="0.5"}   18010
http_request_duration_seconds_bucket{path="/checkout",le="1"}     18190
http_request_duration_seconds_bucket{path="/checkout",le="2.5"}   18290
http_request_duration_seconds_bucket{path="/checkout",le="+Inf"}  18379
http_request_duration_seconds_sum{path="/checkout"}   2861.4
http_request_duration_seconds_count{path="/checkout"} 18379
  • Buckets are cumulative. Guaranteed
  • Average latency = _sum ÷ _count: here 2861.4 ÷ 18379 ≈ 0.156 s (computed).
  • Choose bucket bounds around your target, because percentiles are estimated within a bucket. Client libraries default to .005 … 10 seconds.
  • Native histograms (newer) pick buckets automatically and are far more precise. Simplified
Why is a histogram better than an average for latency?
An average hides the slow tail: a few 3-second requests barely move it. Histogram buckets let you estimate percentiles such as p95 and p99, which show what the slowest users experience.

Follow the checkout

After 10:07 the 2.5 s and +Inf buckets grow fastest: payments waiting on the provider’s timeout. 89 requests took longer than 2.5 s (18379 − 18290, computed).

11

Summaries, and why histograms usually win

In plain wordsA summary computes percentiles inside the service and exposes them ready-made. That sounds convenient, but percentiles cannot be added up: the p95 of three servers is not the average of their three p95s. Histograms expose raw bucket counts, which can be added across servers and then turned into a true overall percentile.

New words

summaryA metric whose client library computes quantiles locally.
aggregateCombine values from many series, such as summing them.

Summaries compute exact quantiles per instance but cannot be aggregated across instances; histograms can, so they are the usual choice.

HistogramSummary
Quantiles computedIn Prometheus (PromQL)In the service
Aggregate across instancesYesNo
AccuracyEstimated within a bucketExact for that instance
Change the quantile laterYesNo, fixed in code
Three servers each report a p99 latency. Can you average them to get the p99 of the whole service?
No. Quantiles do not average; the result depends on how many requests each server handled and their distributions. Sum histogram buckets across servers instead, then compute the quantile.

Follow the checkout

Only checkout-1 talks to the failing payment region, so its p95 jumps while the other two stay low. The overall p95 must come from summed histograms.

Cardinality: the number of series

In plain wordsEvery new combination of label values is a new series, and every series costs memory and disk. A label with a handful of values is fine. A label with a value per user, per order or per request ID multiplies the series count into millions and can knock Prometheus over. This is the most common way to break it.

New words

cardinalityHow many distinct series a metric (or a whole server) has.
active seriesSeries that received a sample recently and are held in memory.
unbounded labelA label whose values never stop growing, such as user_id.

A metric’s series count is the product of its labels’ distinct values, so a single high-cardinality label such as a user ID can multiply memory use by orders of magnitude.

Try it: how many series does http_requests_total make?

Worst case: every combination occurs. Memory assumes about 4 KB per active series. Simplified

  • Never put IDs, emails, URLs with parameters or timestamps in labels. Put them in logs or traces.
  • Check the biggest metrics on the TSDB status page (/tsdb-status). Guaranteed · check 4
Why is adding a user_id label to http_requests_total dangerous?
Every user creates new series for every combination of the other labels, so series count grows with the number of users, potentially millions, exhausting Prometheus’s memory and slowing queries.

Follow the checkout

A developer once added order_id as a label to debug a bug; prom-1 ran out of memory within an hour. The label now lives in logs instead. Example value

13

Naming metrics and labels

In plain wordsGood names make queries readable and stop mistakes like mixing milliseconds with seconds. Prometheus has simple conventions: say what is measured, the unit at the end in plain base units, and _total for counters.

New words

base unitSeconds, bytes, ratios between 0 and 1: no milliseconds or kilobytes.
namespace prefixThe first word of a name saying which system it is from, such as checkout_ or node_.

Metric names use snake_case with a namespace prefix, a base-unit suffix and _total for counters; labels describe dimensions with small, fixed sets of values.

GoodAvoidWhy
http_request_duration_secondshttp_latency_msBase unit, and says what kind of duration
node_memory_used_bytesmem_used_mbBytes, with a namespace
http_requests_total{status="500"}http_500_errors_totalStatus is a dimension: a label, not part of the name
Should failed and successful payments be two metrics or one metric with a label?
One metric with a label (for example result="failed" / "succeeded"), so you can sum them for the total and divide one by the total for a failure ratio.

Follow the checkout

QuickCart’s alert divides http_requests_total{status=~"5.."} by http_requests_total: possible only because status is a label on one metric.

Part 2: Collecting metrics

Scraping, discovery, exporters

14

The pull model and the scrape loop

In plain wordsPrometheus keeps a list of targets and visits each one on a fixed schedule, say every 15 seconds. Because Prometheus does the visiting, it always knows when a target stops answering: the visit fails and up turns to 0. Targets do not need to know Prometheus exists.

New words

scrape intervalHow often each target is scraped.
scrape timeoutHow long one scrape may take before it counts as failed.
pull vs pushThe server fetches data / the clients send it.

Prometheus scrapes each target’s /metrics endpoint at a fixed interval, records whether it worked in up, and stores every line with the scrape timestamp.

# prometheus.yml
global:
  scrape_interval: 15s          # stock default is 1m
  evaluation_interval: 15s      # how often rules run; stock default 1m
scrape_configs:
  - job_name: checkout
    static_configs:
      - targets: ['checkout-1:8080', 'checkout-2:8080', 'checkout-3:8080']
  • Stock defaults: scrape every 1 minute, time out after 10 seconds, evaluate rules every 1 minute. Default · check 1
  • Pull makes health free: a dead target is noticed on the next scrape. Guaranteed
  • Also recorded per scrape: scrape_duration_seconds and scrape_samples_scraped.
Why does the pull model make it easy to detect a service that has died?
Prometheus initiates every scrape, so a dead service simply fails the next scrape and up becomes 0. With push, silence could mean either “dead” or “nothing to report”.

Follow the checkout

At 10:07:00 prom-1 scrapes checkout-1 and reads …status="500"} 37; at 10:07:15 it reads 58. Example value

Finding targets: service discovery

In plain wordsTyping every server’s address into a file works for three servers, not for three hundred containers that come and go every hour. Service discovery asks a system that already knows (Kubernetes, AWS, Consul, a file your tooling writes) for the current list of targets, and keeps it up to date automatically.

New words

service discoveryGetting the list of targets from another system instead of typing it.
static configA fixed, hand-written list of targets.
meta labelsTemporary labels from discovery, like __meta_kubernetes_pod_name, used for relabeling.

Service discovery mechanisms such as Kubernetes, EC2, Consul and file-based discovery keep the target list current, attaching metadata labels you can use to filter and label targets.

scrape_configs:
  - job_name: checkout
    kubernetes_sd_configs:
      - role: pod                    # ask the Kubernetes API for pods
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_label_app]
        regex: checkout
        action: keep                 # only pods labelled app=checkout
  • Many built-in mechanisms: Kubernetes, EC2, Azure, GCE, Consul, DNS, file, HTTP and more.
  • Meta labels disappear after relabeling unless you copy them into real labels. Guaranteed
Why is static configuration a poor fit for containers on Kubernetes?
Pods are created and destroyed constantly with changing addresses. Service discovery queries the Kubernetes API for the current set of pods, so targets stay correct without editing configuration.

Follow the checkout

When the team scaled checkout from 3 to 5 pods at 10:20, Kubernetes discovery added checkout-4 and checkout-5 to prom-1 automatically.

Relabeling

In plain wordsRelabeling is a small rule language for editing labels on the way in. Before a scrape you can drop targets you do not want and turn discovery metadata into useful labels. After a scrape you can drop noisy metrics or labels before they are stored.

New words

relabel_configsRules applied to targets before scraping.
metric_relabel_configsRules applied to scraped series before storing them.
actionWhat a rule does: keep, drop, replace, labelmap, labeldrop, hashmod…

relabel_configs rewrite or filter targets before a scrape, and metric_relabel_configs rewrite or filter samples after it, which is how you shape labels and cut cardinality.

relabel_configs:
  - source_labels: [__meta_kubernetes_namespace]
    target_label: namespace                    # copy metadata into a real label
metric_relabel_configs:
  - source_labels: [__name__]
    regex: 'go_gc_.*'
    action: drop                               # throw away noisy runtime metrics
A target exposes thousands of series you never query. Which config can drop them, and when does it run?
metric_relabel_configs with action drop. It runs after the scrape and before storage, so the unwanted series are never stored.

Follow the checkout

Relabeling adds namespace="shop" to every checkout series, so alerts can route by team. Example value

Exporters and instrumentation

In plain wordsThere are two ways to get metrics. For your own code, you add a client library and count things where they happen: a line to count each request, a timer around each payment call. For software you cannot change, like Linux or MySQL, you run an exporter beside it that reads its stats and exposes them in Prometheus format.

New words

client libraryThe Prometheus library for your language (Go, Java, Python…) that creates metrics and serves /metrics.
node_exporterThe standard exporter for machine metrics: CPU, memory, disk, network.
blackbox_exporterAn exporter that probes endpoints from outside (HTTP, TCP, ping).

Your own services are instrumented with client libraries; third-party systems are covered by exporters such as node_exporter, which translate their stats into the Prometheus format.

# Python: instrumenting the checkout handler
from prometheus_client import Counter, Histogram, start_http_server
REQUESTS = Counter('http_requests_total', 'Total HTTP requests.', ['method', 'path', 'status'])
LATENCY  = Histogram('http_request_duration_seconds', 'Request duration.', ['path'])

def checkout(request):
    with LATENCY.labels(path='/checkout').time():
        status = handle(request)
    REQUESTS.labels(method='POST', path='/checkout', status=str(status)).inc()

start_http_server(8080)     # serves /metrics
  • node_exporter listens on 9100. Default
  • Hundreds of exporters exist: databases, queues, proxies, hardware, cloud services.
You want metrics from a PostgreSQL database you cannot modify. Instrument or exporter?
An exporter (postgres_exporter): it connects to the database, reads its statistics and exposes them on /metrics for Prometheus to scrape.

Follow the checkout

The .inc() line above is what turned each failed payment at 10:07 into +1 on our series.

Short-lived jobs and the Pushgateway

In plain wordsA nightly batch job may run for 30 seconds and exit, long before Prometheus would scrape it. The Pushgateway is a small always-on service the job can push its final numbers to; Prometheus then scrapes the Pushgateway. It is a workaround for batch jobs, not a way to monitor ordinary services.

New words

PushgatewayA service that holds metrics pushed by short-lived jobs until Prometheus scrapes them.
batch jobA program that runs, does a task, and exits.

The Pushgateway lets short-lived batch jobs push their metrics so Prometheus can scrape them later; it is meant for service-level batch jobs, not for long-running services.

  • It never forgets: a job that stopped running still shows its last push, so alert on a “last success” timestamp. Guaranteed
  • It is a single point every pushing job depends on, and you lose the automatic up health signal.
Why should a long-running web service not push to the Pushgateway?
Prometheus would lose per-instance health (up), stale values would linger after the service died, and the Pushgateway becomes a bottleneck. Long-running services should be scraped directly.

Follow the checkout

QuickCart’s nightly payout job pushes payout_last_success_timestamp_seconds; checkout itself is scraped directly.

Part 3: Storage

The time-series database inside Prometheus

19

Inside the TSDB

In plain wordsPrometheus writes new samples to memory first, and also to a log on disk so nothing is lost if it crashes. Every two hours it packs the last two hours of samples into a compact, read-only block on disk. Later, small blocks are merged into bigger ones. Old blocks are simply deleted when they pass the retention period.

New words

head blockThe in-memory part holding the most recent samples.
WALWrite-ahead log: every sample is appended here first, so the head can be rebuilt after a crash.
blockA read-only directory of compressed samples covering a time range (2 hours to start with).
compactionMerging smaller blocks into larger ones.

Recent samples live in the in-memory head, protected by a write-ahead log; every two hours they are cut into immutable on-disk blocks, which compaction later merges and retention deletes.

  • Samples compress to about 1–2 bytes each, using delta encoding of timestamps and XOR encoding of values (the “Gorilla” technique). Simplified
  • Blocks are immutable: deleting old data means removing whole directories, which is cheap.
  • Single node, local disk. Prometheus does not replicate its own data; Part 6 covers what to do about that. Guaranteed
Prometheus crashes. How does it recover the samples that were only in memory?
It replays the write-ahead log on startup, which recorded every sample appended to the head block.

Follow the checkout

Our 10:07 samples sit in the head until prom-1 cuts the 10:00–12:00 block shortly after noon. Simplified

20

Retention and disk sizing

In plain wordsPrometheus keeps data for a set time, 15 days unless told otherwise, then deletes it. How much disk that needs is simple arithmetic: how many samples arrive per second, times bytes per sample, times how many seconds you keep them.

New words

retentionHow long data is kept before deletion.
ingestion rateSamples stored per second: active series ÷ scrape interval.

Disk needed ≈ retention seconds × samples per second × bytes per sample, and samples per second ≈ active series ÷ scrape interval.

Try it: how much disk does prom-1 need?

prometheus --storage.tsdb.retention.time=30d --storage.tsdb.retention.size=200GB
  • Default retention is 15 days. Default · check 2
  • A size limit can be set too; the oldest blocks go first when either limit is reached.
  • Need months or years? Send data to long-term storage (Part 6) instead of growing one server.
Halving the scrape interval from 30 s to 15 s: what happens to disk usage?
It roughly doubles, because each series now produces twice as many samples per second.

Follow the checkout

prom-1 holds about 200,000 active series at 15 s for 15 days: the demo’s defaults give its disk estimate.

Staleness and missing data

In plain wordsSamples arrive every 15 seconds, but a query can ask for any instant. Prometheus answers with the most recent sample up to 5 minutes old. When a target disappears, Prometheus writes a special “stale” marker so the series stops showing at once instead of hanging on for 5 minutes.

New words

lookback deltaHow far back a query looks for the latest sample: 5 minutes by default.
stale markerA special sample saying “this series has ended”.

An instant query returns each series’ latest sample within the 5-minute lookback window, and stale markers end a series immediately when its target or the series itself disappears.

  • Lookback is 5 minutes. Default
  • Absent data is not zero: to alert on a series that vanished, use absent() or alert on up == 0.
A checkout pod is deleted. Why does its series stop appearing in queries almost immediately rather than after 5 minutes?
When the target disappears, Prometheus writes stale markers for its series, so queries treat them as ended right away instead of reusing the last sample for up to the 5-minute lookback.

Asking questions in numbers

Selecting series

In plain wordsThe simplest query is just a metric name, which returns every series with that name. Curly braces narrow it down by labels, a bit like a WHERE clause. You can match exactly, exclude, or match a pattern.

New words

instant vectorA set of series with one sample each, at one moment.
label matcherA condition on a label: =, !=, =~ (regex), !~ (not regex).
regexA text pattern, such as 5.. for any three-character code starting with 5.

A selector names a metric and filters its series with label matchers, returning an instant vector: the latest sample of every matching series.

http_requests_total                                         # every series of the metric
http_requests_total{job="checkout"}                         # exact match
http_requests_total{job="checkout", status=~"5.."}          # regex: any 5xx
http_requests_total{job="checkout", path!="/health"}        # exclude a path
What does the matcher status=~"5.." select?
Series whose status label is any three-character value starting with 5 (500, 502, 503…), because Prometheus regex matches are anchored to the whole value.

Range vectors and rate()

In plain wordsA counter’s raw value only tells you a total. rate() looks at the samples over a window, such as the last 5 minutes, and works out how fast the counter grew, per second. It also notices when a counter dropped back to zero because the service restarted, and counts that as a reset rather than negative traffic.

New words

range vectorFor each series, all samples in a time window: [5m].
rate()Average per-second increase of a counter over the window, handling resets.
increase()The total increase over the window (rate × window length).
irate()Per-second increase using only the last two samples: spiky, for fast graphs.

rate(counter[5m]) turns a counter into an average per-second rate over the last five minutes, correcting for counter resets, and is the basis of nearly every useful query.

Try it: compute rate() over 2 minutes of samples

Real reset handling; the real rate() also extrapolates slightly to the window edges, which is left out here. Simplified

rate(http_requests_total{job="checkout", status=~"5.."}[5m])        # failures per second
increase(http_requests_total{job="checkout", status=~"5.."}[1h])    # failures in the last hour
  • Always take rate() before summing counters, never sum then rate: resets on one instance would corrupt the total. Guaranteed · check 8
  • Make the window at least 4 × the scrape interval so it always holds enough samples: [1m] or more at 15 s. Simplified
A counter goes 100, 150, 20, 60 over four samples because the process restarted. What increase does rate() account for?
90: +50 (100→150), then a reset, counted as +20 (from 0 to 20), then +40 (20→60). A naive “last minus first” would give −40.

Aggregation: sum, avg, topk and friends

In plain wordsUsually you do not want one line per instance, method and status; you want one number per service, or one line per status code. Aggregation operators add, average or rank series together, keeping only the labels you name.

New words

by (…)Keep these labels in the result; combine across all others.
without (…)Drop these labels; keep all others.
topkThe k series with the highest values.

Aggregation operators such as sum, avg, max, count and topk combine series, and by or without decide which labels survive.

sum(rate(http_requests_total{job="checkout"}[5m]))                       # total requests/s
sum by (status) (rate(http_requests_total{job="checkout"}[5m]))           # one line per status
sum by (instance) (rate(http_requests_total{job="checkout",status=~"5.."}[5m]))
topk(3, sum by (path) (rate(http_requests_total[5m])))                    # 3 busiest paths
What is the difference between sum by (instance) and sum without (instance)?
sum by (instance) keeps only the instance label and adds up everything else. sum without (instance) removes instance and keeps every other label, adding up across instances.

Percentiles with histogram_quantile()

In plain wordsTo get the 95th-percentile latency, take the rate of each histogram bucket, add the buckets up across instances, then ask PromQL which duration 95% of requests stayed under. It finds the bucket where the 95% mark falls and assumes requests are spread evenly inside it.

New words

histogram_quantile()Estimates a quantile from histogram bucket rates.
leThe bucket’s upper bound label (“less than or equal”).
linear interpolationAssuming values are evenly spread between a bucket’s lower and upper bound.

histogram_quantile(φ, sum by (le) (rate(…_bucket[5m]))) estimates a latency percentile from bucket rates, interpolating linearly inside the bucket that contains it.

Try it: estimate a percentile from buckets

Same algorithm as Prometheus: find the bucket, interpolate linearly inside it. Bucket rates are invented. Guaranteed · check 5

histogram_quantile(0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="checkout", path="/checkout"}[5m])))
  • Keep the le label when aggregating; without it there are no buckets left to work with.
  • The answer is only as precise as the buckets: if p95 falls in 1–2.5 s, the true value could be anywhere in that range.
Why must you write sum by (le) inside histogram_quantile when combining instances?
histogram_quantile needs the bucket boundaries, which are the le label. Summing by le adds each bucket across instances while keeping the buckets separate.

Ratios and vector matching

In plain wordsThe most useful alert numbers are ratios: failures divided by all requests. PromQL can do arithmetic between two sets of series, pairing up series that have the same labels. When the label sets differ, you say which labels to match on.

New words

binary operatorArithmetic or comparison between two values or vectors: + − * / > < ==.
vector matchingPairing series from two sides of an operator by their labels.
on / ignoringMatch only on these labels / on all labels except these.
group_leftAllow many series on the left to match one on the right.

Binary operators combine vectors by matching series with identical labels, and on, ignoring and group_left control the matching when label sets differ.

# error ratio of the whole service
  sum(rate(http_requests_total{job="checkout", status=~"5.."}[5m]))
/ sum(rate(http_requests_total{job="checkout"}[5m]))

# per instance: both sides keep the instance label, so they pair up
  sum by (instance) (rate(http_requests_total{job="checkout", status=~"5.."}[5m]))
/ sum by (instance) (rate(http_requests_total{job="checkout"}[5m]))

# comparison as a filter: only return instances above 5%
(…the ratio above…) > 0.05
Why does a comparison like ratio > 0.05 return fewer series rather than true/false values?
In PromQL a comparison filters by default: series that fail the condition are dropped, and the rest keep their values. Add the bool modifier to get 0/1 instead.

Recording rules

In plain wordsSome queries are expensive and asked over and over by dashboards and alerts. A recording rule runs a query on a schedule and stores the answer as a new, cheap series. Dashboards then read the pre-computed series instead of crunching raw data every time.

New words

recording ruleA query Prometheus evaluates regularly and stores as a new series.
rule groupRules evaluated together, in order, at the same interval.

Recording rules pre-compute expensive or frequently used expressions into new series at every evaluation interval, named by the convention level:metric:operations.

# rules/checkout.yml
groups:
  - name: checkout
    rules:
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))
      - record: job:http_errors:ratio_rate5m
        expr: |
          sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
          / sum by (job) (rate(http_requests_total[5m]))
What does the name job:http_errors:ratio_rate5m tell you?
By convention: aggregated to the job level, about HTTP errors, and computed as a ratio of 5-minute rates.

What to measure: golden signals, RED and USE

In plain wordsYou could measure a thousand things. Three well-known checklists say which few matter most. For a service handling requests: how many, how many fail, how long they take (RED). For a resource like a disk or CPU: how busy, how overloaded, how many errors (USE). Google’s “four golden signals” combine the two.

New words

REDRate, Errors, Duration: the key metrics for a request-driven service.
USEUtilization, Saturation, Errors: the key metrics for a resource.
golden signalsLatency, traffic, errors, saturation.
saturationHow much work is waiting because a resource is full.

RED (rate, errors, duration) covers services, USE (utilization, saturation, errors) covers resources, and the four golden signals combine them into what to put on every dashboard.

Part 5: Alerting

From a condition to a person

30

Alerting rules

In plain wordsAn alerting rule is a PromQL condition with a waiting period. Prometheus checks it every evaluation interval. When it first becomes true the alert is “pending”; if it stays true for the whole waiting period, it becomes “firing” and is sent to Alertmanager. A short blip never pages anyone.

New words

forHow long a condition must stay true before the alert fires.
pending / firingCondition true but waiting / condition true long enough, alert sent.
annotationsHuman text attached to an alert: summary, description, runbook link.

An alerting rule fires when its expression returns results continuously for the for duration; it moves from inactive to pending to firing and is sent to Alertmanager while firing.

groups:
  - name: checkout-alerts
    rules:
      - alert: CheckoutHighErrorRate
        expr: job:http_errors:ratio_rate5m{job="checkout"} > 0.05
        for: 5m
        labels:
          severity: page
          team: payments
        annotations:
          summary: "Checkout errors at {{ $value | humanizePercentage }}"
          runbook_url: "https://wiki.quickcart.example/runbooks/checkout-errors"

Try it: when does the alert fire?

Rule evaluated once a minute here for clarity; QuickCart evaluates every 15 s. Simplified

  • States: inactive → pending → firing. Guaranteed · check 6
  • The for clause trades speed for calm: longer waits mean fewer false pages, later real ones.
A rule has for: 5m. The condition is true from 10:07 and is evaluated every 15 s. Roughly when does it fire?
About 10:12, once the condition has been continuously true for 5 minutes. Before that it is pending.

Alertmanager: grouping, routing, silencing

In plain wordsPrometheus only says “this alert is firing”. Alertmanager decides what people receive: it bundles related alerts into one message, sends each bundle to the right team’s pager or chat, holds back follow-on alerts when a bigger one explains them, and stays quiet during planned maintenance.

New words

groupingCombining alerts with the same chosen labels into one notification.
route / receiverThe rule tree that picks a destination / the destination itself (pager, Slack, email).
inhibitionSuppressing some alerts while another, more important one is firing.
silenceA temporary mute for alerts matching given labels.

Alertmanager deduplicates, groups, routes, inhibits and silences alerts from Prometheus, and sends notifications to receivers such as pagers and chat.

# alertmanager.yml
route:
  receiver: checkout-chat
  group_by: ['alertname', 'job']
  group_wait: 30s          # wait to batch the first notification
  group_interval: 5m       # wait before notifying about changes in a group
  repeat_interval: 4h      # re-send while still firing
  routes:
    - matchers: [ 'severity="page"' ]
      receiver: oncall-pager
inhibit_rules:
  - source_matchers: [ 'alertname="CheckoutDown"' ]
    target_matchers: [ 'alertname="CheckoutHighErrorRate"' ]
    equal: ['job']
  • Stock timers: group_wait 30 s, group_interval 5 m, repeat_interval 4 h. Default · check 7
  • Listens on port 9093; several Alertmanagers form a cluster that deduplicates notifications. Default
The database goes down and fifty services start alerting on errors. Which Alertmanager feature stops fifty pages?
Grouping (by alertname or cluster) and inhibition: a “database down” alert can inhibit the dependent services’ error alerts, so the on-call sees the root cause instead of fifty symptoms.

Good alerts, SLOs and burn rates

In plain wordsAn alert should mean “a human must act now”. Page on what users feel (errors, slowness), not on every internal cause (high CPU). A service level objective says how good is good enough, such as 99.9% successful checkouts a month, and the best alerts fire when you are using up that small allowance of failures too fast.

New words

SLIService level indicator: the measured number, such as the success ratio.
SLOService level objective: the target for the SLI, such as 99.9% over 30 days.
error budgetThe failures the SLO allows: 0.1% of requests for a 99.9% SLO.
burn rateHow fast the error budget is being used compared with “exactly on budget”.

Good alerts page on user-visible symptoms tied to service level objectives, and burn-rate alerts fire when the error budget is being consumed fast enough to matter.

No successful checkouts in 10 minutesDisk at 70% (ticket, not page)
Why page on the checkout error ratio rather than on high CPU?
The error ratio is what users experience and always needs action. High CPU may be harmless (the service still answers fine) and would page people for nothing.

High availability

In plain wordsOne Prometheus is one point of failure: if it is down, nobody gets alerts. The simple fix is to run two identical copies that scrape the same targets and evaluate the same rules. Both send alerts to a cluster of Alertmanagers, which make sure each alert is sent only once.

New words

HA pairTwo identical Prometheus servers scraping the same targets.
deduplicationMaking sure the same alert from both servers produces one notification.
gossipHow Alertmanager cluster members share state with each other.

High availability means running identical Prometheus replicas that independently scrape and alert, with a clustered Alertmanager deduplicating their notifications.

  • The two copies are not identical byte for byte: scrapes happen at slightly different moments. Dashboards pick one, or a querying layer merges them (next lessons).
  • Point Prometheus at all Alertmanagers, not a load balancer, so deduplication works. Simplified
Two Prometheus servers both detect CheckoutHighErrorRate. Why does Sam get one page, not two?
Both send the alert to the Alertmanager cluster, which recognises them as the same alert (same labels) and, sharing state by gossip, sends a single notification.

Follow the checkout

After an outage of prom-1 during an upgrade, QuickCart added prom-2. On 10:07 both fired; Sam got one page.

Federation

In plain wordsA large company runs one Prometheus per cluster or region, each close to its targets. To see the big picture, a global Prometheus can scrape a summary from each of them, usually just the pre-computed recording rules, rather than every raw series.

New words

federationOne Prometheus scraping selected series from others through their /federate endpoint.
hierarchicalArranged in levels: local servers below, a global one above.

Federation lets a higher-level Prometheus scrape selected series, typically aggregated recording rules, from lower-level servers via /federate.

scrape_configs:
  - job_name: federate
    honor_labels: true
    metrics_path: /federate
    params:
      'match[]': ['{__name__=~"job:.*"}']     # only recording-rule aggregates
    static_configs:
      - targets: ['prom-eu:9090', 'prom-us:9090']
Why federate only recording-rule series rather than everything?
Pulling every raw series into one global server would recreate the single-server limits federation is meant to avoid. Aggregates are small and enough for a global view.

Remote write and long-term storage

In plain wordsOne Prometheus keeps two weeks on one disk. For a year of history, one place to query every cluster, and protection against losing a disk, Prometheus can stream every sample to a separate storage system built for that, such as Thanos, Grafana Mimir or VictoriaMetrics, which keeps data in cheap object storage.

remote writePrometheus streaming samples to another system as they arrive.
long-term storageA system that keeps metrics for months or years, usually in object storage.
global viewQuerying all clusters’ metrics in one place.

remote_write streams samples to long-term, horizontally scalable stores such as Thanos, Mimir, Cortex or VictoriaMetrics, which add durable retention, a global query view and deduplication of HA pairs.

Why add a long-term store instead of setting Prometheus retention to one year?

Write the PromQL for the checkout service’s error ratio over 5 minutes.
sum(rate(http_requests_total{job="checkout", status=~"5.."}[5m])) / sum(rate(http_requests_total{job="checkout"}[5m]))
Why does an alert with for: 5m not page on a one-minute spike?
The condition must stay true continuously for 5 minutes; a one-minute spike only makes the alert pending, and it returns to inactive when the condition clears.
What are the two main risks of running a single Prometheus, and the usual fixes?
It is a single point of failure for alerting (fix: an HA pair plus a clustered Alertmanager) and keeps limited history on one disk (fix: remote write to a long-term store such as Thanos or Mimir).
