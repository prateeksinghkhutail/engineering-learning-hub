01

What “analytics” is, and why it needs its own database

In plain wordsThe shop’s website asks its database small questions all day: “show order 90217”, “save this new order”. The analytics team asks big questions a few times a day: “add up every order from last year, by country”. A database built for the first kind is slow at the second, and running big questions on it would slow the website down. So analytics gets its own database, a data warehouse.

New words

OLTPOnline transaction processing: many small reads and writes, like an app’s main database.
OLAPOnline analytical processing: few, big queries that scan and summarise lots of data.
data warehouseA database built for OLAP, holding copies of data from many sources.
aggregateA summary over many rows: SUM, COUNT, AVG.

Analytics means asking big questions over lots of rows, and a data warehouse is a database designed for exactly that, separate from the databases that run the app.

Why not run the analytics team’s “revenue by country for the whole year” query directly on the shop’s main database?
It would scan millions of rows on a database tuned for small lookups, which is slow, and it would compete with the website for resources, slowing down customers. A warehouse is built for such scans and keeps that load away from the app.

02

Why analytics stores data by column

In plain wordsMost app databases store each row together: all of order 90217’s fields side by side. That is perfect for “show me this order”. But “sum the amount column” then has to read every field of every row. Storing each column together instead lets the warehouse read just the two columns the question needs, and similar values next to each other also compress very well.

New words

row storeStores all fields of a row together.
column storeStores all values of one column together.
compressionStoring data in fewer bytes; works best when similar values sit together.

A column store keeps each column’s values together, so a query that needs 2 of 20 columns reads roughly a tenth of the data, and compresses it well too.

06

Facts and dimensions

In plain wordsEvery business question has two halves: something you measure (how much was sold) and the things you slice it by (which country, which product, which day). Warehouses store those halves in different tables. Facts hold the numbers, one row per event. Dimensions hold the descriptions: who, what, where, when.

New words

fact tableA table of business events with numeric measures, such as one row per order.
measureA number you add up or average: amount, quantity.
dimension tableA table describing something you group or filter by: customer, product, date.
grainWhat exactly one row of a fact table represents, such as “one order line”.
surrogate keyA plain number the warehouse assigns as a dimension’s key, instead of reusing the source system’s ID.

Dimensional modelling splits data into fact tables, which record measurable events at a declared grain, and dimension tables, which describe the who, what, where and when of those events.

  • Declare the grain first. “One row per order” and “one row per order line” give different answers to “average price”. Guaranteed
  • Facts are long and thin; dimensions are short and wide.
  • A date dimension pre-computes weekday, week, quarter and holidays so nobody has to work them out in every query. 4 October 2026 is a Sunday in ISO week 40, quarter 4 (computed).
Is “country” a fact or a dimension attribute, and what about “amount”?
Country describes the context, so it is a dimension attribute (of the customer). Amount is a number you add up, so it is a measure in the fact table.

Star schema and snowflake schema

In plain wordsDraw the fact table in the middle and each dimension around it, joined by keys, and it looks like a star. If you then split a dimension into smaller tables (customer → city → country), the points branch out like a snowflake. That shape gave the “snowflake schema” its name; it is unrelated to the company, which happens to share it.

New words

star schemaOne fact table joined directly to flat, denormalized dimension tables.
snowflake schemaA star schema whose dimensions are split into further normalized tables.
joinCombining rows from two tables that share a key.

A star schema joins one fact table straight to flat dimension tables; a snowflake schema normalizes those dimensions into sub-tables, saving some space at the cost of more joins.

Why do most modern cloud warehouses prefer star schemas over snowflake schemas?
Columnar compression makes repeated dimension text cheap, so the space a snowflake schema saves is small, while its extra joins make queries slower and harder to write.

08

Normalization and denormalization

In plain wordsAn app’s database stores each fact exactly once and links tables by keys, so updates are simple and nothing contradicts itself (normalized). A warehouse is read far more than it is written, so it often copies descriptive fields into the tables people query, trading duplication for fewer joins and faster, simpler queries (denormalized).

New words

normalizationSplitting data so each fact is stored once, linked by keys.
third normal form (3NF)The usual target for app databases: no repeated groups, no fields depending on non-key fields.
denormalizationDeliberately copying data into fewer, wider tables to speed up reads.

App databases normalize to make writes safe; warehouses denormalize to make reads fast, because they are written in controlled batches and read constantly.

  • The warehouse can afford duplication because the pipeline, not users, writes it, and rebuilds it when sources change.
  • ShopCo’s ANALYTICS.ORDERS is denormalized: it carries country directly, which is why the dashboard needs no join at all.
Why is duplicating the customer’s country into every order row acceptable in a warehouse but risky in an app database?
In the app, many users write data and duplicates can drift apart. In the warehouse, a controlled pipeline writes the data and can rebuild every copy from the sources, so duplication is safe and saves joins.

Slowly changing dimensions

In plain wordsLena lived in Germany when she bought the keyboard and moves to Austria in November. Should last month’s report suddenly show her purchase as Austrian? Usually not. Dimensions change slowly over time, and the warehouse must choose whether to overwrite history or keep it.

New words

SCDSlowly changing dimension: a dimension whose attributes change now and then.
Type 1Overwrite the old value; history is lost.
Type 2Add a new row with validity dates; history is kept.
Type 3Keep a “previous value” column alongside the current one.

Slowly changing dimension techniques decide what happens to history when a dimension attribute changes: overwrite it (Type 1), version it (Type 2), or keep one previous value (Type 3).

Try it: Lena moves from Germany to Austria

-- Type 2: close the old row, insert the new one
UPDATE dim_customer SET valid_to = '2026-10-31', is_current = FALSE
 WHERE customer_id = 5512 AND is_current;
INSERT INTO dim_customer (customer_key, customer_id, name, country, valid_from, valid_to, is_current)
VALUES (88231, 5512, 'Lena', 'AT', '2026-11-01', '9999-12-31', TRUE);
  • Type 2 is the usual choice when reports must stay correct for the past.
  • Facts point to the surrogate key that was current at the time, so old orders keep their old country.
  • Streams, MERGE and dynamic tables are the Snowflake tools for maintaining SCDs (later parts).
Under SCD Type 1, what happens to October’s “revenue by country” report after Lena moves to Austria?
It changes: her October order is now counted under Austria, because her only customer row was overwritten. Type 2 would keep it under Germany.

OLAP operations: roll-up, drill-down, slice, dice, pivot

In plain wordsAnalysts explore data by zooming out (from days to months), zooming in (from countries to cities), fixing one value (only Germany), cutting a sub-block (Germany and Austria, Q4 only), and turning rows into columns. These moves have names, and SQL has shortcuts for several of them.

New words

roll-up / drill-downSummarise to a coarser level / break down to a finer level.
slice / diceFilter on one dimension value / on several values of several dimensions.
pivotTurn values of one column into separate columns.
OLAP cubeThe idea of data arranged by several dimensions at once, with totals at every level.

Roll-up, drill-down, slice, dice and pivot are the standard ways of exploring a multidimensional data set, and Snowflake supports them with GROUP BY ROLLUP, CUBE, GROUPING SETS and PIVOT.

-- totals per country, per country+month, and a grand total, in one query
SELECT country, DATE_TRUNC('month', order_date) AS month, SUM(amount)
  FROM orders
 GROUP BY ROLLUP (country, month);

-- every combination of the listed dimensions
SELECT country, category, SUM(amount) FROM orders_with_products GROUP BY CUBE (country, category);

-- pivot: one column per country
SELECT * FROM (SELECT order_date, country, amount FROM orders)
  PIVOT (SUM(amount) FOR country IN ('DE', 'AT', 'FR'));
  • ROLLUP adds subtotal rows along a hierarchy; CUBE adds subtotals for every combination. Guaranteed
  • Subtotal rows show NULL in the rolled-up columns; GROUPING() tells them apart from real NULLs.
What is the difference between GROUP BY ROLLUP (country, month) and GROUP BY CUBE (country, month)?
ROLLUP gives totals per country+month, per country, and a grand total (following the hierarchy). CUBE adds totals per month across all countries as well: every combination.

Massively parallel processing and columnar compression

In plain wordsTo add up 100 million rows quickly, split the work: give each of many machines a slice, let them add up their slices at the same time, then add the partial results together. And make the slices small: columns of similar values compress into a fraction of their size, so there is less to read.

New words

MPPMassively parallel processing: many machines each working on part of one query.
nodeOne machine in a compute cluster.
dictionary encodingStoring each distinct value once and replacing it with a small number.
run-length encodingStoring “DE ×4000” instead of “DE” four thousand times.

Snowflake warehouses are MPP clusters: each node scans part of the micro-partitions and partial results are combined, while columnar encodings shrink what each node must read.

  • Snowflake calls its design a hybrid: shared storage that every warehouse sees (shared-disk), with MPP clusters whose nodes each process a share of the data (shared-nothing). Guaranteed
  • Compression is automatic; Snowflake picks an encoding per column. You never choose it.
  • Bigger warehouse = more nodes, which is why a size up can halve a large query’s time.
Why does a column of countries compress much better when the rows are sorted by country?
Equal values sit next to each other, so run-length encoding can store each run as one value and a count instead of repeating the value thousands of times.

Data lake, lakehouse and open table formats

In plain wordsA data lake is a big pile of files in cheap cloud storage: cheap and flexible, but hard to query reliably. A warehouse is tidy and fast, but its data lives in its own format. A lakehouse tries to have both, using open table formats like Apache Iceberg that add table features on top of plain files any engine can read.

New words

data lakeRaw files (JSON, Parquet, CSV) in object storage, without a database managing them.
ParquetAn open, columnar file format widely used in data lakes.
open table formatA standard (Iceberg, Delta Lake, Hudi) that turns folders of Parquet files into tables with transactions and schemas.
lakehouseA data lake with warehouse features, built on an open table format.

Data lakes store open files cheaply, warehouses add speed and management, and open table formats like Apache Iceberg let warehouse engines such as Snowflake work directly on lake data.

Why might a company store some tables as Iceberg tables instead of standard Snowflake tables?
So the same data, in open Parquet and Iceberg format in their own storage, can be read and written by other engines such as Spark, without copying it out of Snowflake.

Three layers, and why they are separate

The three layers

In plain wordsThink of a library. The shelves hold the books (storage). Reading rooms with desks are where people work (compute); you can open more rooms when it gets busy and close them at night. The front desk keeps the catalogue, checks library cards and tells you where books are (services). Snowflake is built the same way, and each part grows independently.

New words

storage layerWhere table data lives, in the cloud provider’s object storage.
compute layerThe virtual warehouses that run queries.
cloud services layerSnowflake’s always-on brain: login, security, metadata, query planning.
object storageCheap, durable cloud file storage such as Amazon S3.

Snowflake has three layers: storage in cloud object storage, compute in virtual warehouses, and a cloud services layer that coordinates everything.

  • Storage: one copy of the data, in the cloud provider’s object storage, managed by Snowflake. You never see the files. Guaranteed
  • Compute: any number of warehouses, each a separate cluster, all reading the same storage.
  • Services: always on, shared by the whole account; it decides what each query must read.
Which layer decides which parts of a table a query needs to read, and which layer actually reads them?
The cloud services layer plans the query using its metadata and decides what to read. A virtual warehouse in the compute layer does the reading and computing.

Why separating storage and compute matters

In plain wordsIn many older warehouses, data lives on the same machines that run queries. Need more speed? Buy more machines and move data around. One team’s huge report slows everyone else. Snowflake keeps data in one place and lets each team rent its own reading room: the loaders, the analysts and the data scientists never queue behind each other.

workload isolationDifferent jobs running on separate compute so they cannot slow each other.
concurrencyHow many queries run at the same time.

Because every warehouse reads the same storage, you can give each workload its own compute, size it independently, and pay for each only while it runs.

  • No contention between teams that use different warehouses. Guaranteed
  • Scale compute in seconds without moving any data.
  • Storage grows on its own, without buying compute you do not need.
The data science team runs a 40-minute model-training query. How do you stop it slowing down the morning dashboard?
Give data science its own warehouse. Both read the same storage, but the dashboard’s warehouse is a separate cluster that the training query never touches.

Micro-partitions

In plain wordsSnowflake does not store a table as one big file. It cuts it into many small files, each holding a slice of the rows, stored column by column and compressed. For every file it also writes a little label: the smallest and largest value of each column inside. Those labels are what make the next lesson possible.

New words

micro-partitionOne of the small, immutable files a table is split into, holding 50 to 500 MB of uncompressed data.
immutableNever changed after it is written; an update writes a new micro-partition instead.
metadataData about the data, such as each micro-partition’s min and max per column.

Every table is stored as many small, immutable, columnar files called micro-partitions, and Snowflake keeps the minimum and maximum of every column for each one.

  • 50 to 500 MB uncompressed each, much smaller once compressed. Guaranteed
  • Created automatically as data is loaded, in the order it arrives. You do not define them.
  • Never edited: an UPDATE writes new micro-partitions and retires the old ones, which is also how Time Travel works (Part 7).
What two things does Snowflake record about each column of every micro-partition, and why?
The minimum and maximum value (plus counts such as nulls and distinct values). They let the optimizer skip micro-partitions that cannot contain matching rows, without opening them.

Pruning: skipping data without reading it

In plain wordsBefore reading anything, Snowflake checks each micro-partition’s label. If the dashboard wants 4 October and a label says “1 October to 1 October”, that file is skipped without being opened. When the table is stored roughly in date order, a one-day question opens one day’s files out of a whole year.

New words

pruningSkipping micro-partitions whose min/max show they cannot match the filter.
scanActually reading data from storage.

Pruning uses the min and max labels to skip micro-partitions that cannot match a query’s filter, so how well the data is ordered decides how much a query reads.

Try it: one year of orders, 365 micro-partitions

  • Functions can hide a column from pruning: prefer order_date = '2026-10-04' over wrapping the column in an expression when you can.
  • The query profile shows it: “Partitions scanned” versus “Partitions total”. Guaranteed · check 3
A table was backfilled with a year of orders in random order. Why does a “yesterday only” query read almost everything?
Each micro-partition then holds rows from all over the year, so its min and max span nearly the whole year and none can be ruled out. Pruning only helps when each partition covers a narrow range of the filtered column.

Clustering and clustering keys

In plain wordsPruning works when rows with similar values sit in the same micro-partitions. Data loaded day by day is naturally sorted by date. If your queries filter on something else, or the order gets scrambled by updates, you can ask Snowflake to keep the table sorted by chosen columns in the background, for a fee.

New words

clusteringHow well rows with similar values are grouped into the same micro-partitions.
clustering keyColumns you ask Snowflake to keep the table ordered by.
clustering depthHow many micro-partitions overlap for a given value; lower is better.

Natural load order usually clusters tables by time; for very large tables queried by other columns, a clustering key makes Snowflake re-sort data in the background so pruning keeps working.

ALTER TABLE shopco.analytics.orders CLUSTER BY (order_date, country);
SELECT SYSTEM$CLUSTERING_INFORMATION('shopco.analytics.orders', '(order_date)');
  • Most tables need no clustering key. It pays off for multi-terabyte tables with selective filters. Simplified
  • Automatic Clustering is a background service billed in credits; it re-sorts only what has become disordered.
  • Put low-cardinality, commonly filtered columns first, usually a date. Clustering on a unique ID wastes money.
Why is a unique order ID usually a poor clustering key?
Queries rarely filter on ranges of order IDs, and keeping billions of distinct values sorted is expensive. Clustering pays off on columns that queries filter by and that group many rows, such as dates.

Scaling up versus scaling out

In plain wordsTwo different problems, two different fixes. If one big query is slow, use a bigger warehouse: more machines work on that query (scale up). If many people’s queries are queueing, add more copies of the warehouse so they run side by side (scale out).

Constraints: declared, mostly not enforced

In plain wordsIn an app database, declaring “order_id is the primary key” stops anyone inserting a second order 90217. In Snowflake’s standard tables you may declare primary, unique and foreign keys, but they are only labels for documentation and tools. Snowflake will happily store two copies of order 90217. New words

constraintA rule about the data, such as “this column is unique”.
enforcedChecked by the database, which rejects rows that break it.
informationalRecorded for tools and readers, but not checked.

On standard Snowflake tables PRIMARY KEY, UNIQUE and FOREIGN KEY are informational only; only NOT NULL is enforced, so pipelines must prevent duplicates themselves.

CREATE TABLE t (id NUMBER PRIMARY KEY, name STRING NOT NULL);
INSERT INTO t VALUES (1, 'a');
INSERT INTO t VALUES (1, 'b');          -- succeeds: the primary key is not enforced
INSERT INTO t VALUES (2, NULL);         -- fails: NULL result in a non-nullable column

Transactions and concurrency

In plain wordsA transaction groups changes so they all happen or none do. Snowflake supports this like any database. Each statement normally commits on its own; you can group several with BEGIN and COMMIT. Readers never wait for writers, but two statements updating the same table may queue behind each other.

New words

ACIDAtomic, consistent, isolated, durable: the guarantees of a transaction.
autocommitEach statement is its own transaction unless you start one explicitly.
READ COMMITTEDEach statement sees data committed before it started.
lockA claim on a table that makes conflicting writers wait.

Snowflake transactions are ACID with READ COMMITTED isolation; reads never block, inserts run concurrently, and UPDATE, DELETE and MERGE on the same table generally wait for each other.

BEGIN;
DELETE FROM analytics.orders WHERE order_date = '2026-10-04';
INSERT INTO analytics.orders SELECT … FROM raw.orders_clean WHERE order_date = '2026-10-04';
COMMIT;      -- dashboards never see the day half-deleted
  • Isolation level is READ COMMITTED. Guaranteed
  • Waiting writers time out after LOCK_TIMEOUT (12 hours by default). Default · check 13
  • Design pipelines to append where possible; frequent small UPDATEs fight each other and rewrite micro-partitions.
Two pipelines MERGE into the same table at the same time. What happens?
They generally cannot run in parallel: one takes the table’s lock and the other waits until the first commits (or until LOCK_TIMEOUT expires).

MERGE: insert, update or delete in one statement

In plain wordsA batch of new and changed orders arrives. Some orders are new and must be inserted; some already exist and must be updated; cancelled ones must be removed. MERGE compares the batch with the table by a key and does the right thing for each row, in one statement.

New words

MERGEOne statement that inserts, updates or deletes target rows depending on whether they match source rows.
upsertInsert if missing, update if present.
target / sourceThe table being changed / the incoming rows.

MERGE matches source rows to target rows on a key and applies inserts, updates and deletes accordingly, which is how incremental pipelines and slowly changing dimensions are maintained.

MERGE INTO analytics.orders t
USING raw.orders_new s
   ON t.order_id = s.order_id
 WHEN MATCHED AND s.status = 'cancelled' THEN DELETE
 WHEN MATCHED THEN UPDATE SET t.amount = s.amount, t.status = s.status
 WHEN NOT MATCHED THEN INSERT (order_id, customer_id, country, order_date, amount, status)
                       VALUES (s.order_id, s.customer_id, s.country, s.order_date, s.amount, s.status);
  • Deduplicate the source first: if two source rows match one target row, MERGE can fail or behave unpredictably.
  • MERGE + a stream processes only changed rows, the classic incremental pipeline.
Why should the source of a MERGE contain at most one row per key?
If several source rows match the same target row, the update is ambiguous; Snowflake raises an error (or picks one nondeterministically, depending on settings). Deduplicating the source first avoids it.

Time Travel

In plain wordsBecause micro-partitions are never edited, an UPDATE or DELETE writes new files and keeps the old ones for a while. So you can ask “what did this table look like an hour ago?”, or bring back a table you dropped by mistake, with ordinary SQL.

New words

Time TravelQuerying or restoring data as it was at an earlier moment.
retention periodHow long old versions are kept for Time Travel.
UNDROPRestore a dropped table, schema or database within retention.

Time Travel lets you query, clone or restore data as it was at any point within the retention period, because old micro-partitions are kept.

SELECT * FROM orders BEFORE(STATEMENT => '01b7c3a2-…');          -- just before a statement
CREATE TABLE orders_restored CLONE orders AT(TIMESTAMP => '2026-10-05 09:29:00'::timestamp_ltz);
DROP TABLE orders;  UNDROP TABLE orders;
  • Default retention is 1 day. Default · check 7
  • Up to 90 days on Enterprise edition for permanent tables. Edition
  • UNDROP brings back a dropped table, schema or database within retention. Guaranteed · check 8
  • Retention costs storage: changed and deleted data is kept and billed for the period.
Someone ran DELETE FROM orders without a WHERE clause twenty minutes ago. How do you get the rows back?
Use Time Travel: for example create a clone of the table AT a timestamp just before the delete (or insert the rows back from a SELECT … AT/BEFORE query). It works within the retention period.

Pipelines inside Snowflake: streams, tasks and dynamic tables

In plain wordsRaw JSON arrives every minute; the clean ORDERS table must keep up. A stream remembers what is new in a table since you last looked. A task runs SQL on a schedule. Together they process only new rows. A dynamic table does the same with one statement: “keep this query’s result no more than N minutes stale”.

New words

streamA record of the changes to a table since it was last read.
taskSQL that Snowflake runs on a schedule or when a condition is true.
dynamic tableA table defined by a query that Snowflake keeps refreshed within a target lag.
incrementalProcessing only what changed, not everything again.
MERGEOne statement that inserts, updates or deletes rows depending on whether they match (see the MERGE lesson).

Streams track changes, tasks schedule SQL, and dynamic tables declare a refreshed result, so transformations can run incrementally inside Snowflake.

Test yourself, then look up any term.

Explain in two sentences why Snowflake can give each team its own compute without copying data.
Data lives once in cloud storage, separate from compute. Any number of virtual warehouses can read the same micro-partitions, so each team gets its own warehouse over one shared copy.
Name the three caches and which one needs a running warehouse.
Result cache, warehouse (local disk) cache, and metadata. Only the warehouse cache needs a running warehouse; it is lost on suspend.
What makes Time Travel and zero-copy cloning possible?
Micro-partitions are immutable: changes write new ones and old ones are kept, so earlier versions can be read and new tables can point at existing files.
