Part 0: Start here

No analytics knowledge needed

01

What “analytics” is, and why it needs its own database

In plain wordsThe shop’s website asks its database small questions all day: “show order 90217”, “save this new order”. The analytics team asks big questions a few times a day: “add up every order from last year, by country”. A database built for the first kind is slow at the second, and running big questions on it would slow the website down. So analytics gets its own database, a data warehouse.

New words

OLTPOnline transaction processing: many small reads and writes, like an app’s main database.
OLAPOnline analytical processing: few, big queries that scan and summarise lots of data.
data warehouseA database built for OLAP, holding copies of data from many sources.
aggregateA summary over many rows: SUM, COUNT, AVG.

Analytics means asking big questions over lots of rows, and a data warehouse is a database designed for exactly that, separate from the databases that run the app.

Why not run the analytics team’s “revenue by country for the whole year” query directly on the shop’s main database?
It would scan millions of rows on a database tuned for small lookups, which is slow, and it would compete with the website for resources, slowing down customers. A warehouse is built for such scans and keeps that load away from the app.

Follow the dashboard

Order 90217 was saved by the shop’s app database at 09:41 on 4 October. A copy reaches Snowflake a minute later, and the next morning it is one of the rows summed into Germany’s revenue.

02

Why analytics stores data by column

In plain wordsMost app databases store each row together: all of order 90217’s fields side by side. That is perfect for “show me this order”. But “sum the amount column” then has to read every field of every row. Storing each column together instead lets the warehouse read just the two columns the question needs, and similar values next to each other also compress very well.

New words

row storeStores all fields of a row together.
column storeStores all values of one column together.
compressionStoring data in fewer bytes; works best when similar values sit together.

A column store keeps each column’s values together, so a query that needs 2 of 20 columns reads roughly a tenth of the data, and compresses it well too.

Try it: bytes read for one query

2

20 columns of about 8 bytes each; compression assumed at 5× for the column store. Real ratios vary widely. Simplified · check 1

A table has 20 columns. A query sums one column for all rows. Roughly how much less does a column store read than a row store, before compression?
About 20 times less: it reads 1 column out of 20 instead of every column of every row.

The dashboard query uses 3 of the 20 columns: country, amount and order_date. Snowflake reads only those three for the rows it needs.

03

What Snowflake is

In plain wordsSnowflake is a data warehouse you rent rather than run. You do not install it or manage servers. You sign up, load data, and write SQL. Behind the scenes it keeps your data in the cloud provider’s storage and switches computers on and off to answer your queries, and you pay for the storage you use and the minutes those computers run.

New words

cloudComputers and storage rented from a provider like AWS, Azure or Google Cloud.
SaaSSoftware as a service: you use it over the internet; the vendor runs it.
virtual warehouseSnowflake’s name for a cluster of computers that runs your queries. Despite the name, it holds no data.
creditThe unit Snowflake bills computing in.

Snowflake is a cloud data warehouse sold as a service: data lives in cloud storage, queries run on compute clusters called virtual warehouses, and you use plain SQL.

  • No servers to manage. No installing, patching or tuning disks. Guaranteed
  • Standard SQL plus extensions for JSON and analytics.
  • Runs on all three big clouds; you pick a cloud and region when the account is created.
Does a Snowflake “virtual warehouse” store your data?
No. A virtual warehouse is only compute: the machines that run queries. Data lives separately in cloud storage, which is why warehouses can be started, stopped and resized freely.

In plain wordsThink of a gym that charges for your locker by size, and for the treadmill by the minute you use it. Snowflake charges for storage by how much data you keep, and for compute by how many seconds your warehouses run, multiplied by their size. A warehouse that is switched off costs nothing.

storageThe space your data takes, after compression.
auto-suspendA warehouse setting that switches it off after it has been idle for a while.

Snowflake bills storage per terabyte per month and compute in credits per second of running warehouse, so idle compute should be switched off.

Part 1: Architecture

Three layers, and why they are separate

06

The three layers

In plain wordsThink of a library. The shelves hold the books (storage). Reading rooms with desks are where people work (compute); you can open more rooms when it gets busy and close them at night. The front desk keeps the catalogue, checks library cards and tells you where books are (services). Snowflake is built the same way, and each part grows independently.

New words

storage layerWhere table data lives, in the cloud provider’s object storage.
compute layerThe virtual warehouses that run queries.
cloud services layerSnowflake’s always-on brain: login, security, metadata, query planning.
object storageCheap, durable cloud file storage such as Amazon S3.

Snowflake has three layers: storage in cloud object storage, compute in virtual warehouses, and a cloud services layer that coordinates everything.

  • Storage: one copy of the data, in the cloud provider’s object storage, managed by Snowflake. You never see the files. Guaranteed
  • Compute: any number of warehouses, each a separate cluster, all reading the same storage.
  • Services: always on, shared by the whole account; it decides what each query must read.
Which layer decides which parts of a table a query needs to read, and which layer actually reads them?
The cloud services layer plans the query using its metadata and decides what to read. A virtual warehouse in the compute layer does the reading and computing.

Follow the dashboard

ShopCo runs two warehouses: LOAD_WH writes new orders in; ANALYTICS_WH answers the dashboard. Both see the same ORDERS table. Example value

07

Why separating storage and compute matters

In plain wordsIn many older warehouses, data lives on the same machines that run queries. Need more speed? Buy more machines and move data around. One team’s huge report slows everyone else. Snowflake keeps data in one place and lets each team rent its own reading room: the loaders, the analysts and the data scientists never queue behind each other.

New words

shared-nothingAn older design where each machine stores and processes its own slice of data.
workload isolationDifferent jobs running on separate compute so they cannot slow each other.
concurrencyHow many queries run at the same time.

Because every warehouse reads the same storage, you can give each workload its own compute, size it independently, and pay for each only while it runs.

  • No contention between teams that use different warehouses. Guaranteed
  • Scale compute in seconds without moving any data.
  • Storage grows on its own, without buying compute you do not need.
The data science team runs a 40-minute model-training query. How do you stop it slowing down the morning dashboard?
Give data science its own warehouse. Both read the same storage, but the dashboard’s warehouse is a separate cluster that the training query never touches.

Marco’s nightly reload runs on LOAD_WH at the same time as Priya’s queries on ANALYTICS_WH. Neither notices the other.

08

Micro-partitions

In plain wordsSnowflake does not store a table as one big file. It cuts it into many small files, each holding a slice of the rows, stored column by column and compressed. For every file it also writes a little label: the smallest and largest value of each column inside. Those labels are what make the next lesson possible.

New words

micro-partitionOne of the small, immutable files a table is split into, holding 50 to 500 MB of uncompressed data.
immutableNever changed after it is written; an update writes a new micro-partition instead.
metadataData about the data, such as each micro-partition’s min and max per column.

Every table is stored as many small, immutable, columnar files called micro-partitions, and Snowflake keeps the minimum and maximum of every column for each one.

  • 50 to 500 MB uncompressed each, much smaller once compressed. Guaranteed
  • Created automatically as data is loaded, in the order it arrives. You do not define them.
  • Never edited: an UPDATE writes new micro-partitions and retires the old ones, which is also how Time Travel works (Part 5).
What two things does Snowflake record about each column of every micro-partition, and why?
The minimum and maximum value (plus counts such as nulls and distinct values). They let the optimizer skip micro-partitions that cannot contain matching rows, without opening them.

Follow the dashboard

Order 90217 sits in one of the micro-partitions loaded on 4 October; that partition’s order_date label reads min 2026-10-04, max 2026-10-04. Example value

09

Pruning: skipping data without reading it

In plain wordsBefore reading anything, Snowflake checks each micro-partition’s label. If the dashboard wants 4 October and a label says “1 October to 1 October”, that file is skipped without being opened. When the table is stored roughly in date order, a one-day question opens one day’s files out of a whole year.

New words

pruningSkipping micro-partitions whose min/max show they cannot match the filter.
scanActually reading data from storage.

Pruning uses the min and max labels to skip micro-partitions that cannot match a query’s filter, so how well the data is ordered decides how much a query reads.

Try it: one year of orders, 365 micro-partitions

Each square is one micro-partition. Yellow is scanned; faded is pruned. One partition per day of rows, labels computed from the rows each holds. Simplified

  • Filters on well-ordered columns prune well. Dates usually are, because data arrives over time.
  • Functions can hide a column from pruning: prefer order_date = '2026-10-04' over wrapping the column in an expression when you can.
  • The query profile shows it: “Partitions scanned” versus “Partitions total”. Guaranteed · check 3
A table was backfilled with a year of orders in random order. Why does a “yesterday only” query read almost everything?
Each micro-partition then holds rows from all over the year, so its min and max span nearly the whole year and none can be ruled out. Pruning only helps when each partition covers a narrow range of the filtered column.

10

Clustering and clustering keys

In plain wordsPruning works when rows with similar values sit in the same micro-partitions. Data loaded day by day is naturally sorted by date. If your queries filter on something else, or the order gets scrambled by updates, you can ask Snowflake to keep the table sorted by chosen columns in the background, for a fee.

New words

clusteringHow well rows with similar values are grouped into the same micro-partitions.
clustering keyColumns you ask Snowflake to keep the table ordered by.
clustering depthHow many micro-partitions overlap for a given value; lower is better.

Natural load order usually clusters tables by time; for very large tables queried by other columns, a clustering key makes Snowflake re-sort data in the background so pruning keeps working.

ALTER TABLE shopco.analytics.orders CLUSTER BY (order_date, country);
SELECT SYSTEM$CLUSTERING_INFORMATION('shopco.analytics.orders', '(order_date)');
  • Most tables need no clustering key. It pays off for multi-terabyte tables with selective filters. Simplified
  • Automatic Clustering is a background service billed in credits; it re-sorts only what has become disordered.
  • Put low-cardinality, commonly filtered columns first, usually a date. Clustering on a unique ID wastes money.
Why is a unique order ID usually a poor clustering key?
Queries rarely filter on ranges of order IDs, and keeping billions of distinct values sorted is expensive. Clustering pays off on columns that queries filter by and that group many rows, such as dates.

Follow the dashboard

ShopCo’s table is loaded daily, so it is already well ordered by date. They added no clustering key, and the dashboard still prunes 99% of partitions.

Part 2: Virtual warehouses and cost

Compute you switch on and off

Virtual warehouses

In plain wordsA virtual warehouse is a group of computers Snowflake lends you to run queries. You pick a T-shirt size; each size up has twice the machines and costs twice as much per hour. It starts when a query arrives, stops itself after a quiet spell, and you pay only for the seconds it ran.

New words

warehouse sizeX-Small, Small, Medium, Large… each double the previous in compute and credits per hour.
auto-resumeStart the warehouse automatically when a query arrives.
suspendedSwitched off; costs nothing and holds no cache.

A virtual warehouse is a cluster of compute nodes in one of several sizes, billed per second while running, which can suspend and resume itself.

CREATE WAREHOUSE analytics_wh
  WAREHOUSE_SIZE = 'SMALL'
  AUTO_SUSPEND   = 60        -- seconds idle before switching off
  AUTO_RESUME    = TRUE;     -- start when a query arrives
  • Each size doubles compute and price. These are the published rates for standard warehouses. Guaranteed · check 4
  • Billed per second, with a 60-second minimum each time the warehouse starts or resumes. Guaranteed
  • The SQL default for AUTO_SUSPEND is 600 seconds; many teams lower it to 60. Default · check 4
  • Resuming takes a second or two; queued queries wait for it.
A Medium warehouse runs a 30-second query after being suspended, then suspends again 60 seconds later. How many credits did that cost?
It ran for 90 seconds (30 s query + 60 s idle before auto-suspend). Medium is 4 credits per hour, so 4 × 90 / 3600 = 0.1 credits.

Scaling up versus scaling out

In plain wordsTwo different problems, two different fixes. If one big query is slow, use a bigger warehouse: more machines work on that query (scale up). If many people’s queries are queueing, add more copies of the warehouse so they run side by side (scale out).

New words

scale upResize to a bigger warehouse so each query has more compute.
scale outRun extra clusters of the same warehouse to serve more queries at once.
multi-cluster warehouseA warehouse that adds and removes clusters automatically as the queue grows and shrinks.
queuingQueries waiting because the warehouse is busy.

Resize a warehouse up when individual queries are slow; let a multi-cluster warehouse scale out when many concurrent queries are queuing.

ALTER WAREHOUSE analytics_wh SET WAREHOUSE_SIZE = 'LARGE';        -- scale up

ALTER WAREHOUSE analytics_wh SET
  MIN_CLUSTER_COUNT = 1  MAX_CLUSTER_COUNT = 4                     -- scale out
  SCALING_POLICY = 'STANDARD';
  • Multi-cluster warehouses need Enterprise edition. Edition
  • Scaling policy: Standard (the default) adds clusters quickly to avoid queuing; Economy waits longer to save credits.
  • Bigger is not always faster: a query that is already quick, or one that reads little data, gains nothing from a larger size.
At 9 am many analysts complain their small queries wait in a queue, but each runs fast once started. Scale up or scale out?
Scale out: the problem is concurrency, not the speed of each query. A multi-cluster warehouse adds clusters to run the queued queries side by side.

Follow the dashboard

The dashboard query is small and fast, so ANALYTICS_WH stays Small. On month-end, when finance runs heavy reports, it is temporarily resized to Large.

Credits, and where the money goes

In plain wordsThe bill is mostly “how big was each warehouse, times how long was it on”. A warehouse left running all night with nobody using it is the classic surprise. Short auto-suspend, right-sized warehouses and separate warehouses per team are most of cost control.

New words

credit priceDollars per credit; depends on edition, cloud, region and contract.
serverless featureWork Snowflake runs on its own compute, such as Snowpipe or Automatic Clustering, billed separately.

Compute cost is credits per hour for the size, times seconds running, times the price per credit; auto-suspend decides how much idle time you pay for.

Try it: what does the morning dashboard cost?

Assumes runs are spread out, so each one resumes the warehouse: billed time per run = max(60 s, query + auto-suspend). Simplified

  • Cloud services usage is free up to 10% of daily warehouse usage; above that it is billed. Guaranteed
  • Storage is billed per TB per month after compression, including Time Travel and Fail-safe copies.
  • Serverless features (Snowpipe, Automatic Clustering, search optimization) add their own credits.
Why can a 3-second query cost far more than 3 seconds of compute?
A resumed warehouse is billed at least 60 seconds, and keeps running until auto-suspend triggers. With a 10-minute auto-suspend, one 3-second query can bill over 10 minutes.

Keeping spend under control

In plain wordsBecause compute is pay-as-you-go, a forgotten warehouse or a runaway query can burn money quietly. A resource monitor is a budget alarm: it counts credits and can email you, or even switch warehouses off, when a limit is reached.

New words

resource monitorA credit budget with actions at chosen percentages.
statement timeoutA limit on how long one query may run before it is cancelled.

Resource monitors cap credits per period and can notify or suspend warehouses, and per-warehouse timeouts stop runaway queries.

CREATE RESOURCE MONITOR analytics_monthly
  WITH CREDIT_QUOTA = 50  FREQUENCY = MONTHLY  START_TIMESTAMP = IMMEDIATELY
  TRIGGERS ON 75 PERCENT DO NOTIFY
           ON 90 PERCENT DO NOTIFY
           ON 100 PERCENT DO SUSPEND;
ALTER WAREHOUSE analytics_wh SET RESOURCE_MONITOR = analytics_monthly;
ALTER WAREHOUSE analytics_wh SET STATEMENT_TIMEOUT_IN_SECONDS = 1800;
  • Monitors cover warehouses only, not serverless features or storage. Guaranteed
  • One warehouse per team plus a monitor per warehouse makes every team’s cost visible.
What is the difference between a resource monitor’s SUSPEND and SUSPEND_IMMEDIATE actions?
SUSPEND lets currently running queries finish and then suspends the warehouse; SUSPEND_IMMEDIATE cancels running queries at once.

Stages and file formats

In plain wordsBefore Snowflake can load files, it needs to know where they are and how to read them. A stage is a saved pointer to a folder of files, usually in your own S3 bucket. A file format says “these are JSON” or “these are CSV with a header row”.

New words

stageA named location of files for loading or unloading.
external stagePoints at your own cloud storage, such as an S3 bucket.
internal stageStorage inside Snowflake that you upload files into.
storage integrationA trust set-up that lets Snowflake read your bucket without storing keys.

A stage names a location of files and a file format describes how to parse them; together they tell Snowflake where data comes from.

CREATE FILE FORMAT shopco.raw.json_ff TYPE = JSON;

CREATE STAGE shopco.raw.orders_stage
  URL = 's3://shopco-landing/orders/'
  STORAGE_INTEGRATION = shopco_s3
  FILE_FORMAT = shopco.raw.json_ff;

LIST @shopco.raw.orders_stage PATTERN = '.*2026/10/04.*';
  • Formats: CSV, JSON, Parquet, Avro, ORC, XML. Parquet and compressed CSV load fastest. Simplified
  • Aim for files of roughly 100–250 MB compressed so loading spreads across the warehouse. Simplified
Does creating an external stage copy files into Snowflake?
No. A stage is just a named pointer to a location. Files are only read when a COPY INTO or Snowpipe load runs.

Bulk loading with COPY INTO

In plain wordsCOPY INTO is the “load these files into this table” command. A warehouse reads the files in parallel and writes micro-partitions. Snowflake also remembers which files it has already loaded, so running the same command twice does not double the data.

New words

COPY INTOThe SQL command that loads staged files into a table, or unloads a table into files.
load metadataSnowflake’s record of which files have been loaded into a table.
ON_ERRORWhat to do with bad rows: stop, skip the file, or continue.

COPY INTO loads staged files in parallel on a warehouse and skips files it has already loaded, which makes reruns safe.

COPY INTO shopco.raw.orders_raw
  FROM @shopco.raw.orders_stage/2026/10/04/
  ON_ERROR = 'SKIP_FILE';

file                         status  rows_parsed  rows_loaded
…/2026/10/04/0941-17.json    LOADED  37           37
…/2026/10/04/0942-03.json    LOADED  41           41
  • Already-loaded files are skipped for 64 days, based on load metadata. Guaranteed · check 5
  • Runs on a warehouse you choose, so give loading its own warehouse.
  • Good for batches: hourly or nightly loads of many files.
A nightly job accidentally runs COPY INTO twice over the same folder. Are the rows duplicated?
No. Snowflake’s load metadata records which files were already loaded into that table (for 64 days) and skips them on the second run.

Continuous loading with Snowpipe

In plain wordsInstead of loading once a night, Snowpipe loads each file within about a minute of it landing. S3 tells Snowflake “a new file arrived”, and Snowflake runs a COPY for it on its own compute. You do not run a warehouse for it.

New words

SnowpipeA service that loads files automatically as they arrive.
event notificationA message from S3 saying a new file was created.
latencyThe delay between a file landing and its rows being queryable.

Snowpipe runs a COPY statement automatically for each new file, triggered by cloud storage events, on serverless compute billed separately from warehouses.

CREATE PIPE shopco.raw.orders_pipe AUTO_INGEST = TRUE AS
  COPY INTO shopco.raw.orders_raw FROM @shopco.raw.orders_stage;
  • Latency is usually around a minute, not guaranteed. Simplified
  • Serverless: you pay for Snowpipe’s compute separately, not through a warehouse.
  • Very small files are inefficient; batch them into larger files when you can.
  • Need seconds, not minutes? Snowpipe Streaming writes rows directly, without files.
What tells Snowpipe that a new file needs loading when AUTO_INGEST is on?
An event notification from the cloud storage (for S3, an object-created event delivered through a queue) for each new file.

JSON and the VARIANT type

In plain wordsRaw data often arrives as JSON, with nesting and fields that change over time. Snowflake can store a whole JSON document in one column of type VARIANT and still query inside it with a simple path syntax, so you can load first and decide on columns later.

New words

VARIANTA column type that holds any JSON-like value.
pathThe way into nested data: v:customer.country.
cast (::)Convert a value to a type: ::string, ::number.
FLATTENTurns each element of an array into its own row.

A VARIANT column stores semi-structured data such as JSON, and you query it with paths, casts and FLATTEN as if it were columns.

-- raw row in ORDERS_RAW (one VARIANT column v)
{"order_id":90217,"customer":{"id":5512,"country":"DE"},"ts":"2026-10-04T09:41:07Z",
 "items":[{"sku":"KB-01","qty":1,"price":89.50},{"sku":"MS-02","qty":1,"price":40.00}]}

SELECT v:order_id::number           AS order_id,
       v:customer.country::string   AS country,
       i.value:sku::string          AS sku,
       i.value:price::number(10,2)  AS price
  FROM shopco.raw.orders_raw,
       LATERAL FLATTEN(input => v:items) i
 WHERE v:order_id = 90217;

The life of a query

In plain wordsWhen the dashboard sends its query, the services layer checks permissions, looks at the min/max labels to decide which files are needed, and makes a plan. Only then does the warehouse wake up, fetch those files, and add up the numbers across its machines.

A query is compiled and pruned in the cloud services layer, then executed in parallel on the warehouse’s nodes, which fetch only the needed columns of the needed micro-partitions.

Which part of the query’s work is done before the warehouse even starts?
Compilation in the cloud services layer: permission checks, the result-cache check, pruning with micro-partition metadata, and building the plan.

Three caches

In plain wordsSnowflake avoids repeating work three ways. If someone asks exactly the same question and the data has not changed, it hands back the saved answer for free. If a warehouse recently read some data, it keeps a copy on its own fast disks. And some questions, like counting rows, can be answered from the labels alone.

New words

result cacheSaved results of recent queries, reused for identical queries on unchanged data.
warehouse cacheRecently read data on a warehouse’s local SSDs, lost when it suspends.
metadata cacheCounts and min/max kept by the services layer, enough for some queries.

The result cache returns identical queries for free, the warehouse’s local disk cache speeds up re-reads while it runs, and metadata answers simple counts without compute.

  • Result reuse requires the same query text, unchanged underlying data, and a role allowed to see it. Guaranteed · check 6
  • Auto-suspend trades cost for warmth: suspending quickly saves credits but empties the warehouse cache.
Two analysts run the identical query five minutes apart and nothing was loaded in between. What does the second run cost?
No warehouse credits. It is answered from the result cache in the services layer, as long as both are allowed to see the data.

Spilling, and when to size up

In plain wordsBig joins and sorts need working memory. When a warehouse runs out of memory it writes the overflow to its local disk, then to remote storage, and each step is much slower. The query profile shows this as “bytes spilled”. A bigger warehouse has more memory, so the spilling stops.

New words

spillingWriting intermediate data to disk because it does not fit in memory.
local / remote spillingSpill to the warehouse’s SSD (slow) / to cloud storage (much slower).

When a query spills to local or remote storage, it needs more memory: reduce the data it handles, or run it on a larger warehouse.

  • First, read less: filter early, select fewer columns, avoid exploding joins.
  • Then, size up: a size up doubles memory and often halves the time, for a similar cost.
A query profile shows gigabytes “spilled to remote storage”. What two fixes do you try?
Reduce the data the query processes (better filters, fewer columns, fixing a join that multiplies rows), or run it on a larger warehouse with more memory.

Analytics SQL patterns

In plain wordsMost dashboards are built from a handful of SQL shapes: totals per group, totals per day, running totals, “top N per group”, and keeping only the latest version of each row. Learn these and you can answer most business questions.

New words

window functionA calculation across related rows that keeps every row, such as a running total.
PARTITION BYIn a window function, the groups the calculation restarts for.
QUALIFYSnowflake’s filter on window-function results.

GROUP BY, date truncation, window functions and QUALIFY cover most dashboard questions in a few lines of SQL.

-- revenue per country per day
SELECT DATE_TRUNC('day', order_ts) AS day, country, SUM(amount) AS revenue
  FROM orders GROUP BY 1, 2;

-- running total within the month
SELECT order_date, SUM(amount) AS revenue,
       SUM(SUM(amount)) OVER (PARTITION BY DATE_TRUNC('month', order_date)
                              ORDER BY order_date) AS month_to_date
  FROM orders GROUP BY order_date;

-- top 3 products per country
SELECT country, sku, SUM(price) AS sales
  FROM order_items GROUP BY 1, 2
QUALIFY ROW_NUMBER() OVER (PARTITION BY country ORDER BY sales DESC) <= 3;

-- keep only the latest version of each order (deduplicate)
SELECT * FROM orders_raw_flat
QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY loaded_at DESC) = 1;
What does QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY loaded_at DESC) = 1 keep?
For each order_id, only the row with the latest loaded_at, which removes older duplicate versions of the same order.

Part 5: Time Travel, cloning, pipelines, sharing

What immutable files make possible

25

Time Travel

In plain wordsBecause micro-partitions are never edited, an UPDATE or DELETE writes new files and keeps the old ones for a while. So you can ask “what did this table look like an hour ago?”, or bring back a table you dropped by mistake, with ordinary SQL.

New words

Time TravelQuerying or restoring data as it was at an earlier moment.
retention periodHow long old versions are kept for Time Travel.
UNDROPRestore a dropped table, schema or database within retention.

Time Travel lets you query, clone or restore data as it was at any point within the retention period, because old micro-partitions are kept.

SELECT COUNT(*) FROM orders AT(OFFSET => -60*60);              -- one hour ago
SELECT * FROM orders BEFORE(STATEMENT => '01b7c3a2-…');          -- just before a statement
CREATE TABLE orders_restored CLONE orders AT(TIMESTAMP => '2026-10-05 09:29:00'::timestamp_ltz);
DROP TABLE orders;  UNDROP TABLE orders;
  • Default retention is 1 day. Default · check 7
  • Up to 90 days on Enterprise edition for permanent tables. Edition
  • UNDROP brings back a dropped table, schema or database within retention. Guaranteed · check 8
  • Retention costs storage: changed and deleted data is kept and billed for the period.
Someone ran DELETE FROM orders without a WHERE clause twenty minutes ago. How do you get the rows back?
Use Time Travel: for example create a clone of the table AT a timestamp just before the delete (or insert the rows back from a SELECT … AT/BEFORE query). It works within the retention period.

Fail-safe

In plain wordsAfter Time Travel’s window ends, Snowflake keeps the old data for seven more days in a vault only Snowflake staff can open. It is a last resort for disasters, not something you can query yourself.

New words

Fail-safeA 7-day period after Time Travel during which only Snowflake support can recover data.
transient tableA table with no Fail-safe and at most 1 day of Time Travel, cheaper to keep.

Fail-safe keeps permanent tables’ historical data for 7 days after Time Travel ends, recoverable only by Snowflake, and it adds to storage cost.

  • 7 days, not configurable, for permanent tables. Guaranteed
  • Transient and temporary tables have no Fail-safe: use them for staging data you can reload, to save storage.
Why might a team store its intermediate staging tables as TRANSIENT?
Staging data can be rebuilt from the source, so it does not need Fail-safe’s 7 days of extra copies. Transient tables skip Fail-safe and cut storage cost.

Zero-copy cloning

In plain wordsCopying a 10 TB table normally takes hours and doubles your storage. A Snowflake clone just copies the list of micro-partitions, so it is instant and free at first. Only data you change afterwards gets new files.

New words

cloneA new table, schema or database that starts by sharing the original’s micro-partitions.

CLONE creates a full, independent copy of a table, schema or database instantly by pointing at the same micro-partitions; storage is used only for later changes.

CREATE DATABASE shopco_dev CLONE shopco;                         -- seconds, for any size
CREATE TABLE orders_backup CLONE orders AT(OFFSET => -3600);    -- combine with Time Travel
  • Instant and initially free. Guaranteed · check 9
  • Great for testing: give developers a full copy of production to break.
Why does cloning a 10 TB database not double the storage bill on day one?
The clone only copies metadata pointing at the same immutable micro-partitions. New storage is used only when either side changes data.

Pipelines inside Snowflake: streams, tasks and dynamic tables

In plain wordsRaw JSON arrives every minute; the clean ORDERS table must keep up. A stream remembers what is new in a table since you last looked. A task runs SQL on a schedule. Together they process only new rows. A dynamic table does the same with one statement: “keep this query’s result no more than N minutes stale”.

New words

streamA record of the changes to a table since it was last read.
taskSQL that Snowflake runs on a schedule or when a condition is true.
dynamic tableA table defined by a query that Snowflake keeps refreshed within a target lag.
incrementalProcessing only what changed, not everything again.

Streams track changes, tasks schedule SQL, and dynamic tables declare a refreshed result, so transformations can run incrementally inside Snowflake.

-- the declarative way
CREATE DYNAMIC TABLE shopco.analytics.orders
  TARGET_LAG = '5 minutes'  WAREHOUSE = load_wh
AS
SELECT v:order_id::number AS order_id, v:customer.id::number AS customer_id,
       v:customer.country::string AS country, v:ts::timestamp_ntz::date AS order_date,
       v:amount::number(10,2) AS amount            -- … 15 more columns, trimmed
  FROM shopco.raw.orders_raw
QUALIFY ROW_NUMBER() OVER (PARTITION BY v:order_id ORDER BY v:ts DESC) = 1;
  • Streams and tasks: full control, you write the MERGE yourself.
  • Dynamic tables: say what the result is; Snowflake works out how to refresh it, incrementally when it can.
What does a stream on a table give a task that a plain SELECT on the table does not?
Only the rows that changed since the stream was last consumed, with what kind of change each was, so the task can process new data incrementally instead of the whole table.

Data sharing

In plain wordsSending data to a partner usually means exporting files, emailing them and keeping them in sync. In Snowflake you can grant another account access to live tables instead. Nothing is copied: they query your micro-partitions on their own warehouse, so they pay for their queries and see updates instantly.

New words

shareAn object that grants another Snowflake account read access to chosen tables.
provider / consumerThe account sharing the data / the account receiving it.
MarketplaceA catalogue of datasets other companies share, some free, some paid.

Secure data sharing gives another account live, read-only access to your data without copying it; the consumer pays for the compute it uses.

CREATE SHARE shopco_supplier_share;

Who pays for the compute when a consumer queries a share?
The consumer, on its own warehouse. The provider pays only for storing the data it already owns.

Roles and access control

In plain wordsIn Snowflake you never give permissions to a person directly. You give permissions to a role, like “analyst”, and give people roles. When Priya changes teams, you change her role, not fifty grants.

roleA named bundle of permissions.
grantGiving a privilege (like SELECT) on an object to a role, or a role to a user.

Masking and row access policies

In plain wordsSometimes people may see a table but not everything in it. A masking policy shows “***” instead of an email to most roles. A row access policy shows each country manager only their own country’s rows. The rule lives with the data, so it applies in every tool.

New words

masking policyA rule that hides or transforms a column’s values depending on who is asking.
row access policyA rule that filters which rows a role can see.
PIIPersonally identifiable information, such as emails and addresses.

Masking policies hide column values and row access policies filter rows based on the querying role, enforced in every query.

CREATE MASKING POLICY email_mask AS (val string) RETURNS string ->
  CASE WHEN CURRENT_ROLE() IN ('SUPPORT') THEN val ELSE '***MASKED***' END;
ALTER TABLE customers MODIFY COLUMN email SET MASKING POLICY email_mask;

CREATE ROW ACCESS POLICY country_rows AS (c string) RETURNS boolean ->
  CURRENT_ROLE() = 'ANALYST' OR c = (SELECT country FROM role_country WHERE role = CURRENT_ROLE());
ALTER TABLE orders ADD ROW ACCESS POLICY country_rows ON (country);
  • Both need Enterprise edition. Edition
  • One policy, every tool: BI, notebooks and SQL all get the same result for the same role.
Why is a masking policy safer than hiding a column in each dashboard?
The policy is enforced by Snowflake on every query against the column, whatever tool runs it. Dashboard-level hiding only protects that one dashboard.

So transformations can be fixed and rerun from the original data at any time, without going back to the sources.
