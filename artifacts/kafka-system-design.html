Part 0: Start here

No messaging knowledge needed

01

Why services send messages

In plain wordsA shop’s checkout has to tell the warehouse, the email system and the analytics team about each order. Phoning each of them and waiting for an answer means one busy line holds up the customer. Dropping a note in each team’s inbox lets the checkout finish at once; each team reads its notes when it is ready.

New words

serviceA separate program that does one job, such as checkout or email, talking to others over the network.
synchronousThe caller waits for the answer before continuing.
asynchronousThe caller hands over the work and continues without waiting.
messageA piece of data sent from one service for others to read later.

When one service calls several others directly, it is only as fast and as reliable as the slowest of them; sending a message and moving on removes that dependency.

  • Decoupling: the sender does not need to know who reads, how many readers there are, or whether they are up.
  • Buffering: a burst of orders piles up as messages and is worked through, instead of overloading every service at once.
  • The cost: the sender no longer gets an immediate answer from the readers.
Why does calling three services directly make checkout slower and less reliable than sending one message?
Checkout must wait for all three and fails if any one of them fails. With a message, checkout only waits for the message to be stored; each service reads it later at its own pace.

02

Events: writing down what happened

In plain wordsA command says “send this email”: it is addressed to one service. An event says “order 7001 was paid”: it is addressed to nobody in particular. The email service decides to send an email, the warehouse decides to pack the box, and tomorrow a new fraud service can start listening without anyone changing checkout.

New words

eventA record of something that happened, written in the past tense.
producerA program that writes events.
consumerA program that reads events.
payloadThe content of the event, often JSON.

An event is a message that records a fact that already happened, like “order 7001 was created”, so that any service interested in that fact can react to it.

{
  "type":       "OrderCreated",
  "order_id":   7001,
  "user_id":    123,
  "product_id": 501,
  "total":      49.99,
  "at":         "2026-10-04T10:00:00Z"
}
  • Events are facts, so they are never edited; a correction is a new event.
  • Order 7001 produces three events over its life: OrderCreated, PaymentReceived, OrderShipped.
What is the difference between the command “SendConfirmationEmail” and the event “OrderCreated”?
The command tells one specific service to do one thing. The event states a fact; any number of services can react to it in their own way, and new ones can be added without changing the sender.

03

Kafka in five words

In plain wordsPicture a set of notebooks. A topic is a subject, like “orders”. Because one notebook would fill too fast, the subject gets several notebooks (partitions). Every line in a notebook has a line number (offset). The notebooks sit on shelves in different rooms (brokers). Readers work in teams (consumer groups) that split the notebooks between them.

New words

topicA named stream of events, such as shop.orders.
partitionOne of the parallel, ordered logs a topic is split into.
offsetAn event’s line number inside its partition: 0, 1, 2, …
brokerA Kafka server that stores partitions and answers producers and consumers.
consumer groupA team of consumers that share a topic’s partitions between them.

Kafka stores events in named topics; each topic is split into partitions; each event gets a numbered position called an offset; servers called brokers hold the data; and consumers read in groups.

  • Reading does not delete. Each consumer group just remembers the offset it has reached.
  • Order is kept inside a partition, not across partitions. Part 5 explains how to use that.
Two events sit at offset 2. Can they be different events?
Yes, if they are in different partitions. Each partition numbers its own events from 0, so an offset only means something together with its partition.

Your first topic, hands on

In plain wordsKafka ships with small command-line tools. One creates topics, one lets you type events, one prints events as they arrive. Trying them once makes every later lesson concrete.

With one Kafka server on your laptop you can create a topic, write events with a producer, and read them back with a consumer in a few commands.

$ docker run -d --name kafka -p 9092:9092 apache/kafka:4.1.0
$ docker exec -it kafka bash
$ cd /opt/kafka/bin

# 1. create a topic with 3 partitions
$ ./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic shop.orders --partitions 3
Created topic shop.orders.

# 2. write events (type a line, press Enter; Ctrl+C to stop)
$ ./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic shop.orders
> {"type":"OrderCreated","order_id":7001}
> {"type":"OrderCreated","order_id":7002}

# 3. read everything from the start, as consumer group "email-svc"
$ ./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic shop.orders \
    --from-beginning --group email-svc
{"type":"OrderCreated","order_id":7001}
{"type":"OrderCreated","order_id":7002}

# 4. ask where the group got to
$ ./kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group email-svc

email-svc  shop.orders  0          2               2               0
# trimmed: both keyless lines happened to land in partition 0
  • bootstrap-server is any broker’s address; the tools learn the rest of the cluster from it.
  • Run a second consumer with a different group and it reads both events again: groups are independent.
  • Keyless lines like these may land in any partition. Real producers usually set a key (Part 3). Simplified
You restart the console consumer with the same --group and without --from-beginning. What does it print?
Only events written after it last stopped. The group’s position (its committed offset) is stored in Kafka, so it resumes where it left off.

05

Many brokers, many copies

In plain wordsIf all the notebooks sat in one room and the room flooded, everything would be gone. So each notebook is photocopied into two other rooms. One copy is the “original” that new lines are written to; the others copy each new line as soon as it appears. If the original’s room floods, a copy takes over. This lesson only introduces the words; Part 6 explains them properly.

New words

clusterSeveral brokers working together as one Kafka.
replicaOne copy of a partition, on one broker.
leaderThe replica that producers write to and consumers read from.
followerA replica that copies the leader and can take over if it fails.
controllerThe part of Kafka that tracks which brokers are alive and which replica leads each partition.

In production Kafka runs as a cluster of brokers, and every partition is copied to several of them, so losing one server loses no data.

A partition has three replicas and the broker holding the leader dies. What happens to the data?
A follower on another broker that has kept up becomes the new leader, and producers and consumers switch to it. The data is still on the surviving copies.

Part 1: Why Kafka

A log, not a queue

06

A distributed log, not a queue

In plain wordsA queue is like a to-do pile: once someone takes a task, it is gone. Kafka is more like a newspaper archive: every edition stays on the shelf, and any number of readers can each read every edition, at their own pace, even years later. That one difference explains most of what makes Kafka useful.

New words

logAn append-only list of records: new ones go at the end, old ones are never changed.
retentionHow long Kafka keeps events before deleting them, such as 7 days.
replayReading old events again, for example after fixing a bug.

A queue hands each message to one worker and deletes it; Kafka appends every event to a durable log that any number of readers can read, re-read and replay at their own pace.

  • Replay. Fix a bug, reset the group’s offset, reprocess last week. Guaranteed within retention
  • Fan-out for free. A new consumer group reads the whole stream without the producer changing.
  • Retention is time or size, not “until consumed”: 7 days by default. Default · check 1
What can a Kafka topic do that a traditional queue cannot, because reading does not delete?
Let several independent consumer groups each read every event, and let any of them replay older events by moving its offset back, as long as the data is still within retention.

07

When to choose Kafka, and when not to

In plain wordsKafka is powerful but takes real work to run. It is worth it when many services need the same events, volumes are high, or you need to replay history. For a simple job queue, a simpler tool does better.

New words

throughputHow much work gets done per second, such as events per second.

Kafka earns its operational cost when you have high volume, several independent consumers or a need to replay; for a simple job queue it is a semi-truck sent for groceries.

Choose it for

  • High-throughput event streams
  • Decoupling services; absorbing spikes
  • Event sourcing and audit logs
  • Pipelines with many sources and sinks
  • Many consumers of the same data
  • Replay after bugs or for new consumers

Avoid it for

  • Simple task queues
  • Request-reply
  • Low volume: hundreds per minute
  • Global order across all events
  • Permanent storage
  • Content-based routing
Interview systemWhy Kafka works
Activity feedHigh write volume; feed, analytics and notifications each consume
Log aggregation, metricsThousands of producers, high throughput
Event sourcingDurable, ordered, replayable log
Change data captureDatabase changes streamed to many systems
Real-time analyticsFeeds Flink or Spark
Order processingDecouples intake from fulfilment
NotificationsFan-out to email, push, SMS
In an interview. Not “we need a message queue”, but: “Inventory, email, analytics and shipping each consume every order event at their own pace, and finance wants a week of replay. Consumer groups and retention give us both.”
A team needs workers to pick up image-resize jobs, a few hundred per minute, and never needs to look at a job again. Kafka or something else?
Something simpler, like SQS or RabbitMQ. It is a plain task queue at low volume with no replay or fan-out need, so Kafka’s operational cost buys nothing.

08

Why Kafka is fast

In plain wordsKafka handles millions of events a second on ordinary machines. The secret is not clever algorithms but doing the simplest possible things with disks and networks, and doing them in bulk.

New words

sequential writeWriting to the end of a file, the fastest thing a disk can do.
page cacheMemory the operating system uses to keep recently used file data.
batchMany records sent or stored together as one unit.

Kafka gets its throughput from boring physics: it only appends to files, lets the OS cache them, sends file bytes straight to the network, and moves everything in batches.

Sequential writes

Appending to the end of a file is the fastest thing a disk does. No random seeks, no in-place updates.

The page cache

Kafka leaves caching to the operating system. Consumers near the head read from RAM without Kafka managing a cache.

Zero-copy

For plaintext connections, sendfile moves bytes from the file cache to the socket without passing through the JVM. Added

Batching

Producers send batches, brokers store them as-is, consumers fetch them. One request moves thousands of records.

Name two reasons Kafka can write millions of messages a second to ordinary disks.
Any two of: it only appends sequentially; it batches records per request; it relies on the OS page cache; it serves reads with zero-copy sendfile.

Records and keys

In plain wordsEvery event in Kafka is a record with a key, a value, a timestamp and optional headers. The key looks like a small detail but decides which partition the record goes to, and therefore which records stay in order together.

New words

recordKafka’s name for one event: key, value, timestamp, headers.
keyAn optional value, such as an order ID, used to choose the partition.
headerExtra labelled metadata on a record, such as a trace ID.

A record is a key, a value, a timestamp and headers; the key is the one field that changes behaviour, because it decides the partition and therefore the order.

  • Same key, same partition, same order. All three events for order 7001 stay in sequence. Guaranteed while the partition count is unchanged
  • Choose the key from what must stay ordered. Order lifecycle: order_id. A user’s activity: user_id.
  • Schemas belong outside the record. A schema registry stores Avro or Protobuf schemas; records carry a small schema ID. Added
Order events must be processed in order per order, but you key them by a random UUID per event. What breaks?
Each event of an order lands on a random partition, so consumers can see “shipped” before “created”. Keying by order_id puts all of an order’s events on one partition, in order.

Part 3: Producers

Throughput, keys and safety

12

Inside send()

In plain wordsWhen your code “sends” an event, nothing goes over the network yet. The event is turned into bytes, assigned to a partition and added to a batch, and a background thread sends whole batches. That is how Kafka producers move huge volumes.

New words

serializerTurns your object into bytes.
partitionerDecides which partition an event goes to.

Calling send() does not hit the network: the record is serialized, given a partition and added to a batch, and a background thread ships batches to brokers.

  1. Serialize key and value to bytes.
  2. Partition: hash the key, or pick a partition for keyless records.
  3. Accumulate into that partition’s current batch.
  4. Send when a batch is full or has waited long enough.
  5. Acknowledge: the returned future completes when the broker answers.
If the buffer fills: when brokers are slow, the accumulator (32 MB by default) fills and send() blocks for up to max.block.ms, then throws. Back-pressure reaches your request threads. Added
Why can the producer achieve high throughput even though your code calls send() once per record?
send() only adds the record to an in-memory batch for its partition. A background sender thread sends whole batches, so one network request carries many records.

13

The partitioner: keys decide everything

In plain wordsEvery event must go to exactly one partition. If it has a key, Kafka hashes the key, so the same key always lands in the same partition. If it has no key, Kafka just spreads events around. The demo shows what good and bad keys do to the load.

New words

hashA function that turns a value into a number that looks random but is always the same for the same input.
murmur2The particular hash function Kafka’s default partitioner uses.
modThe remainder after division: 14 mod 12 = 2.

With a key, the partition is murmur2(key) mod the partition count; without a key, the producer fills one partition’s batch at a time and then moves on.

key present:  partition = toPositive(murmur2(keyBytes)) % numPartitions
key null:     stick to one partition until its batch is sent, then switch (sticky)

Try it: 2,000 events, different keys

Real murmur2 from Kafka’s partitioner; the event mix is invented. Guaranteed · check 2

  • High cardinality, even spread: order_id gives every partition about the same load.
  • Low cardinality is a trap: three countries can use at most three partitions, however many you have.
  • Sticky keyless batching replaced round-robin in Kafka 2.4: fewer, fuller batches. Added
A topic has 12 partitions and you key by country, with 3 countries. How many partitions get data, and what does that do to consumers?
At most 3. The other 9 partitions stay empty, so at most 3 consumers in a group can do any work, and the busiest country’s partition limits throughput.

acks: when is a write “done”?

In plain wordsWhen should Kafka tell the producer “saved”? After nothing, after the leader saved it, or after every up-to-date copy saved it. Each step is a little slower and a lot safer.

New words

acknowledgement (ack)The broker’s reply telling the producer a write succeeded.
in-sync replicaA copy that is keeping up with the leader. Part 6 covers these in depth.

The acks setting chooses when the leader replies: never, after its own write, or after every in-sync replica has the record.

acksReply afterLatencyLost if…
0NothingLowestAnything goes wrong at all
1Leader wrote itMediumLeader dies before followers copy it
all (default since 3.0)All in-sync replicas have itHighestEvery in-sync replica dies
  • acks=all is the default since Kafka 3.0. Default · check 3 Added
  • “All” means all in-sync replicas, which can shrink to one. Lesson 28 pairs it with min.insync.replicas to stop that.
With acks=1, describe exactly how an acknowledged record can be lost.
The leader writes it and replies, then crashes before any follower fetched it. A follower becomes leader without the record, and the old leader truncates it when it rejoins.

Batching and compression

In plain wordsSending one event per network request wastes most of each request on overhead. Waiting a few milliseconds to send many together, and compressing them, moves far more data with the same effort.

New words

lingerHow long the producer waits to fill a batch before sending.
compressionShrinking data before sending, at the cost of some CPU.

Waiting a few milliseconds to fill bigger batches, and compressing them, trades a little latency for a lot of throughput.

batch.size=16384          # bytes per partition batch
linger.ms=5               # wait up to 5 ms for more records (the default since Kafka 4.0)
compression.type=lz4

Raising linger.ms from 0 to 20 ms: what gets better, what gets worse?
Throughput and compression improve because batches are fuller and requests fewer. Each record’s latency can grow by up to 20 ms.

16

The idempotent producer

In plain wordsNetworks drop replies. If the producer never hears “saved”, it sends again, and without protection Kafka would store the event twice. The idempotent producer numbers every batch so the broker can spot and drop the repeat.

New words

idempotentDoing it twice has the same effect as doing it once.
retrySending again after a failure or a missing reply.
sequence numberA counter on each batch, so repeats can be recognised.

When an acknowledgement is lost the producer must retry, and the broker uses a producer ID plus a per-partition sequence number to drop the duplicate.

Try it: the ack gets lost, the producer retries

  • On by default since Kafka 3.0. Default · check 3 Added
  • Keeps order with up to 5 requests in flight, because the broker rejects out-of-sequence batches. Guaranteed
  • Scope: one producer session, one partition. A restarted app gets a new producer ID, so app-level retries need lesson 30 or 26.
What does the idempotent producer protect against, and what does it not?
It removes duplicates caused by the producer’s own retries within one session. It does not stop duplicates if your application calls send() twice, or if a restarted producer resends, because that is a new producer ID.

Part 4: Consumers

Groups, offsets, rebalances, lag

17

Consumer groups

In plain wordsA consumer group is a team that shares the work of reading a topic. Kafka gives each partition to exactly one team member, so the work is split and each partition is still read in order. A different team gets its own full copy of the stream.

New words

assignmentWhich partitions each consumer in a group is reading.

Inside one group each partition goes to exactly one consumer, which gives parallelism without breaking order; separate groups each get the whole stream.

  • One partition, one consumer per group. That is what keeps per-key order. Guaranteed
  • A consumer can own many partitions. 8 partitions, 2 consumers: 4 each.
  • More consumers than partitions = idle consumers. Partitions cap a group’s parallelism.
  • Groups are independent: own offsets, own pace.
A topic has 6 partitions. A group runs 8 consumers. How many do work, and how would you get more parallelism?
6. Two sit idle. To use more consumers you need more partitions, or more parallelism inside each consumer (for example a worker pool per partition, keyed to keep order).

Who gets which partition

In plain wordsWhen consumers join or leave, Kafka must decide again who reads which partition. Different strategies trade simplicity against how much gets shuffled around each time.

New words

assignorThe rule that splits partitions between a group’s consumers.

Rebalancing

Lag, and one group per job

In plain wordsLag is how far behind a consumer group is: how many events have been written that it has not processed yet. Giving each kind of job its own group means one slow job only falls behind by itself.

New words

fan-outOne event being delivered to many independent readers.

Lag is how far a group is behind the end of the log, and giving each downstream job its own group means one slow job never holds up the others.

  • Lag = log-end offset − committed offset, per partition. Alert on growth, not on a fixed number.
  • Separate groups give graceful degradation: SMS down means SMS lag grows; email and push carry on, and SMS catches up later from its offset.
Why put email, push and SMS in separate consumer groups instead of one group that routes to each channel?
With separate groups each channel reads the topic independently, so a slow or broken channel only grows its own lag. With one group, a slow email call holds up the partition for push and SMS too.

Changing the partition count

In plain wordsYou can add partitions to a topic, but the hash rule then sends many keys to different partitions than before. Events for the same key can end up split across two partitions and read out of order.

You can add partitions to a topic at any time, but the key → partition mapping changes for most keys, so ordering per key breaks across the change.

  • Adding is allowed, removing is not. Guaranteed
  • Existing records do not move. Only new records follow the new mapping.
  • Safer path for keyed topics: create a new topic with the right count, dual-write or migrate, switch consumers.
Why does adding partitions to a keyed topic break per-key ordering, even though old data is untouched?
hash(key) mod N changes with N, so a key’s new events go to a different partition than its old ones. Consumers of the two partitions can process them out of order.

Replicas and the in-sync set

In plain wordsEach partition is stored on several brokers. The copies that are keeping up with the leader are called in-sync; only they are trusted to take over without losing data.

New words

replication factorHow many copies of each partition exist.
ISRIn-sync replicas: the copies that are up to date enough to become leader.

Each partition is copied to several brokers; the in-sync replicas (ISR) are the copies that are keeping up, and only they count as safe copies.

RFReplication factor: how many copies. RF 3 survives losing 2 copies’ brokers without losing data.

RuleA follower drops out of the ISR if it has not caught up to the leader’s end within replica.lag.time.max.ms (30 s).

  • A shrinking ISR is your early warning. ISR of 1 means one more failure loses data or availability.

Leader election, clean and unclean

In plain wordsWhen the broker holding a partition’s leader dies, Kafka promotes an up-to-date copy. If no up-to-date copy is left, you must choose: wait for one to come back, or promote an out-of-date copy and accept losing some events.

New words

leader electionChoosing which replica becomes the new leader.
unclean electionPromoting a replica that is missing some events.

When a leader dies, the controller promotes an in-sync replica; if none is left, you choose between waiting (unavailable) and electing a stale copy (data loss).

  • Unclean election is off by default. Default · check 9
  • Failover is fast: the controller already knows the ISR, so a clean election takes well under a second per partition. Simplified
  • Clients follow automatically: producers and consumers get “not leader” errors, refresh metadata and retry.
A partition’s only in-sync replica dies; a stale follower is alive. What happens with unclean leader election disabled, and with it enabled?
Disabled: the partition stays offline until the in-sync replica comes back, with no data loss. Enabled: the stale follower becomes leader at once, and any records it never received are lost.

The high watermark

In plain wordsConsumers are only shown events that every up-to-date copy already has. The high watermark is the line that marks that point, so no consumer ever reads an event that a failover could make disappear.

New words

high watermarkThe first offset not yet on every in-sync replica; consumers read below it.
committed (event)Stored on every in-sync replica, so it cannot be lost by a single failure.

Consumers may only read records that every in-sync replica has, and the high watermark marks that line, so no consumer ever sees a record a failover could erase.

  • The high watermark is exclusive: it is the first offset not yet committed. Your notes say “HW = 6” for the same picture; Kafka would report 7. Guaranteed · check 7 Added
  • Followers report progress by fetching: asking for offset 7 tells the leader they have everything below 7.
  • acks=all waits for the high watermark to pass your record before replying.
Why can a consumer not read a record the leader has written but the followers have not?
Because that record is above the high watermark. If the leader crashed, a follower without it would become leader and the record would vanish, so a consumer that had read it would have acted on data that no longer exists.

Part 7: Delivery guarantees

Lost, duplicated, or exactly once

At-most-once, at-least-once, exactly-once

In plain wordsA consumer does two things per event: the work (say, send an email) and saving its position. A crash between the two means either the work is lost or it is repeated, depending on the order. That choice is called the delivery guarantee.

New words

at-most-onceNever repeated, but may be lost.
at-least-onceNever lost, but may be repeated.
exactly-onceNeither lost nor repeated.

Where the consumer commits relative to processing decides what a crash does: commit first and you may lose work, process first and you may repeat it.

Try it: email-svc crashes while handling order 7001

GuaranteeProducerConsumerUse for
At-most-onceacks 0 or 1, no retriesCommit, then processMetrics, logs where gaps are fine
At-least-onceacks=all, retriesProcess, then commitMost applications
Exactly-onceIdempotent, transactionalread_committed, offsets in the transaction, or idempotent processingMoney, counts that must be right
Pick at-least-once by default and make processing idempotent. That gives “effectively once” almost everywhere.
A consumer processes a record and crashes before committing. Under at-least-once, what happens after restart?
It resumes from the last committed offset, which is before that record, so the record is processed a second time.

Idempotent consumers and de-duplication

In plain wordsIf doing the work twice gives the same result as doing it once, repeats are harmless. When that is not naturally true, the consumer can remember the IDs of events it has already handled and skip repeats.

New words

deduplicationDetecting and skipping repeats.
event IDA unique identifier for each event, used to recognise repeats.

If processing a message twice has the same effect as once, duplicates stop mattering; when it does not, remember which message IDs you have handled.

  1. Give every event an ID at the producer: event_id, or topic-partition-offset.
  2. Check before acting: has this ID been processed?
  3. Record the ID in the same transaction as the effect, so they cannot disagree. Added
  4. Expire old IDs after the longest retry window.
-- de-duplicating consumer, MySQL
START TRANSACTION;
INSERT INTO processed_events (event_id) VALUES ('evt-7001-paid');   -- fails if seen: skip
UPDATE stats SET paid_orders = paid_orders + 1;
COMMIT;
Why should the processed-ID record and the side effect be written in the same database transaction?
Otherwise a crash between them leaves one without the other: either the effect happened but the ID was not saved (it will happen again), or the ID was saved but the effect did not happen (it is skipped forever).

Transactions: exactly-once inside Kafka

In plain wordsFor programs that read from Kafka and write back to Kafka, transactions make three things happen together or not at all: the output events, and the saved input position. That is exactly-once, as long as you stay inside Kafka.

New words

transactionA group of writes that become visible together, or not at all.
read_committedA consumer setting that hides events from unfinished or cancelled transactions.

A Kafka transaction makes “read from one topic, write to another, commit my input offset” all-or-nothing, which is exactly-once for pipelines that stay inside Kafka.

# producer
enable.idempotence=true
transactional.id=order-enricher-1
# downstream consumers
isolation.level=read_committed       # the default is read_uncommitted
  • Zombie fencing: a restarted instance with the same transactional.id bumps an epoch; the old instance’s writes are rejected. Added
  • Consumers see uncommitted writes by default. Downstream readers must set read_committed, or aborted records reach them. Default · check 10 Added
  • Only covers Kafka. Sending an email or writing to MySQL inside the loop is outside the transaction; use lesson 30 for those.
  • Costs latency: consumers see results only at commit, so commit interval adds delay.
Can Kafka transactions guarantee that an email is sent exactly once? Why or why not?
No. Transactions only make Kafka writes and offset commits atomic. An email is an external side effect, so it needs idempotent handling, such as recording a sent-email ID.

The designs interviews ask for

Fan-out: one event, many reactions

In plain wordsInstead of the order service calling four other services, it publishes one event and each service listens for it. Adding a fifth service later needs no change to the order service at all.

Instead of the order service calling four services, it publishes one event and each service subscribes with its own consumer group.

Direct calls

  • Order service knows every downstream
  • One slow service slows checkout
  • One failure needs retry logic in the caller

Fan-out via Kafka

  • Producer knows only the topic
  • Each group has its own pace and lag
  • A failed service catches up from its offset
The catch: the checkout no longer knows when shipping finished. Anything the user must see immediately still needs a synchronous answer or a status the UI can poll.
What do you have to change in the producer to add a new downstream consumer in a fan-out design?
Nothing. The new service creates its own consumer group and starts reading the topic, from the beginning of retention if it wants history.

Event sourcing, and compacted topics

In plain wordsMost systems store only the latest state: “order 7001 is shipped”. Event sourcing stores every change instead, and works out the current state by replaying them. Kafka is a natural place to keep those changes in order.

New words

event sourcingStoring every change as an event and deriving current state from them.
compactionKeeping only the latest event for each key.

In event sourcing the events are the source of truth and current state is computed by replaying them; Kafka holds the ordered event log, and compacted topics hold the latest state per key.

  • Gains: a complete audit trail, replay, “what did this order look like at 10:05?”, many views from one log.
  • Costs: schemas must evolve carefully forever, and rebuilding from years of events is slow, so services keep snapshots.
  • Retention must match: a 7-day topic is not an event store. Use infinite retention, tiered storage or a database for the full history.
What is the difference between a topic with 7-day retention and a compacted topic?
Retention deletes whole old segments by age or size, regardless of key. Compaction keeps the latest record for every key forever (and drops older records for the same key), so it always holds current state per key.

CQRS: separate write and read models

In plain wordsWriting data and reading data often want different shapes. CQRS keeps one model for writes, publishes events, and builds separate read-optimised copies from those events, such as a search index or a cache.

New words

CQRSCommand Query Responsibility Segregation: separate models for writes and reads.
read modelA copy of the data shaped for one kind of query.
eventually consistentUp to date after a short delay, not instantly.

Commands update one model built for correctness, which publishes events; each read model consumes them and stores the data shaped for its queries.

  • Each side scales and is optimised separately.
  • Read models are eventually consistent: right after a write, a read model may not have it yet. Show the user their own write from the write side or wait for it.
  • Read models are disposable: drop one, replay the events, and it is rebuilt.
A user places an order and immediately searches for it, but the search index does not have it yet. Why, and what are two fixes?
The search read model is updated asynchronously from Kafka, so it lags the write. Fixes: show the new order from the write side for a short time, or have the UI wait until the read model has processed the event (for example by checking its offset).

Dead letter queues and retry topics

In plain wordsIf one event can never be processed (say its data is corrupt), retrying forever would block every event behind it. After a few tries it is moved aside to a separate topic for a person to look at.

New words

A message that keeps failing must not block its partition forever, so after a few retries it is moved to a dead letter topic for people to inspect.

Why does one bad message in a Kafka partition need special handling that a queue with many workers might not?
A partition is consumed in order by one consumer per group, so if that message keeps failing nothing behind it is processed. Moving it to a dead letter topic lets the partition continue.

Quick revision and glossary

In plain wordsTest yourself with every quick check from the course, then look up any word you have forgotten in the glossary.

Test yourself, then look up any term.

What three settings make a write survive one broker failure without data loss and keep accepting writes?
replication.factor 3, min.insync.replicas 2, and acks=all on the producer (plus unclean leader election disabled, the default).
What decides the ordering guarantee you get, and what can silently break it later?
The record key: same key, same partition, same order. Adding partitions to the topic changes which partition a key maps to, which breaks per-key order across the change.
Give the usual recipe for “effectively once” processing that writes to a database.
At-least-once delivery (process, then commit offsets) plus an idempotent consumer, for example recording each event ID in the same database transaction as its effect.
